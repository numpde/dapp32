Contract Application Manifest (CAM) 1.1.0

Experimental draft. UI document version: 1.0.0. Implementation baseline: 6a3c3c4. Revisions of this document are tracked in Git; they do not change either wire version.

A CAM host exposes a manifest URI and hash through contract read calls. This repository's CamRoot host stores them and its named contract address bindings on chain. The manifest JSON, contract ABIs, and UI JSON are external resources: an agent or viewer downloads, verifies, and interprets them off chain to prepare calls and display views. The called contracts enforce their business rules when the EVM executes those calls.

This reference is for AI and LLM coding agents and the people reviewing their work. It explains the document model and the repository's EVM execution profile so a reader can author or interpret a bundle without starting from an application example. It describes verified behavior at the baseline, rather than claiming a complete independent standard or interoperability with other implementations.

How the contract, bundle, and host work together

A bundle consists of the externally stored CAM JSON document, contract ABIs, and a UI JSON document. The ABI describes callable EVM functions and their value types; it is not the deployed contract code. The UI document describes named views and controls. Off-chain software interprets the manifest's namespaces and routes to join these resources; the host contract does not fetch or interpret the bundle.

In this document, document rules describe accepted CAM/UI shapes. EVM profile describes this repository's adapter. runtime policy describes loader or viewer choices. Authoring advice is identified as advice. A rejection during document loading is separate from a contract revert during execution.

Find and verify a manifest

Start with an independently selected chain and CAM host address. The EVM profile uses a chain identifier such as eip155:1, with a positive safe-integer chain number, checks the RPC client's chain, and checks ERC-165 support for ICamApp (0x03625ff6). That interface exposes camURI() and camHash(). This repository's CamRoot extension additionally supplies contractAddress(string). The lookup argument is the bare contract name: contracts.Registry maps to Registry.

The host lookup needs a bootstrap ABI before the advertised ABIs are available. These signatures describe the calls used by this profile:

function supportsInterface(bytes4 interfaceId) external view returns (bool);
function camURI() external view returns (string);
function camHash() external view returns (bytes32);
function contractAddress(string contractName) external view returns (address);

The loader requires supportsInterface(0x03625ff6) to return true; false or a failed read blocks loading. The CAM interface ID excludes the inherited ERC-165 selector. The adapter uses the separately known binding signature after loading the manifest; support for ICamApp alone does not assert support for that extension.

A nonboolean interface response is also rejected. The URI must be a string, the root hash must be 0x plus 64 hexadecimal digits, and each contract binding must be a valid nonzero EVM address. Malformed responses fail at the host or binding boundary.

Contract bindings are separate, mutable host facts. The root hash does not commit to their addresses, and loading does not promise an atomic snapshot of root URI, hash, and bindings. An agent reviewing a transaction needs to inspect the actual selected chain and resolved destination.

A JavaScript safe integer is an integer from −9,007,199,254,740,991 to 9,007,199,254,740,991. EVM chain identifiers use only the positive part of this range; expression array indexes use only the nonnegative part.

The root commitment is Keccak-256 of the manifest bytes, stored on chain and returned as bytes32. The off-chain loader downloads those bytes, computes their hash, and compares it with the contract-returned commitment before parsing JSON. Reformatting JSON changes those bytes even when the parsed objects appear equivalent. A zero root hash is rejected by default; the adapter's explicit unsigned-loading option permits it and skips root hash verification. Do not describe such a load as contract-anchored integrity.

Contract ABI and UI declarations in the external manifest carry integrity in the form sha256:0x followed by exactly 64 lowercase hexadecimal digits. The off-chain loader verifies SHA-256 of each resource's original bytes before parsing it. This second commitment lets the verified root manifest bind the resources it references, even though their bytes are stored off chain. Neither digest authenticates a human author's identity or proves that an ABI matches deployed bytecode.

Supported IPFS spellings are CIDv0 base58btc (Qm plus 44 base58btc characters) decoding to a SHA-256 multihash, or lowercase CIDv1 base32 with version 1, raw (0x55) or dag-pb (0x70) codec, and a 32-byte SHA-256 multihash. IPFS roots and secondaries use the same path restrictions shown above; credentials, trailing slashes, and query or fragment components are rejected. URI acceptance does not supply an IPFS transport. A caller-provided loader still has to retrieve the bytes.

Relative resource references resolve against the directory of the original camURI: https://example.org/app/main.json plus ./abi/Registry.json becomes https://example.org/app/abi/Registry.json. The same rule applies to the UI resource.

Resolution drops the root's query and fragment: https://example.org/app/main.json?rev=2#section plus ./ui/main.json becomes https://example.org/app/ui/main.json.

Runtime policy: the shared HTTP loader restricts requests to a selected origin, refuses redirects, and bounds decoded response bytes to 2 MiB per resource. A custom loader has its own access and timeout responsibilities; accepting a URI is not permission to access arbitrary network or local resources. The adapter also checks returned resource size. A zero or invalid contract binding is rejected.

Declare the manifest and namespaces

CAM is declarative JSON interpreted off chain. Its root has exactly cam, entry, namespaces, and routes. cam is "1.1.0"; the readers also accept explicit "1.0.0" documents. entry names an existing route. Unknown fields are rejected at the closed document, namespace, route, and invocation boundaries.

Namespace nameDeclaration fieldsPurpose
contracts.<Name>type: "contract", abiURI, integrityCalls a host-bound contract. Name matches [A-Za-z_][A-Za-z0-9_]*.
routestype: "routes"Names routes within this manifest; has no external resource.

Invocations use {"namespace": "…", "function": "…", "args": {…}}. The namespace has to exist and have the type allowed at that call site. In CAM routes, function is a nonempty literal name. Argument values may contain expressions recursively. An ABI call's argument keys are ABI parameter names, not positions.

Define routes, arguments, and results

A route has kind, inputs, call, and then. inputs declares its complete external argument interface as an array of unique expression identifiers. Route execution rejects missing and additional input names before resolving either invocation, even if the route does not read every input.

Kindcallthen
readContract namespace; EVM function is view or pure.UI namespace; passes resolved arguments to a named UI node.
writeContract namespace; EVM function is nonpayable or payable.Routes namespace; the viewer's write continuation goes to a read route after successful confirmation.

EVM profile: a bare function name must identify one ABI function; an overloaded bare name is ambiguous and rejected. A full signature using the types declared in the supplied ABI, such as lookup(uint256), selects an overload. The named arguments must match its named inputs, including tuple component names. The adapter checks the following value shapes and ranges before calling. Use decimal strings to avoid rounding large integers. Fixed-size arrays are unsupported in this profile.

Signature matching uses the supplied ABI's type spellings without whitespace, expands tuple components inside parentheses, and retains array suffixes. For example, a tuple of uint256 and address has signature type (uint256,address). The adapter does not rewrite uint to uint256 while matching signatures.

ABI value typeAccepted input and normalization
uintN, intNN is 8–256 in steps of 8; bare uint/int mean 256. Strings match -?[0-9]+, or numbers are safe integers. Values must fit the type: unsigned 0 through 2N−1, signed −2N−1 through 2N−1−1. Leading zeros and negative zero are accepted where in range.
addressString 0x plus 40 hexadecimal digits; ABI normalization lowercases it.
bytes, bytesNString 0x plus complete hexadecimal byte pairs. Dynamic bytes permits empty 0x; N is 1–32 and requires exactly N bytes.
bool, stringBoolean or string respectively, without converting text into booleans.

Read outputs are a positional array: no ABI outputs produces []; one ABI output produces one array item, even if that item is itself an array or tuple. Integer outputs become decimal strings, addresses become lowercase strings, bytes remain hexadecimal strings, and named tuple components become object fields. A continuation can use $outputs.0 or $outputs.0.component. ABI output names do not create expression roots.

Top-level ABI outputs may be unnamed because their position identifies them. Tuple components, including components of output tuples, must have unique nonempty names; unnamed or duplicated components are rejected. This lets an agent select tuple fields by name without guessing how a decoder represented them.

The adapter validates the entire loaded ABI array, including functions no route currently calls. Unsupported parameter types, malformed function declarations, and duplicate function signatures reject the ABI; nonfunction entries receive only an object/type check, so this is not a comprehensive ABI linter. Separately, a read result with the wrong count, shape, or range is rejected at runtime rather than silently converted or skipped.

Native transaction value in CAM 1.1.0

A write route may additionally declare value, as a literal or expression. It is transaction value in the chain's native base unit, separate from call.args. For a payable function this profile requires an explicit value, including "0" for zero. It must resolve to a decimal uint256 value. A nonpayable function rejects any declared value, including zero. Read routes and CAM 1.0.0 routes reject the value field.

Advice: publish an explicit unit with any amount editor and pass its canonical base-unit string as route input. A token amount in ABI arguments is not automatically native transaction value; transferring a token remains a contract operation.

Resolve expressions

The off-chain runtime resolves expressions by selecting values already supplied to it. Expressions do not evaluate JavaScript, perform arithmetic, concatenate strings, or fetch resources. An expression occupies the entire string. A normal string is literal; a leading $$ escapes one dollar sign.

Runtime values are inert: strings, finite numbers, booleans, null, arrays, and plain objects containing those values. Functions, undefined values, bigint values, and cycles are rejected. EVM integer results are converted to decimal strings before entering this model.

reference  = "$" identifier ("." segment)*
identifier = [A-Za-z][A-Za-z0-9_]*
segment    = identifier | arrayIndex
arrayIndex = "0" | [1-9][0-9]*  (within JS safe-integer range)

Array indexes have no leading zeros; $outputs.01, empty segments, bracket notation, and operator syntax are invalid. Selection traverses arrays by numeric index and objects by their own fields. A missing root or segment fails resolution; it does not become null or an empty string. Selecting an existing null leaf succeeds; traversing through it fails. Recursive resolution preserves the selected value's type. A selected string beginning with $ is a value, not a second expression to execute.

Advice: use $outputs in the continuation of the read that produced it, and pass needed values into the next route explicitly. A write does not turn a Solidity return value, receipt, or event into route outputs.

Describe a UI 1.0.0 view

A UI document has exactly ui: "1.0.0" and a nonempty nodes object. Each named node declares requires, either [] or ["view"]; its caller supplies exactly those argument names. The view value is the explicit handoff from a route or another UI node. Inline children have no requires. Runtime roots such as host and state cannot be shadowed by node arguments.

The element vocabulary is closed. Each element accepts only its listed structure and props, plus the named-node requires declaration. String props may be expressions but have to resolve to strings. There are no style, script, event-handler, or arbitrary HTML fields.

Status with stringList requires an array of strings, displays an empty array as None, and otherwise joins entries with comma and space. bytes and durationSeconds require a nonnegative decimal integer string or safe nonnegative integer number. Bytes are comma-grouped with singular/plural units, such as 1 byte or 1,024 bytes. Durations below 60 use seconds; larger values use nonzero day/hour/minute/second parts followed by total seconds, such as 1 minute, 1 second (61 seconds). Without a format, the host chooses the presentation of the inert value.

Publication tool policy: this repository's conformance typeflow check expects statically known Nft.tokenId references to provide an integer or string; known boolean, tuple, or array references receive a diagnostic. That check does not restrict literal values at this site. The screen runtime's acceptance of any inert token ID remains a separate boundary.

State and typed editing

UI $state holds off-chain editable values; editing a field does not submit a transaction or update contract storage. Each field's state contains key and defaultValue, both expression-capable values. The key resolves to an expression identifier and the default resolves to a string. Selected fields, including fields reached through Includes, collect their defaults before ordinary view and action resolution. Duplicate state keys fail, even when their defaults agree. Default collection starts with empty state because those defaults initialize the state: defaults and the Includes selecting fields cannot depend on editable $state. An Include selecting Buttons without fields can consume state after defaults exist.

The screen runtime separates initialization from rendering current state. Initial resolution discards any supplied state, collects defaults, then resolves the view. Current resolution uses the supplied state without merging defaults, pruning old keys, or initializing fields that appear after an Include changes. The host owns edits and persistence. This repository's viewer starts fresh state on ordinary route navigation; its Back action can restore compatible saved drafts after rereading the prior route. Those choices do not add persistence rules to UI 1.0.0.

Typed numeric fields distinguish editable text from usable values. Empty, incomplete, invalid input, or text still being composed through an input method, has a canonical value of null; a valid zero has the string "0". An agent preparing a call must respect that distinction instead of converting unset input into zero.

Runtime policy: numeric editing accepts at most 2,048 UTF-16 code units of text and 1,024 canonical significant digits. Integer field bounds resolve to nonnegative decimal strings with empty editable state; min and max are inclusive and cannot depend on $state. These editing limits do not replace the ABI's integer range or the contract's business limits.

Integer and base-unit amount editors accept ASCII decimal digits only. Display-unit amount editing also permits one decimal point: .5 and 1. can represent valid values; a lone point is incomplete. Signs, whitespace, grouping separators, hexadecimal forms, and exponents are invalid. Leading zeros are allowed in editing and removed from the canonical value. Amount precision beyond the declared scale is accepted only when the excess digits are zero.

Numeric defaults are base-unit digit strings or empty strings. Invalid or out-of-bounds defaults reject view initialization rather than becoming an editable null value. If both integer bounds are supplied, min cannot exceed max; there is no implicit uint256 maximum in the editor.

AmountField.props.unit has exactly assetId, baseLabel, displayLabel (nonempty literal strings), and decimals (an integer from 0 to 255). For example, a scale of 2 converts display text "1.25" to canonical "125". Conversion uses exact decimal scaling; nonzero excess precision fails instead of rounding. A unit declaration does not verify the asset or authorize spending it.

DocumentHashField can calculate SHA-256 of selected document bytes or bytes obtained from optional sourceURI, producing a 0x plus 64-hex-digit digest. Its editable/default string is not itself guaranteed to be a valid digest; the receiving ABI or contract owns acceptance of the supplied value. This document digest is distinct from ABI/UI resource integrity. File selection and fetching behavior belong to the host.

Composition and availability

An Include's call.function resolves to a node name or an ordered array of distinct node names; an empty array includes nothing. Every selected node must exist and receive its exact required argument set. Include cycles fail. Included nodes share the runtime and state; the Include is replaced by its resolved children in selection order. A Button's call.function resolves to one route name, and call.args supplies that route's inputs.

"enabledWhen": {
  "member": "edit",
  "in": "$view.availableActions"
}

enabledWhen is allowed only on Buttons and fields. It has exactly a nonempty literal member and in, either an expression resolving to an array of nonempty strings or a literal array of them. Membership uses exact case-sensitive equality. Absence of the member disables the control while retaining it in the view. Disabled controls still resolve props, arguments, and defaults, so an unresolved value remains an error. Membership is presentation availability, not permission proof.

Literal membership strings cannot be single-dollar references and do not apply dollar escaping: a literal "$$edit" compares as those two dollar signs. Route and UI node names and invocation argument keys are nonempty strings; they do not share the identifier restriction on route inputs and state keys.

UI 1.0.0 defines route buttons and node composition. Back, history, focus placement, storage, wallet controls, and confirmation dialogs are host features, without corresponding UI document fields.

Execute a route and handle its outcome

For a read, the off-chain runtime supplies the current host, optional account, route inputs, and initially empty outputs. It resolves the call and validates it against the bound ABI, then asks an RPC node to execute the EVM read against chain state without committing transaction effects. The runtime normalizes the returned results and resolves the UI continuation off chain. A failed call or invalid result cannot supply an ordinary successful view.

For a write, the viewer prepares both the contract call and route continuation off chain with empty outputs. A host may first ask an RPC node to simulate the call; simulation executes against the node's state without committing transaction effects and cannot guarantee later success. The wallet authorizes and submits a transaction; submission returns a hash. An included transaction executes the contract on chain and can apply state changes if it succeeds. A reverted transaction does not apply the attempted contract changes.

The transaction hash identifies a submission, not a successful confirmed operation. Receipt observation happens off chain: this repository's web host waits for a successful receipt, then invokes the prepared read continuation through RPC and refreshes the off-chain view.

Confirmation count, timeouts, replacement transactions, reorg recovery, and stale-interaction handling are host policy. CAM does not specify those policies or require the repository's session architecture. If confirmation succeeds but the following read fails, report both facts: the write has succeeded and the view refresh has failed. A timeout or uncertain submission is not proof of failure; check the wallet or chain before retrying a consequential write.

Authoring advice: have writes continue to a read that obtains the needed live state. Do not fabricate write outputs from events or simulated return values. Account availability, RPC connectivity, wallet approval, and contract state can change after a document passes conformance checks.

Follow a neutral worked example

Consider a hypothetical registry contract with labelOf(uint256 itemId) view returns (string) and setLabel(uint256 itemId, string label) nonpayable. Assume a host binds Registry and publishes the following resources. The contract decides who may edit a label.

The manifest, ABI, and UI below are off-chain files. The host stores the manifest URI/hash and the Registry address binding on chain; ABI/UI URIs and digests appear in the external manifest. The next read receives the item ID explicitly because write outputs are empty. The UI receives the previous read's label through view, then keeps the user's edit in local state. This separates live contract results from an unsubmitted draft.

{
  "cam": "1.1.0",
  "entry": "show",
  "namespaces": {
    "contracts.Registry": {
      "type": "contract", "abiURI": "./abi/Registry.json",
      "integrity": "sha256:0xe11b67b27adf4e4ff5a34bb0b2c91afcc61cfae6a90aa33223e3d954063dc8e3"
    },
    "routes": { "type": "routes" },
    "ui": {
      "type": "ui", "uri": "./ui/main.json",
      "integrity": "sha256:0x78d72558471330294d9bccf3d53a7f3f1e66a83fde3fa4c7665e43374f7c2da1"
    }
  },
  "routes": {
    "show": {
      "kind": "read", "inputs": ["itemId"],
      "call": {
        "namespace": "contracts.Registry", "function": "labelOf",
        "args": { "itemId": "$inputs.itemId" }
      },
      "then": {
        "namespace": "ui", "function": "Editor",
        "args": { "view": { "itemId": "$inputs.itemId", "label": "$outputs.0" } }
      }
    },
    "save": {
      "kind": "write", "inputs": ["itemId", "label"],
      "call": {
        "namespace": "contracts.Registry", "function": "setLabel",
        "args": { "itemId": "$inputs.itemId", "label": "$inputs.label" }
      },
      "then": {
        "namespace": "routes", "function": "show",
        "args": { "itemId": "$inputs.itemId" }
      }
    }
  }
}

The digests match the exact UTF-8 text inside the UI and ABI code blocks below, with no added trailing newline. If you save the snippets with changed whitespace, recompute their digests. The manifest has a read entry with an input: a caller must supply itemId, for example {"itemId":"7"}. Hosts that start entry with no inputs need a separate input-free entry design.

{
  "ui": "1.0.0",
  "nodes": {
    "Editor": {
      "requires": ["view"], "element": "Screen",
      "props": { "title": "Edit label" },
      "children": [
        {
          "element": "TextField", "props": { "label": "Label" },
          "state": { "key": "labelDraft", "defaultValue": "$view.label" }
        },
        {
          "element": "Button", "props": { "label": "Save" },
          "call": {
            "namespace": "routes", "function": "save",
            "args": { "itemId": "$view.itemId", "label": "$state.labelDraft" }
          }
        }
      ]
    }
  }
}

Calling show with item ID "7" asks the RPC node to read its label; the off-chain runtime supplies {itemId, label} as view. The field initializes labelDraft from that label. Editing changes only the local draft. Save prepares setLabel with the draft and no native value, then the wallet can authorize and submit it. Successful included execution applies the contract's label update. After observing a successful receipt, the web host calls show again and renders the new result off chain. A reverted write does not apply the attempted label update; a successful update followed by a failed read leaves the contract updated without producing a refreshed view.

Sources, checks, and open limits

This draft derives from the implementation at 6a3c3c4. The links below pin that source baseline rather than following a moving branch. Repository tests are evidence for this implementation's behavior; they are not an independent interoperability certification.

  • ICamApp contract interface and CamRoot binding extension.
  • Wire versions, CAM parser, and core route and parser tests.
  • URI, integrity, and resource bounds, expression grammar and resolution, and protocol tests.
  • EVM host loading, read/result conversion, write submission, and EVM tests.
  • UI parser, UI resolution and state, and UI tests.
  • Viewer write preparation and web host lifecycle.

The existing offline validation commands are make tests/checks, make js/tests, and make cam/conformance/check, after materializing locked dependencies through the repository's separate dependency lanes. Conformance examines supplied document/resource joins. It does not contact live contracts to prove account authority or transaction success.

Open limits: this reference does not define independent discovery catalogs, non-EVM adapters, wallet permissions, a transaction finality standard, an atomic snapshot protocol, deployed code identity, or a complete renderer appearance contract. The worked example has not been exercised against an independently implemented consumer. A consumer should select and document its resource transport and transaction policies before operating a live workflow.
