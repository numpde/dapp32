Manual approval of deployment transactions
2026-10-20

Status: design proposal, not implemented. Scope: Escrow, Bike NFT and
Pay-to-Play releases. Deposit Gateway is excluded.

The operator already uses a dedicated deployment account. The proposed change
is a separate container that reviews each signed transaction before submitting
it to the configured RPC provider. The operator approves the actual request
that arrives, with useful decoded information and comparisons to saved release
files. No standing permission to deploy arbitrary contracts is implied.

Decision
--------
Use one foreground operator terminal owned by the approval proxy. Forge keeps
the deployment key and runs separately, with its output saved to a separate
log. The proxy has no deployment key, repository mount, compiler, Docker socket,
or executable application extensions.

    Forge, with deployment key -> approval proxy -> configured RPC provider
                                       ^
                              operator terminal

Approval belongs to the exact signed transaction bytes retained by the proxy.
The proxy decodes those bytes, displays the review, and makes at most one
upstream submission attempt with those same bytes. It never rebuilds a
transaction from the display.

This replaces the signing lane's unconditional send forwarding. Read-only
artifact and verification proxies retain their existing purpose. Current
forwarding and phase separation are documented in [R1].

Before implementing the full feature, qualify the pinned Forge client's
behavior while a submission waits for human input. That experiment is a
blocking design check, not a final polish item; see "First implementation
slice". The current source contains retries and separate receipt/RPC timeout
paths [F1-F3].

What the boundary guarantees
---------------------------
No eth_sendRawTransaction request is forwarded through this proxy without a
current operator approval of its exact signed bytes. Wrong chain/account,
invalid encoding/signature, and unsupported transaction forms are rejected
before a prompt. The ordinary RPC listener has no approval operation.

This is approval of broadcast through one path. Forge still has the key and can
produce other signatures. Signed transactions can be broadcast by anyone who
obtains them; rejection here does not revoke them. Writable Forge outputs and
permitted read-RPC parameters are possible disclosure channels. Method
filtering is not a general defense against a hostile process exfiltrating its
key or signed bytes.

The host, Docker administrator, reviewed proxy image, decoder dependencies,
operator terminal and selected reference inputs remain trusted. A separate
container cannot make a proxy trustworthy if the same unreviewed release can
silently replace its executable. Select the proxy image by an admitted immutable
identity, independently of the application candidate; do not build it from
that candidate as part of a live approval run.

The useful boundary is therefore: an application process cannot authorize its
own RPC submission, change the displayed request, or alter the proxy's selected
reference snapshot. It is not a claim of key isolation or hostile-code
containment.

What the operator sees
----------------------
Show a compact summary first, then expandable full details. Never abbreviate an
address as its only available representation.

Example, for a call against an already recorded deployment:

    Review transaction 4
    Chain:                 84532, matching selected chain
    Sender:                <full recovered address>, matching selected account
    Target:                <full address>
    Address comparison:    matches CAM root in selected deployment artifact
    Function:              transferOwnership(address newOwner)
    newOwner:              <full address>
    Argument comparison:   matches intendedCamRootOwner in selected release plan
    Native value:          0 wei (0 ETH, using selected network metadata)
    Nonce:                 <exact integer>
    Gas limit:             <exact integer>
    Maximum fee per gas:   <exact wei and readable equivalent>
    Priority fee cap:      <exact wei and readable equivalent>
    Execution fee ceiling: gas limit multiplied by maximum fee per gas
    Other chain fees:      <separate estimate, or explicitly not established>
    Reference:             <selected file name and content digest>
    Transaction hash:      <full locally computed hash>

    Approve with: approve <current challenge>
    Reject / Inspect full data

The example illustrates the layout, not an existing command or transaction.
Approval challenges are generated by the proxy and bound to the ceremony and
full hash. Buffered input for an earlier request must not approve the next one.
Blank input never approves. Avoid a bare "yes" or "approve next".

Present three kinds of information distinctly:

* Signed facts: recovered sender, chain ID, nonce, destination, value, fee
  fields, transaction type, access list, calldata length/hash and full hash.
* Reference comparisons: ABI interpretation, artifact address roles, expected
  constructor/call arguments, bytecode comparisons and selected file digests.
* Chain observations: current code, nonce or receipt, with the provider and
  observation block identified. An RPC observation is not independent proof.

An ABI says how to interpret bytes, not what executing them will do. Do not
infer business meaning from a function name. Any explanation such as "starts a
pending ownership transfer" needs a reviewed source for that exact contract.
Arbitrary descriptions from application output must not appear as proxy-owned
claims. The first implementation can omit prose descriptions entirely.

Escape terminal control characters and bidi controls in labels, URIs and
decoded strings. Bound nesting, element counts and displayed lengths. Show
when content is abbreviated and make full data inspectable; never hide
security-relevant fields behind a summary. Deployment stdout must not be
interleaved with the approval terminal.

Native value and execution fees are different. For supported type-2
transactions, gas limit times maxFeePerGas bounds execution fees; it does not
establish a total charge on chains with additional fee components [E1].
Use exact integer arithmetic. Human-readable units supplement the signed
integers rather than replace them.

Reference inputs and initial deployment
--------------------------------------
The proxy receives a bounded, read-only snapshot of explicitly selected
reference data. Record its digest before processing requests and include that
identity in the approval record. Do not read changing files on every prompt or
fetch arbitrary ABI/explorer/CAM URLs supplied by a transaction.

Existing deployment:
  Compare target and argument addresses with the saved deployment artifact and
  intended authorities in the release plan. Show actual and expected values,
  their named roles and the originating file field. Matching an address proves
  consistency with that file, not ownership or runtime behavior. A code-hash
  observation is a separate comparison; a file checksum is not a contract code
  hash.

Fresh deployment:
  The completed deployment artifact does not exist yet [R2-R4]. Use the selected
  release plan and compiler outputs produced before key-bearing execution:
  ABI, fully linked creation bytecode, constructor argument expectations, and
  source/compiler identity. These are supplied data, not executable plugins.
  A digest identifies them; it does not independently establish their honesty.
  Include every contract used in the ceremony. CAM-exported ABIs alone are
  insufficient: Bike NFT's CAM ABI set omits CamRoot and BicycleComponents,
  although its deployment creates and calls both [R3].

  Match the creation-bytecode prefix exactly, decode the complete constructor
  suffix and verify its exact re-encoding. Do not strip compiler metadata or
  wildcard arbitrary bytes. Report ambiguous matches. A library's constructor
  decoder is not itself proof that the supplied bytecode prefix matched [V1].

  For direct CREATE, display the address derived from recovered sender and
  signed nonce as "predicted", then promote it to "observed" only after checking
  the matching successful creation receipt. Later binding calls can compare
  against those earlier observed creations. Before approving a transaction
  whose target or constructor/call argument depends on an earlier creation in
  this ceremony, require its matching successful receipt. Failed, missing or
  mismatching receipts stop that dependent approval; a prediction alone is
  insufficient.

  Factory calls and CREATE2 require their own interpretation; do not apply the
  direct-CREATE formula to them. The first supported release paths must be
  qualified against their actual transactions.

Reuse existing app-owned plan/artifact parsers outside the proxy when producing
the comparison snapshot. Keep traceability to the original file digest and
field. The proxy consumes a small data-only description of expected addresses,
arguments, ABIs and compiler outputs; it must not import all CAM/viewer code or
reconstruct each application's business rules.

The reference exporter is part of the trusted preparation path, independent of
the key-bearing application process. Its source-field mapping is not merely a
claim that the proxy can assume true. Qualification must compare the exported
values with the selected original files; keep those originals in the frozen
snapshot for operator inspection. The exact export format and Make wiring are
implementation work after the client feasibility check, not an existing API.

Address matching must preserve roles. An address found somewhere in an artifact
is not automatically the intended recipient for this operation. Show all
matching roles, and compare an argument to an expected role only when that
relationship is explicitly supplied. Unknown and mismatching values remain
visible. For this release lane, unknown interpretation, ambiguous matches,
reference mismatches and incomplete required inputs block approval. Correct or
explicitly replace the selected references outside the active ceremony and
review again; do not add an in-prompt raw-bytes bypass.

Decoding and supported requests
------------------------------
Start with ordinary signed EIP-1559 type-2 transactions, subject to confirming
that all three release scripts emit them. Validate the complete envelope,
signature, chain and recovered sender. Render every supported signed field.
Reject other types explicitly, including blob transactions and EIP-7702
authorization lists; those need additional review semantics [E1, E2].

Use the existing locked transaction/ABI implementation rather than inventing
RLP, Keccak or signature recovery. Viem 2.50.4 supplies relevant operations
[V1], but successful parsing alone is insufficient admission proof. Reject
ambiguous ABI selector matches and require exact supported calldata decoding
and re-encoding so hidden trailing bytes are not ignored.

The first write interface accepts one eth_sendRawTransaction with a JSON-RPC
request ID and exactly one signed transaction parameter. Reject notifications
and any batch containing a write before forwarding any part of it. Keep only
the read methods required by the release and explicit reconciliation.

Use bounded concurrent HTTP handling with one pending approval. Do not add
input() to the current single-threaded handler: that would stop health and read
requests [R1]. Duplicate requests for the same bytes share the same decision
within a bounded waiter limit. A different simultaneous transaction is rejected
as busy, with no hidden approval queue.

A disconnected duplicate removes only that waiter. If the last waiter leaves
before transmission begins, cancel the pending approval and close submissions.
One waiter's disconnect cannot cancel a request still owned by another live
waiter. The shared approval deadline does not restart when a duplicate arrives.

Who waits, and what completes each wait
--------------------------------------
There are three waits with different owners and deadlines:

1. Approval: Forge has sent eth_sendRawTransaction to the proxy and is awaiting
   its HTTP/JSON-RPC response. The proxy retains the validated signed bytes and
   awaits the operator. Nothing has been forwarded upstream. Approval permits
   the next phase; rejection, expiry or cancellation ends this request without
   submission. Read and health requests must remain responsive meanwhile.
2. Upstream submission: after durable approval, the proxy sends the retained
   bytes to its configured provider and awaits that request's response. A
   matching returned hash establishes endpoint acceptance only. The hash was
   already computable locally; knowing it does not prove submission. A timeout
   after sending might have begun means the outcome is uncertain.
3. Receipt: after the send result, Forge queries transaction status and waits
   for a receipt. eth_getTransactionReceipt(hash) returns a receipt or null;
   each read request completes independently rather than remaining open until
   mining. Forge's --slow path waits for the pending receipt before its next
   send [F1, F5, E3]. Receipt-wait expiry is not permission to submit again.

A receipt includes execution status: inclusion can mean success or revert.
It is not a promise of finality. The proxy must independently check matching
successful creation receipts when a later approval depends on those creations;
the signed request alone cannot establish that those creations succeeded.

These waits must not share one ambiguous timeout. The approval and submission
waits occur inside Forge's outstanding send RPC; their combined budget plus
reply margin must fit its effective send timeout. Receipt waiting happens
afterwards, under its own deadline. Its repeated reads are still subject to
per-request transport limits. Exact polling and retry behavior belong to the
pinned client and must be observed, not assumed from the word "await".

Approval, broadcast and failure
------------------------------
1. Receive and validate immutable signed bytes. Compute the hash locally.
2. Display the review with reference identity and a fresh challenge. Set an
   explicit approval deadline; read/health requests remain responsive.
3. On rejection, expiry, operator EOF/detach or cancellation, close submissions
   for this ceremony. Subsequent Forge retries cannot reopen the prompt. Earlier
   approved transactions may already have executed.
4. On approval, durably record the hash, chain, sender, nonce, reference digest,
   decision and permission to begin transmission. A failed write/sync prevents
   submission. Only then make one upstream send attempt using retained bytes.
5. A matching RPC result hash means accepted by that endpoint, not mined or
   successful execution. Persist and sync the observed outcome before accepting
   another transaction. Cache the result value for identical retries without
   sending again, wrapping it in each caller's own JSON-RPC response ID. A
   different hash, JSON-RPC error, malformed response, non-success HTTP status,
   uncertain transport result or post-send persistence failure stops further
   submissions and preserves the locally computed hash. Cache that outcome;
   Forge retries never cause another send. "Already known" and "nonce too low"
   do not prove that the transaction was never submitted.
6. Receipt and deployment verification remain distinct checks. A transaction
   can be approved and accepted yet revert onchain.

Closing submissions leaves bounded read/reconciliation requests available
until deliberate teardown. It never silently reopens writes.

Use a small proxy-owned audit in the existing private release output, mounted
writable only into the proxy. Keep hashes and safe facts, not raw signed
transactions or signatures, in ordinary logs. Forge must not be able to rewrite
this evidence. The existing refund worker provides a relevant pre-send durable
hash precedent [R5]; it is not a reason to import its customer discovery or
worker state machine.

A crash after the durable pre-send entry leaves "may have been sent", even if
the process actually died before network transmission. No automatic restart,
resume, replacement or retransmission is part of this design. A new process
must not silently reuse an output with an unresolved attempt. Reconcile by hash;
absence from one provider's lookup does not prove non-submission. A replacement
has different bytes and always requires a new review.

Recovery remains an explicit operator step: inspect the retained hashes,
receipts and current account/contract state, then decide whether a separately
reviewed continuation is appropriate. There is no "resume" command specified
here. A receipt showing failure still consumes the nonce and may consume fees;
it must not be treated as an unattempted transaction.

One state owner serializes challenge consumption, expiry, EOF, cancellation and
the transition into transmission. After the durable write, atomically check
that the challenge is approved, the ceremony is open and the deadline has not
expired before marking transmission begun. A cancellation that wins before
that transition prevents sending; one that arrives afterwards cannot revoke
it. The durable pre-send record remains conservative evidence of possible
submission if a crash interrupts this transition. Never let independent timer
and HTTP callbacks each make their own send decision.

Approval expiry only stops a request that has not entered transmission.
Disconnecting after approval cannot retract a request already sent. If the last
live waiter disappears before transmission, cancel when detected; a late/undetected
disconnect cannot erase the operator's already recorded decision.

Approval wait, upstream transport and receipt wait are separate deadlines.
The upstream operation needs a total deadline as well as byte and inactivity
limits. Do not send a fabricated transaction hash early to keep Forge happy.
Require the approval deadline plus total upstream deadline plus a response
margin to fit within the measured effective Forge send timeout.

Container and operator integration
----------------------------------
The host launcher selects the proxy image, exact container identity, reference
snapshot, expected chain/account and protected RPC URL. Attach the operator's
TTY only to that proxy. Start Forge separately with logs captured. No approval
API, shared approval file or control credential is exposed to Forge.

Prefer a foreground proxy with a terminal decision loop and bounded HTTP
workers. A separate Unix-socket approval CLI is unnecessary unless the actual
Make/Compose lifecycle proves this interface cannot work reliably.

The proxy gets only its approved references, RPC credential, private audit
output, bounded tmpfs and necessary internal/egress networks. Use a non-root
identity, read-only root, no capabilities/privilege escalation, no host ports,
bounded CPU/memory/swap/PIDs and disabled core dumps. Package reviewed code and
locked runtime dependencies in the image; no runtime repository or broad
node_modules bind. Dependency acquisition stays a separate networked build
step. Source/build context must exclude application files and secrets.

Preserve bounded HTTPS forwarding, credential-safe diagnostics, target
validation and method admission. There should be one owner for outbound RPC
policy. Decide through the feasibility slice whether the typed gate replaces
the signing proxy or uses the existing transport as an exclusive backend;
do not accidentally give Forge both a gated and ungated submission route.

Test effective network behavior, including host services, other containers,
public IPv4/IPv6 and DNS. An internal Docker network alone is not proof of every
claimed egress restriction [D1]. Retain the narrower one-path guarantee above.

First implementation slice: approval-wait qualification test
-----------------------------------------------------------
This is a test specification; neither its fixture nor the approval proxy is
implemented. The acceptance requirement is that a 120-second simulated review
can complete without a send retry or premature submission. Shorter cases help
locate a client limitation. A failed client acceptance assertion is a
compatibility failure, not a green characterization of current behavior.
Infrastructure failures remain separately classified as inconclusive.

Given:
  Use the pinned Foundry image and the maintained deploy-release service's
  actual --broadcast --slow command, with Escrow as the first representative
  app. Use the existing disposable rehearsal infrastructure, a public fixture
  key, fresh chain and release output per case. No real RPC, funds or keys.
  Record the image digest, source commit, complete safe command/configuration
  and independent approval, upstream, receipt and outer-run deadlines.

When, separately for D = 10, 50 and 120 seconds:
  Intercept only the first logical eth_sendRawTransaction and hold it BEFORE
  any upstream send. Start a monotonic timer at its first admitted arrival;
  duplicates share that original timer. At D, simulate operator approval and
  forward the exact retained signed bytes. Later release transactions pass
  normally so the experiment does not multiply the human delay per contract.
  This is a fixture-only delay, not an implementation of operator approval.

Then, for each case:
  * Upstream submission count for the held transaction stays zero throughout
    the delay. Its first actual send occurs no earlier than D after arrival.
  * During the hold, independently initiated health and eth_blockNumber
    requests complete within a declared local-fixture deadline (five seconds).
    A single-threaded sleeping proxy cannot establish this property.
  * Forge makes exactly one submission attempt for those signed bytes. The
    proxy sends them upstream exactly once after release. Any retry fails
    approval-wait qualification even if the release eventually completes. Any
    additional eth_sendRawTransaction while the first response is held also
    fails, including a replacement with changed signed bytes; it is never
    passed through as an unrelated transaction.
  * Forge receives the provider's actual matching hash, observes a successful
    receipt and completes the release command. No fabricated early result,
    extended deadline on retry or automatic resend may make the case pass.

Preserve observations even when a case fails and run all three durations.
Record every incoming request ID and monotonic arrival time, signed-byte
fingerprint, first upstream-send time/count, response-write outcome, actual
Ethereum transaction hash, receipt and Forge exit/result. A SHA-256 fingerprint
can compare signed bytes without logging them, but is not the Ethereum hash.
A successful socket write does not prove Forge received the response; the
client's result and subsequent reads provide the relevant evidence.

Bound each case independently, including live connections, retained duplicate
requests and evidence size. For example, a 300-second limit from first send
arrival bounds a hung measurement; compilation/setup have separate bounds.
Label a harness timeout or resource cap as inconclusive infrastructure failure,
not a measured Forge timeout. Do not infer its effective timeout from D alone.

Receipt-wait control case:
  In a fresh run, delay no submission. Disable Anvil automining using the
  fixture controller's direct node connection, then forward the first signed
  transaction and return its actual hash promptly. Observe a null receipt while
  it remains unmined, and verify Forge issues no later send. Ten seconds after
  the first observed null receipt, mine it and restore automining for the rest
  of the release. Verify the matching successful receipt, subsequent release
  progress and no second submission of those signed bytes. Keep mining
  control out of the release-facing RPC allowlist. This isolates receipt
  waiting from the approval and submission waits.

Failure controls:
  Return HTTP 200 with JSON-RPC 2.0 error code -32000, message "Fixture approval
  denied", and the current request ID. Keep rejecting all sends for that case
  without forwarding them. Measure Forge's retries and exit; a retry is never
  a new approval. This fixed fixture response is not a proposed production API.

  In a separate run, forward the first transaction, receive and record the
  provider's matching accepted hash, then close Forge's connection without an
  HTTP response. Retain the known hash and observe its chain outcome; never
  call it "not sent". Capture all later send attempts but prevent another
  upstream send in this control. These experiments establish client behavior;
  only the later approval-gate implementation can prove its own denial and
  deduplication policy.

Source inspection shows that --slow serializes sends but does not eliminate
retry. --timeout configures receipt waiting; the broadcaster constructs its
provider separately from the configuration-aware constructor [F1-F3].
The actual pinned binary's effective send timeout remains untested.

Run the matrix first unchanged. Repeat only with a concrete candidate setting
that is demonstrated to affect the send provider; --timeout alone is not such
evidence. If no tested delay exceeds the observed client timeout, report that
coverage gap rather than claiming the 120-second case necessarily crossed it.

Proceed only if a useful human review interval works without fabricated
success or depending on retry to prolong the approval. Otherwise resolve the
client integration first, with a separately reviewed change. Do not silently
add a durable job queue, custom polling protocol or fork of Foundry.

Later approval-gate acceptance tests, before production changes:

* No upstream send before approval, or after denial, deadline, EOF, unsupported
  input, failed evidence persistence or stale challenge.
* Approved and forwarded bytes are identical. Changing any signed field needs
  a new approval; different request IDs cannot bypass duplicate handling and
  each response carries its own caller's ID.
* Approval cannot be supplied over RPC, through Forge stdin/stdout, by changed
  reference files, or by a queued response from a previous prompt.
* Wrong sender/chain, malformed signatures, unsupported types, mixed batches,
  ambiguous ABI selectors, trailing data, mismatching creation code and
  constructor arguments have explicit outcomes.
* Full address/role comparisons, mismatches, large exact quantities, hostile
  terminal strings and missing fee evidence are visible and accurate.
* Reads/health work during human delay; concurrent connections and pending
  memory remain bounded. Losing one duplicate waiter preserves the others;
  losing the last before send-start cancels approval. Duplicates never extend
  the shared deadline.
* Upstream acceptance followed by a lost reply, mismatching returned hash and
  crashes at each pre/post-send boundary preserve uncertainty and never cause
  an automatic second send. Include RPC/HTTP errors, malformed responses and
  expiry or cancellation while the durable pre-send write is slow.
* Each of the three real release scripts completes on a disposable chain with
  simulated operator interaction, exact approved-hash/chain comparison, normal
  artifact verification and owned-resource cleanup. Include rejection midway
  through a release and retained evidence of earlier successful transactions.

The normal operator command may remain one Make target, but it becomes
interactive and requires a TTY. Do not leave an unattended live-deployment
bypass hidden behind a flag. Automated rehearsal uses a separate fixture-only
operator driver that cannot be selected with real RPC/key inputs.

Workshop record
---------------
Initial independent reviews covered (1) authority and container boundary and
(2) client timing, retries and uncertain effects. They identified the missing
initial-deployment reference, unsafe blocking of the single-threaded proxy,
Forge retries and timeout assumptions, and the need for pre-send hash evidence.
The draft adopts those corrections and chooses a foreground TTY instead of
adding a control socket and CLI without demonstrated need.

The display reviewer additionally identified that CAM-exported ABIs do not
cover every deployment contract. The note now requires compiler-output ABI
coverage for the entire ceremony.

The second independent review round corrected four lifecycle omissions:
durable post-send outcomes, response-ID handling on duplicates, the required
approval/upstream/client timeout relationship, and serialized cancellation
versus send-start. It also clarified that every non-matching-success upstream
outcome stops submissions, and replaced an exactly-once-sounding promise with
at-most-one submission attempt.

The design deliberately rejects a separate approval CLI/socket, approval
database, automatic retry/recovery engine and per-application business-rule
interpreter until a concrete integration requirement justifies one.

A fresh context-isolated operator teach-back understood the intended boundary,
reference limits, fresh-deployment distinction and uncertain-send behavior.
It exposed duplicate-waiter cancellation and creation-dependency ambiguity.
The note now cancels only when the last waiter disappears before send-start,
requires successful receipts for dependent approvals, and explicitly leaves
read-only reconciliation available after submissions close. Export format,
transport composition and a future continuation command remain identified
implementation decisions, not hidden claims of existing functionality.
The fresh reader repeated the teach-back after these revisions and found the
rules coherent. A separate fresh source-aware auditor found no further
material design issue after those corrections. These reviews establish clarity
and source consistency; they do not replace the required Foundry runtime probe.

The subsequent wait/test formulation received two independent peer reviews.
It now holds before submission, fails compatibility on extra sends, defines
the rejection/lost-response controls, and restores automining after the
receipt-delay control. The three waits and their owners are explicit. This
follow-up changes the specification only; no fixture was implemented or run.
