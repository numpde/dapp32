Shared CAM UI backlog
=====================

1. Shared URI input and display components

   Requested: 2026-10-29. Status: queued.
   Owner: shared CAM UI authoring/rendering, with adoption across Bike,
   Escrow, Pay-to-Play and other apps wherever a value is a document location.

   Preserve the exact input, provide syntax feedback and explicit open/load
   actions, and reuse existing resource validators and download permissions.
   Supported schemes must match the consumer: HTTPS, IPFS and embedded data
   URIs are not interchangeable everywhere. Do not fetch automatically or
   imply that valid syntax proves reachability, safety or matching content.

   Coordinate URI input with recorded URI/digest presentation: opening a
   document and verifying its bytes are separate actions. This capability
   belongs to shared UI, not an app-specific plugin.

   Fields accepting prose as well as links, such as Bike missing reports,
   resolutions and public profiles, remain text fields.

   Related evidence: note 031, issue 28 (Escrow recorded documents).

2. Compact shared document-hash editor

   Status: complete. Commit: f8226888.
   Owner: shared viewer DocumentHashFieldView.
   Remove the repeated visible digest caption and idle space reserved for
   hidden cancellation/status content. Keep the contextual accessible input
   name, explicit calculation controls, cancellation and error feedback.
   Real feedback may add height; it must not move the input above it.
   Related evidence: note 031, issues 2 and 4.
   Verification: focused viewer browser checks at 1280/761/320. Shared display
   checks now reject invisible normal-flow reservations in native fieldset
   editors, with an injected spacer rejection and accessible-description,
   collapsed-content and overlay positives. This is a rendered-state check,
   not a semantic classifier for all empty space or arbitrary app markup.

6. Open question: share prepared forms through links and QR codes

   Status: open design question; implementation not selected.
   Owner: shared viewer form sharing/navigation, with app-specific use cases.
   Example: prepare Bike registration with serial number, intended NFT owner
   and metadata, then give someone a QR/link that opens the populated form.
   Existing links restore a route and its inputs, but not the editable draft.

   Decide which draft values are shareable, how recipients inspect/edit them,
   and how URL/QR size limits affect embedded metadata. Also decide how a
   shared draft behaves if the app's fields or contract bindings have changed.
   Sharing must not carry wallet credentials or transaction approval, select
   a signing wallet, or automatically submit a transaction. Form values in a
   shared link are disclosed to anyone who receives it.

   The historical PoC QR renderer is a reference, not a migration decision.
   A QR represents the same prepared-form link; URL/draft construction belongs
   to its existing shared owner rather than the QR display component.
