Recording an Escrow multi-party walkthrough
=========================================

Use the running disposable Escrow fixture and the existing Chromium viewer
page exposed through CDP at http://127.0.0.1:9222. Do not open another browser
window or CDP target, restart the fixture, or replay old transaction footage.
The walkthrough creates a new agreement on the current local chain.

Before recording
----------------

Record the source commit, UTC start time, CDP target ID, full viewer URL,
viewport, RPC endpoint, chain ID, CamRoot and Escrow addresses, CAM URI, and
keccak256 of the served manifest bytes. Verify the actual RPC chain is 31337,
that the configured viewer selects that chain, and that CamRoot's URI/hash and
contract bindings match the served CAM bundle. Mount the current checked-in
manifest read-only, calculate its keccak256, and compare the source, served
bytes and contract hash before proceeding. Check ABI/UI integrity too.
Stop before signing if these checks fail.

Use an explicit fixture provider for the existing page. Load only the public
repeated-pattern client, contractor and arbitrator keys from
compose/escrow/local/deploy.yml. Limit submission to five transactions against
the verified Escrow contract: createAgreement, acceptAgreement,
submitAgreement, approveAgreement, withdrawTo. Recheck the chain before each
submission. Account changes must pass through the provider's accountsChanged
notification and the app's normal wallet handling. Use a fresh agreement
reference and retain the agreement ID returned by the real creation receipt.

Prepare two real UTF-8 files: agreed terms and the contractor's submitted work.
Save their exact bytes alongside the movie and record their SHA-256 hashes.
The temporary harness can fulfill two explicitly named same-origin document
URLs through CDP Fetch, serving those exact bytes. Mark these as local recording
fixtures in the accompanying evidence: these URLs exist only while that CDP
interception is active, not on a durable document host. Enter each URI through
the actual form and use Calculate from URL; compare the digest with the file hash.
Do not mock app state or transaction receipts.

Capture and encode
------------------

Use an ephemeral Node harness through the existing secured
compose/escrow/local/browser-check.yml service
escrow-viewer-browser-write-check. Keep its pinned image, non-root user,
read-only source/dependency mounts, dropped capabilities, resource bounds, and
host networking for the existing loopback RPC/CDP endpoints. Use a command
override with --no-deps, --pull never and --rm; do not add a permanent service,
lane, dependency or recording helper to the application.

Mount the temporary harness read-only and copy it into the service's staged
/work/js workspace so it can use the existing fixture/CDP utilities and viem.
Build @cam/protocol with the workspace runner before executing the harness.
Use the same required CDP_ORIGIN, VIEWER_URL, EXPECTED_CAM_URI and
EXPECTED_CAM_HASH inputs as the maintained browser-check lane. Export artifacts
before the run container is removed; do not rely on its disposable /tmp.
Preserve the exact invocation and harness bytes with the recording evidence.

Ephemeral implementation recipe, from the repository root (the /tmp script is
operator-created for this run, not a maintained repository command):

  LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)" \
  WALKTHROUGH_COMMIT="$(git rev-parse HEAD)" \
  CDP_ORIGIN=http://127.0.0.1:9222 \
  VIEWER_URL='<full existing viewer URL>' \
  EXPECTED_CAM_URI='<verified onchain CAM URI>' \
  EXPECTED_CAM_HASH='<verified nonzero onchain CAM hash>' \
  docker compose -f compose/escrow/local/browser-check.yml run \
    --no-deps --pull never --rm \
    --volume /tmp/dapp32-walkthrough-record.mjs:/validation.mjs:ro \
    --volume "$PWD/dapps/escrow/cam/main.json:/fixture/main.json:ro" \
    --volume /tmp/dapp32-walkthrough-output:/recording-output:rw \
    escrow-viewer-browser-write-check \
    run-js-workspace sh -eu -c '
      npm run build -w @cam/protocol
      cp /validation.mjs /work/js/apps/cam-web/test/escrow-walkthrough-record.mjs
      exec node /work/js/apps/cam-web/test/escrow-walkthrough-record.mjs
    '

Before this command, reject symlink/wrong-type staging paths and explicitly
create /tmp/dapp32-walkthrough-output as a directory owned by the operator.
Docker must not create that host path implicitly. Use the already available
lane image; dependency installation remains a separate explicit operation.
Bound total harness execution to 240 seconds; bound capture to 180 seconds
and at most 900 screenshot frames, stopping cleanly at either capture limit.
The host staging directory contains the WebM, evidence.json, and frame JPEGs
before the run container is removed.

Capture the existing viewport with Page.captureScreenshot every 200 ms
(JPEG, quality 80, captureBeyondViewport=false). Encode those frames with an
unattached canvas in that same page: canvas.captureStream(5) and MediaRecorder
using video/webm;codecs=vp9 after checking browser support. Feed screenshots to
the canvas without adding a visible overlay or altering the app layout. Keep
capture and encoding offscreen; helper labels must not appear as app controls.
The movie contains the app viewport only, without OS/browser chrome or audio.
No host ffmpeg installation is required. Stop recording before reloading the
page and retain the completed WebM blob in the current document until export
is verified. Read Blob.slice ranges of at most 512 KiB through bounded CDP
requests and write the returned chunks in order to the staging file. Verify
its byte count and SHA-256 before deleting the retained blob. Avoid sending an
entire multi-megabyte base64 blob in one CDP result.

Drive native browser input through CDP Input keyboard/mouse events. Pause about
1.5 seconds after each visible field edit, role change, prepared transaction,
receipt and resulting view. Preserve elapsed wall-clock time in the frame
sequence; do not compress receipt waits into instant success. Optional VTT
captions and a player page are separate artifacts, labelled with actor/action
and elapsed time, rather than changes to the viewer itself.

Walkthrough sequence
--------------------

1. Client: connect, enter the reference, contractor, arbitrator, amount,
   timeout recipient and four durations; enter the terms URI and calculate its
   digest. Prepare creation, show the simulation and value, then Send with
   wallet. Wait for the successful receipt and funded agreement view.
2. Contractor: switch the provider account, wait for the refreshed view,
   prepare acceptance and send it. Wait for confirmation and accepted state.
3. Contractor: enter the submission URI, calculate the exact-file digest,
   prepare submission and send it. Wait for confirmation and submitted state.
   Arbitrator: briefly switch to the arbitrator and show the submitted view.
   Resolution is unavailable because this success path has no dispute; do not
   send an arbitrator transaction.
4. Client: switch accounts, wait for the refreshed view, prepare approval and
   send it. Wait for confirmation and released state. Show that payment is
   contractor credit requiring a separate withdrawal.
5. Contractor: switch accounts, open account credit, record the credit and
   balance, prepare withdrawal to the contractor address and send it. Wait for
   confirmation. Show zero remaining credit and verify the recipient balance
   increase, accounting for the transaction's gas cost.

Keep a timestamped event log with actor address, visible action, agreement ID,
transaction hash, receipt status/block, and resulting state. Preserve before/
after credit and balance values and withdrawal receipt gasUsed and
effectiveGasPrice. A successful movie has five successful real transaction
receipts and the final credit/balance evidence, not just prepared-call screens.

Artifacts and cleanup
---------------------

Export the WebM to /home/ra/tmp/escrow-multiparty-20261013.webm using an explicit
copy of the completed staging file. Keep the terms/submission files, event and
receipt evidence, optional VTT/player, harness and invocation alongside it.
Validate the exported WebM with an offscreen video element in the same page:
check video dimensions/metadata and decode stills at representative timestamps.
Confirm those frames contain the actual app and visible workflow stages before
reporting a usable movie. Preserve the evidence and remove the validation
elements afterward.
Record the UTC end time and any capture interruption. Resume an existing
agreement after an interruption only from observed current state; never repeat
a send merely because the recorder lost its response.

Persist the exact identifiers returned by addScriptToEvaluateOnNewDocument,
the runtime binding names and the attached session ID before any interaction.
Remove the recorded identifiers; do not guess script IDs. Attempt each cleanup
operation independently, retaining the original failure and any later cleanup
failures so one cannot mask the other.

In finally cleanup, stop the recorder and all media tracks, release screenshot
timers and CDP pending work, disable Fetch interception, remove the injected
provider/new-document script/binding and recorder globals, and detach the CDP
session. After artifacts are safely exported, use an explicit Page.reload to
verify provider/recorder globals are absent in a new document realm. Navigating
to a URL that changes only its fragment may retain the old realm; lingering
globals there do not prove a new-document injection is still registered.
Leave the same existing page and running fixture available. Do not
close the tab, stop the GUI or remove fixture state as part of recording cleanup.
Report any cleanup failure and retained artifact path.
