CAM UI local state revision
===========================

Purpose
-------

Fix the class of bugs where editable UI values are initialized from one
authority but rendered or submitted from another.

The observed browser symptom was an input that could not be typed into. The
general bug was not a React event problem. It was state authority confusion:
the renderer wrote edits into viewer-local form state, then read the visible
input value back from contract/view output on every render.

The durable invariant should be:

  Contract/view outputs initialize local viewer state.
  Viewer state owns live interactive values.
  Actions read live interactive values from viewer state.
  Renderers never read editable live values from contract/view props.

This note records the state-ownership invariant behind the UI schema revision.
The migration has landed with the `element`/`TextField`/`Button` vocabulary.


Non-goals
---------

Do not put React, JSX, functions, event handlers, or arbitrary JavaScript in CAM
resources.

Do not invent a second UI framework. The manifest should describe a small,
portable element tree that maps naturally to React and other renderers.

Do not preserve backwards compatibility with the old `form`/`Input` shape
unless a migration tool is deliberately added later.


Vocabulary
----------

Use React-aligned concepts, but keep protocol and renderer boundaries clear.

`element`
  The portable UI element to instantiate, such as `Screen`, `Fragment`,
  `Text`, `TextField`, `Status`, `Address`, `Nft`, `Button`, or `Include`.
  This replaced the old `tag` field. `component` is intentionally avoided in
  the schema because the flagship dapp uses component as a business-domain
  noun.

`props`
  Resolved render props. These are display/presentation inputs for a known
  element and should be safe for a renderer to spread at the renderer boundary.
  They must not contain live editable values or event behavior.

`state`
  Optional local viewer-state wiring for interactive elements. A node with
  `state` participates in viewer-local state. A node without `state` does not.

`state.key`
  The key under the viewer snapshot's local state object.

`state.defaultValue`
  Initial value for `state.key`, resolved from CAM context, usually from
  contract/view data. It is consumed by the viewer/session when seeding local
  state. It is not the live React value after initialization.

`call`
  Button behavior. A UI node may call the `routes` namespace. Contract calls
  still go through CAM routes, not directly through UI nodes.

`children`
  Composition.

`$state`
  Runtime expression root for viewer-local state. This replaces `$form`.


Target JSON shape
-----------------

A text field should look like:

```json
{
  "element": "TextField",
  "props": {
    "label": "Serial number",
    "placeholder": "Frame serial"
  },
  "state": {
    "key": "serialNumber",
    "defaultValue": "$view.serialNumber"
  }
}
```

A button should read the live value from `$state`:

```json
{
  "element": "Button",
  "props": {
    "label": "Look up component"
  },
  "call": {
    "namespace": "routes",
    "function": "component",
    "args": {
      "serialNumber": "$state.serialNumber"
    }
  }
}
```

An include remains composition only:

```json
{
  "element": "Include",
  "call": {
    "namespace": "ui",
    "function": "$view.viewId",
    "args": {
      "view": "$view"
    }
  }
}
```

`Include` must not own state. If included content needs state, the included
node should contain a stateful child.


Why defaultValue still belongs
------------------------------

React's `defaultValue` is useful: it initializes an uncontrolled input. The CAM
protocol needs the same concept, but at the headless viewer/session boundary,
not only at the DOM boundary.

If `defaultValue` is placed inside `props`, a renderer that spreads props can
accidentally give React both:

```tsx
<input {...node.props} value={state[key]} />
```

That mixes an initialization prop with the live controlled value and recreates
the original source-of-truth bug in a subtler form.

Therefore CAM should keep the same idea but move it under the local state
contract:

```json
"state": {
  "key": "serialNumber",
  "defaultValue": "$view.serialNumber"
}
```

The viewer consumes `state.defaultValue` before render. The renderer receives a
controlled value from viewer state. A renderer that deliberately wants
uncontrolled DOM fields can still map the seeded viewer state to React
`defaultValue`, but that is renderer policy, not CAM protocol state ownership.


React mapping
-------------

The manifest's `state.defaultValue` corresponds to React's initialization idea,
but the CAM viewer should render controlled React components.

Viewer/session flow:

1. Resolve `state.defaultValue`.
2. If the state key is not present in the current route-local state, seed it.
3. Return a snapshot containing the current local state.
4. On edits, update the viewer state.
5. Re-resolve button arguments and render props against the updated state.

Minimal React mapping:

```tsx
function TextFieldNode({ node, state, updateState }) {
  const { label, placeholder } = node.props
  const { key } = node.state

  return (
    <TextField
      label={label}
      placeholder={placeholder}
      value={state[key]}
      onChange={(value) => updateState(key, value)}
    />
  )
}
```

For generic prop spreading, the split is:

```tsx
<TextField
  {...node.props}
  value={snapshot.state[node.state.key]}
  onChange={(value) => updateState(node.state.key, value)}
/>
```

The renderer knows to read from viewer state because the node has a `state`
field. It should not infer editability from component names or from prop names
such as `value`.


Validation rules
----------------

The parser should be closed-world:

- reject unknown elements;
- reject stale `tag`;
- reject stale `$form`;
- reject `props.name`, `props.value`, `props.defaultValue`,
  `props.checked`, and `props.defaultChecked` on all nodes unless a future
  display element explicitly needs one of those names for a non-editable
  meaning. For stateful controls, initialization belongs in
  `state.defaultValue`;
- require `state.key` and `state.defaultValue` on stateful controls;
- reject `state` on elements that do not participate in local state;
- reject `call` on elements that are not buttons or includes;
- reject `children` on leaf elements;
- reject duplicate state keys within one resolved UI tree unless the protocol
  deliberately adds shared-control semantics later.

The important rule is structural:

  Only `state` marks live local state ownership.


Resolver rules
--------------

Initial UI resolution:

- resolve all stateful nodes without button calls first;
- collect state keys and resolved default values;
- seed the route-local viewer state;
- resolve the full UI with button calls using that state.

Current UI resolution:

- keep existing viewer state;
- do not overwrite viewer state from `state.defaultValue`;
- expose enough state metadata for renderers to wire controlled components;
- resolve button calls from `$state`.

Navigation:

- route inputs remain route-scoped data;
- route outputs remain contract/view data;
- local state is route/viewer state and should be seeded for the new view from
  that view's stateful controls.


Migration steps
---------------

1. Rename runtime concepts in code:
   - `form` -> `state`;
   - `updateForm` -> `updateState`;
   - `snapshot.form` -> `snapshot.state`;
   - `$form.*` -> `$state.*`.

2. Revise `@cam/screen` types and parser:
   - `tag` -> `element`;
   - `Input` -> `TextField`;
   - editable wiring moves from `props.name` and `props.value` to
     `state.key` and `state.defaultValue`.

3. Revise `@cam/screen` resolver:
   - stateful nodes seed local state on initial resolution;
   - current resolution uses existing state;
   - button calls resolve `$state.*`.

4. Revise `@cam/viewer`:
   - expose `snapshot.state`;
   - update via `updateState`;
   - preserve route-local state semantics explicitly.

5. Revise renderers:
   - React web reads editable live values from `snapshot.state`;
   - terminal commands and debug output say `state`, not `form`.

6. Revise `dapps/bike-nft/cam/ui.json`:
   - replace `tag` with `element`;
   - replace `Input` with `TextField`;
   - move input initialization into `state.defaultValue`;
   - replace `$form.*` button arguments with `$state.*`.

7. Revise docs that still describe `form`, especially
   `dapps/bike-nft/cam/README.md` and older notes if they are used as operator
   references.


Incisive tests
--------------

The core test should not be browser-specific.

Test: state default seeds local state once.

- Given a `TextField` with `state.key = "serialNumber"` and
  `state.defaultValue = "$view.serialNumber"`;
- and `view.serialNumber = "DEMO-FRAME-001"`;
- initial resolution yields `snapshot.state.serialNumber = "DEMO-FRAME-001"`.

Test: live state beats default on re-resolution.

- Given the same UI and `snapshot.state.serialNumber = "ABC123"`;
- re-resolution keeps `snapshot.state.serialNumber = "ABC123"`;
- the resolved control metadata still points at `state.key = "serialNumber"`.

Test: buttons read live state.

- Given a button whose call args use `$state.serialNumber`;
- and local state `serialNumber = "ABC123"`;
- the resolved call args contain `"ABC123"`, even when
  `view.serialNumber = ""`.

Negative tests:

- stale `tag` is rejected;
- stale `$form.*` is rejected;
- `TextField` without `state` is rejected;
- non-stateful element with `state` is rejected;
- editable live values in `props` are rejected;
- duplicate state keys in one resolved tree are rejected.


Definition of done
------------------

- Typing in the web viewer persists.
- Terminal state updates use the same state model.
- Actions use the typed value without renderer-specific logic.
- `make package-ci` passes.
- `make checks` passes.
- `make test-integration-fuzz-bike-nft` passes.
- The bike CAM README no longer documents the old `form` model.


AmountField: exact paired entry
------------------------------

AmountField adds two editable representations of one unsigned amount. Its
literal unit declaration belongs to the publisher; it is not a verified asset
registry, wallet denomination, or inference from a field name, ABI type, or
chain identifier. Asset identity is scoped to the current CAM host.

{
  "element": "AmountField",
  "props": {
    "label": "Escrow amount",
    "unit": {
      "assetId": "native",
      "baseLabel": "wei",
      "displayLabel": "Native asset",
      "decimals": 18
    }
  },
  "state": { "key": "amount", "defaultValue": "" }
}

The parser validates the unit as an own, flat declaration and snapshots each
scalar once. Unit strings, including leading dollar signs, remain literal;
other expression-bearing props retain ordinary CAM expression semantics.
The default is a base-unit string. Empty defaults seed null; malformed defaults
fail resolution before the new view is committed.

CamViewerSession owns one bounded active lexical draft per amount field.
The resolved AmountField exposes its unit, baseText, displayText, status, optional
issue, and optional composing: true for an unfinished primary phase. The only
canonical amount is snapshot.state[key]:
a decimal integer string or null. Routes keep reading $state.amount here; the display
text is never submitted as an amount.

Use session.editAmount(name, "base" | "display", text). Existing
updateState({ amount: text }) uses the same base-entry transition. Both paths
reject edits to disabled or unrendered fields. Terminal users can enter
`amount amount display 0.0100`, `amount amount base 10000000000000000`, or omit
the value to clear the field. Ordinary `set amount ...` remains base entry.

Conversion uses decimal strings without floating-point arithmetic or rounding.
Base entry accepts ASCII digits. Display entry accepts unsigned digits and one
period, including `.1` and `1.`. Leading zeros and trailing fractional zeros
remain in the active text. Extra fractional zeros are representable; discarding
any nonzero fractional digit is rejected. Signs, exponents, spaces, currency
symbols, and numeric separators are unsupported. Zero is structurally valid;
business minima and ABI ranges remain with their existing contract and adapter
owners.

Empty entry and an incomplete period have no canonical amount. Ordinary invalid
text stays in the active control with the other representation blank. No previous
valid amount remains available behind it. CR/LF entry is rejected as lineBreak
and clears both texts because native single-line inputs sanitize those characters.
Oversized input also clears both texts. These are explicit rejection states,
not trimming, truncation, padding, or substitution with a previous value.

Resource bounds are 2048 UTF-16 code units of active text, 1024 significant
canonical base-unit digits, and a declared scale from 0 through 255. A bounded
entry that exceeds the canonical digit limit retains its active text but is
unavailable. The canonical and scale bounds leave room for both representations
to round-trip within the text bound. They do not mirror uint256 limits.

load, navigate, and setAccount seed fresh defaults. Back restores a draft only
when its key and complete unit declaration still match; changed identity, labels,
or scale use fresh defaults. Failed projections preserve the coherent prior view.
An IME edit passed with { composing: true } preserves its active text and keeps
the canonical value null until an explicit finishing edit. History retains that
unfinished phase. Form drafts remain outside route URL inputs.

The web application invalidates prepared reviews on either representation's edit.
The session re-resolves actions against the new canonical state, and preparation
validates the cloned routed call against its ABI before returning it. Renderers
own native event transport and accessible feedback; they do not own a second
amount conversion or retain a last valid canonical amount.

The browser captures raw plain-text paste/drop and native beforeinput before
single-line input sanitization. Rejected noncancelable insertion cannot be
rehabilitated by the following sanitized input or composition completion.
Ordinary valid editing keeps native selection and caret behavior. Rebinding
the native listener preserves pending rejection transport; owner changes clean
up the listener and obsolete refs.

Only compositionstart on the actual input starts a native phase. Blur and
authoritative phase reset retire it; late composing input/end restore the
current projected text without editing the fresh draft. A true model projection
does not start native IME, so Back-restored unfinished drafts can be finished by
ordinary input. Maintained Chromium tests exercise these rendered event sequences,
paste sanitation, exact routed amounts, caret behavior, and narrow layouts.
They do not establish physical keyboard or operating-system IME behavior.


NonNegativeIntegerField: exact whole-number entry
-------------------------------------------------

NonNegativeIntegerField is a single editable control for ASCII decimal digits.
It does not infer number semantics from labels, state keys, ABI types, or values
that happen to contain digits. Ordinary TextField keeps its string-state model.

{
  "element": "NonNegativeIntegerField",
  "props": {
    "label": "Work duration in seconds",
    "min": "1",
    "max": "$view.maxPhaseDuration"
  },
  "state": { "key": "workDuration", "defaultValue": "" }
}

Minimum and maximum are optional, inclusive publisher declarations. Zero is
valid without a declared positive minimum. Each bound resolves to an exact
bounded decimal string. Bounds use the read-only initialization context, with
empty $state; they cannot depend on editable form state, directly or through
Include arguments. Malformed, unresolved, or reversed bounds fail projection
before the new view is committed. Contract business rules and ABI widths remain
authoritative; declaring a UI range does not authorize a contract operation.

Integer and amount fields share one session-owned discriminated numeric draft
map. Integer bounds stay in current resolved field metadata, outside drafts
and history. The integer draft preserves its lexical text, including leading
zeros. Its canonical state is the zero-normalized decimal string or null; the
browser and terminal display the lexical draft rather than canonical state.
The same 2048 UTF-16 active-text and 1024 significant-digit resource limits
apply to both numeric controls.

Use session.editInteger(name, text, { composing: true }) for an unfinished
native composition phase, or omit the option for a finishing edit. Existing
updateState uses the same finishing transition. Empty, composing, malformed,
or out-of-range entry has no canonical value. CR/LF or oversized input clears
the bounded draft explicitly; other invalid entry remains visible for repair.
There is no rounding, separator removal, clamping, or previous-valid fallback.

Back preserves same-kind integer text and revalidates it against freshly
resolved bounds. Cross-kind fields use fresh defaults; amount fields still
require matching complete units. Account changes seed fresh defaults, and
failed reprojections leave the prior coherent session untouched. Numeric edits
project canonical state before actions resolve, so a preceding button cannot
capture an old valid value from an invalid current draft.

The browser's NumericInput owns native event transport for both integer and
amount controls. Conversion and validity remain in the screen/session owners.
Terminal users can enter `integer workDuration 600`, omit the value to clear,
or use ordinary `set` for a finishing edit. Empty and valid controls add no
narrator hint; invalid or incomplete entry supplies associated correction.

The retained Chromium suite exercises integer range and syntax feedback,
leading-zero drafts, caret behavior, composition and history, exact prepared
arguments, and invalidation of an older prepared call. Existing paired amount
and workflow cases still pass through the shared transport. A temporary
component-shaped hint checks that a supported 1024-digit bound remains visible
at 320 CSS pixels; this is a geometry fixture, not a published-contract test.
Rendered event sequences do not establish physical keyboard, operating-system
IME, or operating-system clipboard behavior.
