1. Deadline settings: unclear meaning and explanation-to-field association

   Location: agreement creation, Deadlines section.

   User report:
   "Here, much is unclear. First, which clarification belongs to which setting.
   The UI doesn't say what those are, just dumps constraints."

   Observed in the supplied screenshot:
   - General limits and transaction/timing rules precede the duration settings.
   - Phase explanations appear between groups of inputs, making it unclear
     whether a paragraph describes the preceding or following setting.
   - Labels such as Acceptance duration and Work duration do not, by themselves,
     explain what the user is choosing. The surrounding copy leads with rules,
     deadlines and timeout settlement rather than the setting's purpose.

   Desired behavior:
   - Make each explanation visibly belong to its corresponding setting.
   - Explain what each duration controls and why the user chooses it before
     presenting its limits, timing mechanics and timeout consequences.
   - Preserve material contract rules while making the primary decision clear.

   Implementation: deferred. No layout or wording solution selected yet.

13. Calculate from file: justify its role when the app does not upload files

    User challenge: "If the interface does not allow/provide upload it doesn't
    seem useful to calculate from file, but prove me wrong."

    Context: Terms URI and document-digest controls offer Calculate from file
    and Calculate from URL, while explicitly stating that local files are not
    uploaded or checked against the URI.

    Candidate use case discussed: the user publishes the document through
    another service and hashes the exact local original. This can also work
    when the hosting service prevents the browser from fetching the URL.

    Important limit: hashing a selected local file establishes its digest; it
    does not establish that the entered URI is valid or serves matching bytes.

    Follow-up: evaluate whether this externally published-document workflow
    warrants the capability and its current prominence, and how the interface
    should explain the missing publication/URI-matching steps. No decision to
    retain, remove, relocate or supplement the control has been made. Upload
    support is not authorized by this question.

    Implementation: deferred.

19. Agent finding / design question: calculated digest survives a source change

    Attribution: agent-identified during a second live pass on 2026-10-28.

    Reproduction: set Terms URI to the local /cam/protocol.html and activate
    Calculate from URL. The calculation succeeds and populates a digest.
    Change Terms URI to /cam/main.json. The old digest remains, while the
    calculation-success message disappears. No current indication identifies
    the digest as calculated from the previous URI.

    Consequence: changing the document location can leave a populated URI/hash
    pair whose relationship has not been checked. Users may miss the need to
    recalculate or confirm the pair themselves.

    Qualification: the old success claim is correctly removed. A location
    change does not necessarily mean different document bytes; keeping a
    manually entered digest can be intentional. This is an unresolved workflow
    question, not proof that retaining a digest is always wrong.

    Follow-up: review the document pair's editing/calculation flow and source
    provenance. Do not silently erase a valid manual digest, automatically
    fetch on every edit or add conditional commentary by default. Choose the
    interaction only after establishing the intended document workflow.

    Implementation: deferred.

21. Agent finding: agreement review collapses the settings into a JSON tuple

    Attribution: agent-identified in the live unsigned transaction-review
    step on 2026-10-28.

    Reproduction: populate a temporary valid creation draft and activate
    Create agreement. Simulation succeeds and the viewer opens Review
    transaction. No Send action was activated.

    row containing compact JSON, including the reference, two addresses,
    recipient enum, amount, four durations and nested terms URI/digest.

    Attribution: agent-reproduced through the ordinary local creation UI
    after the user authorized test transactions on 2026-10-28.

    Draft: reference walkthrough-20261028-lifecycle, the existing client/
    contractor/arbitrator fixture accounts, 0.001 test ETH and four one-day

    explicit local chain IDs and previously supported omitted IDs work;
    wrong chains and unsupported fields are rejected. Regression tests cover

28. Agent finding: recorded documents have no open or verification affordance

    Attribution: agent-observed in submitted, disputed and closed agreements
    on 2026-10-28.

    Observation: Terms URI, Submission URI and Dispute URI are plain text
    fact values, with separate digest rows. The valid local protocol-document
    URI in the walkthrough renders as an ordinary dd, not a link. The prose
    instructs users to retrieve the document independently and compare its
    hash. The page offers no recorded-document open/download/hash-check action,
    although evidence-entry editors can calculate a hash from a URL.

    Consequence: a client reviewing submitted work or an arbitrator reviewing
    a dispute must manually extract URLs and use another workflow to read and
    check the evidence, rather than following a clear action from the record.

    Follow-up: review reusable presentation of a recorded URI/digest pair.
    Distinguish opening a document from verifying its bytes or its meaning.
    Reuse URL admission, download scope and bounded loading if retrieval is
    offered; do not automatically fetch contract-returned URLs or turn every
    arbitrary string into a link. No app-specific component/plugin is selected.

    Shared URI input/display work is tracked across all apps in
    notes/034_shared_cam_ui_backlog.txt, item 1.

    Implementation: deferred.
