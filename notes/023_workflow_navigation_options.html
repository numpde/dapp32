Navigation options for generated CAM workflows

2026-10-23 · Baseline addd8b7 · Design exploration · Provisional recommendation

CAM manifests describe contract calls and declarative interfaces. The web viewer renders these interfaces, but several workflows place many independent forms on one page. Reduce that clutter while keeping object identity, available and disabled actions, and transaction consequences easy to find.

Provisional direction: an object overview with focused task screens. Compare horizontal navigation, a sidebar, and ordinary task links before choosing a presentation or extending the protocol. Tabs are one candidate.

What exists today

Bike separates lookup, registration and workshop delegation, but its component view stacks details, metadata editing, missing reports, service state, workshop access and transfer. Escrow separates creation, agreement and account credit; agreement details and all action forms still share a surface. Pay-to-Play separates balance selection, position, signing details and recovery; its position combines funding, withdrawals, moves, keys, collection and payee changes.

In the renderer, nested Screen nodes become sections. They do not declare peer destinations. The route model supports calls and continuations; graph connectivity cannot determine a complete tab structure, task hierarchy or useful human labels.

These patterns can combine. Guidance distinguishes related tabbed content, tab semantics and keyboard behavior, collapsible sections, in-page navigation and navigation between pages. Their existence does not establish which works best here.

Fit each workflow

  • Bike: overview keeps component identity, NFT, owner and missing/service status visible. Focused tasks cover metadata, reports, workshop permissions and transfer. Keep registration separate.
  • Escrow: agreement overview keeps phase, deadline, parties, amount and action availability visible. Focus evidence entry on its task; disclose detailed terms and timings. Consider a wizard only for creation.
  • Pay-to-Play: retain customer, channel and balance identity across funding, withdrawal/move, voucher and management tasks. Recovery already has a separate destination; preserve its consequential distinctions.

Ownership and navigation requirements

Each CAM application, through its manifest and UI resources, owns task grouping, labels, order and destinations. The generic renderer owns layout, focus, accessibility and navigation mechanics. Contracts retain business-rule authority. This proposal requires no contract change and specifies no new metadata schema; the current CAM reference remains the protocol baseline.

Current web navigation replaces the URL, enabling route/input deep links without adding browser-history entries. The session maintains its own Back stack: ordinary navigation starts fresh; Back refreshes facts and restores compatible drafts. A successful viewing-account change resets forms and session history. Review invalidation prevents stale prepared transactions from reappearing; submitted transaction evidence has a separate lifecycle.

Proposed task navigation must define refresh, browser Back/Forward, session Back and draft behavior explicitly. Preserve disabled actions, invalidate stale review, and retain submitted transaction evidence when changing screens. Do not turn a presentation change into new permission logic.

Next comparison and evidence boundary

Use the same Bike content and grouping to compare horizontal route links, sidebar and overview task links. Exercise lookup, metadata editing, missing reports, delegation and transfer at desktop and narrow widths, including keyboard, disabled, pending and recovery states. Decide from that comparison before protocol additions.
