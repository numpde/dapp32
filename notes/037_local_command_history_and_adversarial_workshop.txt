Local command history and adversarial exploration
=================================================

Date: 2026-10-30.
Status: proposed design, not implemented or operationally qualified.
Scope: a useful local approximation of interactive failure exploration, starting
with organized command history. No Antithesis dependency, deployment, signing,
operator-secret access or production behavior change is authorized by this note.

This develops sections 13-16 of note 036. Antithesis is excluded from the selected
architecture, including optional execution backends. Other conclusions of 036
remain proposals; command history must not wait for its complete host refactor.

1. Decision and minimum useful result
-------------------------------------
Build automatic structured command recording into the common execution boundary
used by supported workflows. Its facts come from the owner that receives a
request or launches work. Recording is foundational behavior, not an opt-in
fixture notebook. Questions, replies, discussion, readers and replay are later
features and must not delay this foundation.

Keep ordinary commands ordinary:

  make pay-to-play/local/fixture/up FIXTURE_ID=<owned-id>
  make pay-to-play/local/fixture/info FIXTURE_ID=<same-id>

Each supported workflow records automatically in durable local state. No SESSION
variable or extra operator step enables recording. Optional grouping/export may
be added later; neither enables nor disables capture. Checks, builds, reads,
dependency work, service/fixture operations and release operations use the same
boundary without inheriting release-specific approvals or state gates.

Derive coverage obligations from supported target declarations, not a second
manually maintained registry. Reject workflow routes and governed launches that
bypass the recording/execution owner. Prove both the structural route and actual
record publication through supported commands. One fixture is an integration
witness, not completion of all-workflow coverage. Existing Go ownership checks
cover selected JS/TS source roles; they do not yet establish this wider guarantee.

Persist a request before subject work: run ID, source/tool identity and admitted
non-secret inputs. Governed launches record their parent, safe executable/args
and timing, then exit status, signal or an explicitly unknown outcome. Link native
evidence; do not infer external success from process exit. Do not copy signing
inputs, environment dumps or secret argument values into history.

If initial recording fails, refuse before subject work. If recording fails later,
stop further ordinary work while preserving cancellation and cleanup. Interrupted
runs remain incomplete; missing completion never means success. Local recording
cannot commit atomically with remote effects. Explicitly name unobserved internals
and remote activity instead of claiming universal process tracing.

This requirement supersedes the original opt-in and discussion-first workshop
sequencing below. Questions/readers/replay are later capabilities, not foundation
requirements. The ordinary process owner remains responsible for cleanup.

Do not introduce another command language, shell kernel or deployment workflow.
The notebook observes execution; existing process owners still execute and
clean up. Existing native artifacts/audits still establish external outcomes.

2. What 'all commands' means
----------------------------
The desired coverage is every subject command in the experiment: setup, public
operations, inspections, injected conditions, checkers, reset and cleanup. Do not
record only successful deployment commands and omit probes that changed state.

Coverage must also name the observation boundary:

  Public request: the Make target and admitted settings received by its owner.
  Owned launch: literal safe argv at an instrumented process/job boundary.
  Native evidence: linked audit, artifact, receipt, proxy or service evidence.
  Unobserved internals: shell builtins, uninstrumented children, daemon-created
                       processes, remote services and manual outside actions.

Make cannot recover the original shell spelling. Quoting, shell expansion and
some command-line normalization have already happened. Its request is an exact
account of the admitted target/settings, not the original shell command line.
An existing test driver that supplies an argv array can retain that actual array.
Never reconstruct executable argv by parsing echoed recipes or terminal output.

For a participating entrypoint, record the safe request before subject
prerequisites/probes, not only after successful preparation. Native rejection of
bad input or unavailable dependencies is part of the history. Do not duplicate
those validators in the recorder. Make parse errors or earlier bootstrap failures
are outside an in-recipe hook; an existing outer test driver can record its own
Make request/result, but the hook must not claim it observed those earlier steps.

Each session shows its coverage, including missing child coverage. No claim of
universal workstation/container tracing follows from complete root requests.
An external action can be added as a reported intervention, explicitly marked
manual/unobserved. It is not retroactively an observed command.

Recorder administration is distinct from subject actions. Reading a saved
history stays read-only; publishing a question is an annotation. Neither starts
an infinite history of the recorder recording its own bookkeeping. Bootstrap
before the recorder is ready is outside coverage and can link its own logs.

3. Serious alternatives and why this choice
-------------------------------------------
A. Shell history plus a manually maintained Markdown notebook.
   Excellent immediate readability and almost no new runtime. Weak on working
   directory, effective inputs, failures, child commands and crash evidence.
   Keep manual imports useful, but label them as recollections, not captured
   launches. Do not let shell-history completeness become the test oracle.

B. util-linux script/asciinema recordings.
   Good human playback: prompts, terminal progress, resize and timing. A PTY
   does not recover actual process argv or external effects. Input capture can
   record passwords even when echo is disabled. Keep output-only playback an
   optional fixture attachment; never derive runnable commands from it. [R1-R3]

C. Make --trace, shell xtrace and recipe logs.
   Cheap explanation of recipes and dependencies. Expanded values can disclose
   credentials, and a printed recipe is not an executed-process inventory.
   Useful focused diagnostics in a known-safe fixture, not the history owner.

D. strace/exec auditing/eBPF.
   Can expose local process activity missed by application logs. Adds authority,
   scheduling changes and sensitive argv/buffer capture. Following Make forks
   does not follow unrelated Docker-daemon children. Keep as explicitly scoped
   disposable diagnostics, not a default prerequisite or completeness cure. [R4]

E. A generic outer launcher accepting COMMAND or a shell notebook prompt.
   Captures selected root argv and could support arbitrary tools immediately.
   It also creates another argument grammar, process/TTY owner and supported
   way to run deployments. Reject as the mandatory operator path. An existing
   test driver may legitimately own its Make child; no parallel workflow needed.

F. Runme executable Markdown notebooks.
   A genuine reuse candidate: commands beside explanations, saved outputs,
   durations and exit codes, with CLI/editor/browser interfaces. Its separate
   reusable instructions and session outputs fit this problem well. [R5]
   Its shell/environment session is an additional execution model; resetting it
   does not reset Docker, chain state or instance records. Documented auto-save
   does not establish our mandatory before-launch/crash evidence boundary.
   Borrow the presentation separation; an optional imported notebook remains
   possible. Do not require Runme or build a competing generic notebook kernel.
   Its experimental eval mode evaluates agent tasks through a separate adapter;
   that is a different need from recording our ordinary commands. [R6-R7]

G. Instrument the existing host process owners and expose an inert notebook.
   Selected. Public requests and known safe launches are observed where they
   occur. One small record publisher and derived views serve current fixtures
   and the future controller. No copy of deployment semantics or second process
   supervisor. Initial coverage is bounded and visible, then grows by owner.

H. Immediately require a complete VM snapshot/replay system.
   A disposable VM is useful later for real daemon/OS failure experiments, and
   coherent whole-world checkpoints can save time. It adds image/kernel/engine
   retention and virtualization authority before a single question is recorded.
   Do not make the minimum notebook depend on it. Restart first. [R8]

OpenTelemetry can later export a derived view of command spans. It is not the
mandatory durable store: sampling, queue limits and exporter failure can discard
telemetry. Avoid a collector/backend just to read local command history. [R9]

4. The operator and agent experience
------------------------------------
Create one session under an operator-selected durable output root. The command
creates its own dated/unique child directory; no empty-folder preparation. Print
the exact session path and how to attach subsequent ordinary commands.

Prefer SESSION on the command or a deliberately exported session destination.
Preserve the repository's literal-variable transport rules; never interpolate
untrusted path/text into shell source. Deliberately propagate the session to
owned children that participate. Do not rely on recursive Make ambient flags.

Naming workshop, proposed supported targets:

  make ops/session/start DIRECTORY=<durable-output-root>
  make ops/session/show SESSION=<session-dir>
  make ops/session/note SESSION=<session-dir> STEP=<step-id>
  make ops/session/reply SESSION=<session-dir> QUESTION=<entry-id>

These are interface sketches, not supported commands to run today. 'Start'
creates the notebook only; it does not start a chain, Docker daemon or wallet.
'Show' reads it. 'Note' accepts a question/proposal/observation as text from a
file or an explicit text prompt; 'reply' attaches text to an existing question.
Use files/stdin for multiline text, rather than a shell-command string variable.
Author labels are human attribution, not proof of identity or authority.

No new session/run TARGET wrapper is required. A future agent API submits the
same fixed operations and literal inputs through the same supported owners.
There is no eval(text), shell=True or executable Markdown interpretation.

At a command boundary the reader sees, for example:

  004  Inspect fixture                 process exit 0
       pay-to-play/local/fixture/info  fixture: primary
       Output complete; child coverage: declared launches only
       1 open question; no checker assessment yet

  Q7   What if up is repeated with this fixture ID?
       Prediction: refuse without changing the existing deployment.
       Proposed experiment: repeat ordinary fixture/up, then inspect identity.

  005  Repeat fixture creation         process exit 2
       Capture complete; assertion passed: original fixture unchanged
       Verdict: GREEN for duplicate-create safety

This is an illustrative future display, not an execution receipt. A nonzero
process result can be the correct expected refusal. Absence of a checker is
shown directly; no default GREEN badge fills the gap.

5. One notebook, several different facts
----------------------------------------
Session: the purpose, local coverage policy and stable identity of the inquiry.
World: the selected disposable fixture identity and its owned coordinates.
Command: a public request or an observed child launch with parent linkage.
Entry: a question, reply, proposed intervention, observation or assessment.
Case: a reviewed runnable regression, created only after there is one to run.

Do not turn these nouns into a universal workflow type hierarchy. They name
present boundaries; the implementation needs only the fields current readers
and writers consume. One small versioned notebook format is justified by durable
external files, independent processes and future readers, not by anticipated API
generality. It carries command history, not a second deployment artifact schema.

Minimum command facts:
  stable ID and parent/public-request relationship;
  received target/settings or observed argv, explicitly distinguished;
  cwd/source/tool/world references, with omitted facts identified;
  requested time and local ordering;
  launch observation when actually available;
  observed exit code or termination signal when actually available;
  output/evidence references and capture limitations.

The pre-spawn fact says requested/admitted or launch prepared. It cannot say
process started before fork/exec succeeds. A spawn error is an observation. A
crash between recording and spawning leaves uncertainty, not proof of execution
or non-execution. PID alone is not stable process identity after restart.

A command summary is derived. Do not persist a mutable succeeded/running flag
alongside the events or copy 'deployment verified' into the notebook. The native
artifact/audit remains authoritative; the notebook links its exact bytes/digest.
History can be complete while the subject is unresolved, and vice versa.

6. Storage without a database or daemon
---------------------------------------
Proposed durable tree, outside the checkout and outside INSTANCE:

  <output-root>/<session-id>/
    session.json
    events/
      <ordinal>-<event-id>.json
    output/
      <command-id>/
        stdout.log             # pipe mode, when separate streams exist
        stderr.log
        terminal.cast          # PTY mode alternative, not always all three
    index.html                 # generated, disposable projection
    index.txt                  # generated, disposable projection

Allocate only used directories/files. Session identity is not its pathname.
Store child-world identity and parent-trajectory links as needed; no global
registry of all sessions is required for the first reader.

Coarse immutable event files are the notebook facts. Output chunks are not
events. A single shared publication implementation, called by short-lived
owners, takes a brief local lock, allocates order and exclusively publishes one
complete event. Write/fsync its bounded temporary file, publish without replacing
an existing event, and fsync the directory before reporting durable publication.
Keep interrupted unpublished bytes distinguishable from committed events.

The lock covers allocation and publication, never a long-running command.
Concurrent peers can add questions while work runs. The test driver's plan owns
sequential experiment execution. The notebook does not add an execution mutex;
manual concurrent requests are recorded as overlap, not certified as a sequential
replay prefix. Existing fixture/instance owners retain their own resource locks.
Intentionally concurrent tests must specify their synchronization independently.
Ordinal gaps are harmless; never renumber history. Ordinals are committed local
notebook order, not global causality between processes or remote events.

Parent/causal references express observed relationships. Wall clocks help human
navigation; monotonic durations belong to their observing process. A clock jump
or two process clocks cannot fabricate an exact cross-process schedule.

No shared append-log repair, broker, background recorder, hash chain, event-sourced
deployment engine or mutable status cache is needed. The number of coarse facts
in a human investigation is small. Reconsider indexed storage only for measured
scale/concurrency, without changing what the facts mean.

This is a local filesystem assumption, not a claim about NFS or power-loss
behavior on every filesystem. Reuse the durable/exclusive publication owner from
the operations design where available; do not create a second security policy.
Both event/log permissions and exports remain private by default.

The writer needs a real runtime. Do not hand-serialize JSON/fsync in Bash or
assume host Python/Node from containerized tools. Prefer the small native Go
publisher built offline in pinned Docker described by 036, without requiring its
full controller: it writes notebook facts only and owns no subject processes.
Build/cache admission precedes session readiness; retain bootstrap diagnostics
with their explicitly weaker coverage. Once ready, recording must not depend on
starting another Docker container for each event. Otherwise an unavailable
daemon, one of the failures under investigation, would also disable the recorder.
Use one publisher implementation, not parallel host/container format owners.
Keep its host/platform/dependency posture explicit. Implement and qualify the
same proposed offline build boundary as 036; it is not claimed to exist today
and belongs to Slice 1 if still absent when implementation starts.

7. Process ownership and incomplete capture
--------------------------------------------
The existing execution owner performs the actual launch, wait, signal handling
and resource cleanup. The publisher accepts bounded safe facts; it does not
spawn, stop or retry subject commands. There is no extra generic supervisor.

Publish the top-level experiment request before starting its subject work. If
this fails, do not start it. This is not a new permission gate before every
internal child launch. Child instrumentation reports observations best-effort;
it must not make native work depend on notebook writes. Once a public command is
running, capture failure cannot undo its effects. Continue through its existing
owner; do not break its pipe, fill memory or prevent cleanup because a log is full.

Already-owned cleanup is the narrow exception to the before-launch recording
gate: teardown proceeds through its existing owner even if the notebook cannot
write its request. Retain best-effort diagnostics and expose the capture gap.
This grants no new creation, retry, signing or unrelated cleanup authority.

Stop automatic NEXT experiment steps after a capture failure, except necessary
owned cleanup. This does not claim to stop further effects INSIDE the already
running Make command. A recorder has no new authority over its internal signing
or transaction sequencing. Fixture harness cancellation is an explicit action,
recorded separately, and preserves possible effects rather than claiming undo.

Keep independent facts distinct:
  subject observation: exited 0, exited 2, signaled, or no final observation;
  capture observation: complete, truncated, write failed, or missing tail;
  cleanup observation: linked owner proof, incomplete, or unobserved;
  assessment: named assertions passed/failed/not evaluated.

Do not overwrite a useful subject result with 'recorder failed', or report a
truncated transcript as complete because the child exited zero. An experiment
command can return a nonzero infrastructure result while still preserving its
observed child result. Automation must not silently proceed after that failure.

Retain the result the actual owner can observe. For example, Bash wait's encoded
status 143 cannot alone distinguish explicit exit 143 from SIGTERM. Do not invent
a signal cause from that integer; use richer process information only where the
owning adapter actually supplies it.

If the recorder dies, the next reader does not invent completion from the last
line saying success. Missing completion is an unknown observation; inspect
existing resource/audit/artifact authorities. Recovery appends a new observation,
not a fabricated original exit code. Do not retry an unresolved paid effect.

If the whole store fails, its failure event may be missing too. The later reader
shows missing completion or unfinalized output and an incomplete observation;
it cannot invent disk exhaustion, successful cleanup or any other cause. Native
reconciliation may establish later facts, not the lost original process result.

A cancellation request and a later signaled exit are separate observations.
The former does not prove it caused the latter. Direct signals, Docker client
exit and detached container state remain subject to their actual owners.

8. Capture safely and say what is missing
------------------------------------------
Initial scope is disposable local fixtures with public fixture keys. Do not
enable blanket argv/output capture across real signing/operator workflows.
Never dump all environment, stdin, secret files, arbitrary shell strings, raw
signed transactions or Docker inspect objects into a general notebook.

Record safe literal argv only at a boundary with a known secret-free contract.
Some existing launchers pass scripts or credential-bearing values. They require
a safe semantic description/reference or explicit omission, not a regex that
purports to sanitize arbitrary expanded argv. Mark redacted/omitted requests
non-exact and unsuitable for direct reproduction.

Terminal output is not intrinsically safe either: programs can echo input or
print secrets. No promise of universal redaction. Fixture isolation and safe
producer contracts are the initial boundary. Real operator history would need a
separately qualified output policy; private permissions alone do not make
secret capture acceptable. No automatic upload or publish-to-Git action.

Raw keystrokes are not recorded. For repeatable fixture prompts the test driver
may record an intentional semantic choice, such as reject candidate with hash X.
It must match the current prompt/reference before supplying the choice. Do not
replay a timed stream of 'a' keys or carry approval authority into a fresh run.

Choose pipe or PTY to preserve the existing invocation's intended behavior.
Do not force a PTY on JSON/protocol stdout or replace interactive release input
with a pipe merely to simplify logging. In PTY mode streams are merged; record
that fact, geometry/resize and relevant terminal mode. Playback may be attached
using an existing format such as asciicast, rather than inventing a terminal
protocol. Input events/environment dumping remain disabled. [R2-R3]

Capture stdout/stderr incrementally with finite byte/memory bounds, plus a
bounded tail where useful. Separate streams have per-stream order; observer
arrival order is not a proof of the subject's original interleaving. A cap is
visible and makes that capture incomplete. Keep reading after it is reached.
Do not insert truncation prose into protocol stdout seen by other consumers.

Before publishing capture-complete for owned retained output, finalize it:
flush/fsync/close and pin byte counts/digests where evidence references require
them, then publish the durable completion observation. Failed finalization means
incomplete capture. Existing linked PTY/log artifacts retain their owner's
original retention guarantee; do not silently upgrade them to durable output.
Prefer those existing outputs over another tee/PTY layer with different TTY,
backpressure or cancellation behavior.

Source identity also has limits. Record HEAD/dirty observation and link any
existing fixture-owned candidate snapshot/tool identity. Do not copy all user
files, Git diff or the whole environment into a notebook. Dirty source without
a retained safe snapshot still permits history/discussion, but not an exact
source replay claim. Source or environment drift is not a reason to erase facts.

Existing input/artifact bytes remain at their natural owner. Pin a digest when
an assertion depends on them; a mutable path alone is not historical evidence.
If it will disappear with fixture teardown, retain an explicitly selected safe
evidence copy before cleanup. Do not copy secrets or treat a digest as a backup.

9. Questions, replies and independent assessment
------------------------------------------------
A discussion entry points at a stable command/event ID and, optionally, exact
evidence bytes/ranges. Live output offsets are provisional until the file is
closed/pinned. Replies point at the question they answer; correcting an earlier
claim appends a correction instead of editing the observation it contradicted.

The useful entry kinds are small:
  question: what might fail, and which law are we testing?
  prediction: the expected outcome, not observed truth;
  proposal: a concrete sandbox experiment, not permission to execute it;
  observation: evidence and how it was obtained;
  decision/assessment: conclusion, checker and remaining limit.

One text body can remain plain text/Markdown. These categories help the reader
distinguish claims; they are not a bureaucracy requiring five entries per step.
A human can ask one sentence and receive a reply before any test exists.

Use the existing agent conversation/messaging tools. An agent or coordinator
publishes the selected question/reply with its step reference; the notebook does
not host a model, invent a new agent SDK or copy entire private chat/tool logs.
Agents read the same structured history and selected evidence as the human
reader. Their conclusions remain attributed claims until supported by evidence.

Adversarial peer: proposes plausible conditions and predicts consequences.
Coordinator: chooses a bounded experiment and supplies already authorized inputs.
Execution owner: runs the actual supported command/intervention.
Checker: evaluates an explicit law using independent observations.

No actor becomes a signer by writing an annotation. A proposed fault string is
not a shell command. No Markdown code fence is executed by the reader. Ordinary
authorization still applies; local test permission never implies Fuji authority.

Examples of substantive questions:
  What if setup creates its directory but Docker cannot allocate the network?
  What if a CREATE is mined but its acknowledgement never reaches the caller?
  What if someone repeats fixture/up with the same identifier?
  What if output storage fills after the child has begun?
  What if the selected UI baseline changes between observation and approval?
  What if we restore the chain but keep instance records from a later point?

Prefer one falsifiable claim and its smallest witness. Do not reward peers for
inventing an enormous failure matrix or listing speculative hardening work.

10. The reader is inert; the runner has explicit authority
----------------------------------------------------------
First provide a text index generated from notebook facts. A small static HTML
projection can add a navigable timeline, command details, output links, question
threads, coverage gaps and parent/child comparisons. Data and presentation stay
separate. Regenerating a view never edits the captured facts.

Opening the file must not execute any command. Render all recorded output and
annotation text as untrusted text; do not run terminal control sequences, inject
HTML, fetch arbitrary recorded URLs or execute Markdown. No Docker socket,
signing configuration, command endpoint or mandatory web server in the reader.

A single exported HTML file may embed a derived safe snapshot so file:// viewing
works without a local JSON-fetch server. That snapshot is a projection, with a
source digest/version, not a second editable source of truth. Large/private logs
are explicit attachments, not automatically embedded. A browser viewer remains
read-only; notes are submitted through the supported publisher command initially.
Show 'through entry N; generated at ...' so a saved projection cannot appear to
be a live timeline. Only owner-generated safe attachment paths become links;
untrusted recorded strings do not become executable or fetching URLs.

No Run button for recorded live/unknown commands. A later 'try this experiment'
action should prepare a reviewed local test selection for the supported runner,
not send an arbitrary historic command to a browser-to-host execution API.

11. Replay has three separate meanings
---------------------------------------
Watch: display saved output and annotations. No processes or external effects.
Use the word playback. Terminal controls are interpreted only by an explicit
qualified player, not pasted into the ordinary history viewer.

Repeat: run an ordinary supported command again against its current selected
world/instance. This may inspect, resume or change that world. Call it rerun or
resume according to the native operation; never label it rollback.

Restart experiment: make a fresh owned test world and execute a reviewed prefix
using logical bindings. Preserve the original run and link a new child history.
This is the default useful approximation of going back command-by-command.

Captured absolute INSTANCE, FIXTURE_ID, port or socket values are historical
facts, not instructions to reuse them. A replay recipe declares logical fixture
bindings and lets the normal owners allocate a fresh instance/ID/resources.
Do not implement arbitrary string substitution over old argv. Values that are
not declared fixture bindings cannot silently be rewritten.

Initially choose a prefix ending between completed commands. Recreate from base,
rerun the required prefix, inspect that boundary, then choose another next step.
Dependencies such as a prior active fixture are explicit; one cannot skip its
creation because an old notebook once printed an address.

Question/proposal text is not a replay script. A reviewed case uses native test
code, exact public targets and assertions. Testscript-style command/assertion
fixtures are a credible pattern, but adopting a new testing dependency is not
required; existing repo test owners can express these cases. [R10]

No reviewed recipe means no AUTOMATIC replay, not a ban on manual experiments.
The reader can show/copy the historical target and safe settings with old world
paths clearly identified. To try a fix before command 5, create a child history
linked to the boundary after 4, record the new source selection, allocate a fresh
world and explicitly review its bindings. Manually run the necessary prefix,
inspect that boundary, then run 5. Preserve both histories and source differences.
If the prefix cannot be reconstructed, report that limit; neither reuse the old
world nor require CI promotion before a useful what-if can be attempted.

Checkpoint/restore comes later only when all required world components have a
qualified restoration mechanism. Anvil revert alone does not restore files,
approval capabilities, mock hosting, processes or Docker resources. Incomplete
checkpoints can be inspected, but restoration is refused; restart from base.

Mid-command faults require real synchronization: for example, an owned proxy
holds a specific request before releasing/dropping it. A progress event plus
SIGSTOP is subject to a race and cannot claim an instruction-level breakpoint.
Record which boundary was actually reached and whether the intervention took
effect. No deterministic execution/replay claim for the ordinary host/daemon.

12. Conditions and commands are different observations
-------------------------------------------------------
The peer may ask what happens with no disk space, stale source, a delayed RPC,
wrong chain or a stopped container. The runner uses a known test adapter that
owns the selected fixture target, not arbitrary peer shell on the workstation.

Record the proposal, requested condition, actual intervention and observation
separately. 'Drop the next reply' is not proof that a reply was dropped. Name the
matched request and whether it had already been forwarded/mined. If the boundary
was missed, mark the intervention unestablished rather than asserting a clean
fault test. Docker/chain/runtime effects remain native observations.

The command that implements a condition is itself captured when it crosses an
instrumented launch boundary. Internal adapter activity can emit safe named facts;
it must not invent a command line for direct in-process work. Reads/checkers and
cleanup are included, not hidden in unrecorded preparation around the test.

No deliberate exhaustion of the shared Docker daemon or host filesystem. Use a
bounded test mount, dedicated daemon/VM, or explicitly modeled failure. A model
of network allocation failure is not an actual Docker-pool exhaustion witness.
Local URLs alone do not prove isolation; the fixture's network/mount/credential
grant defines it. No operator secrets or public-chain writes in a restart world.

13. Worked inquiry: duplicate fixture creation
-----------------------------------------------
This is a proposed experiment using CURRENT supported targets, not a run made
in this workshop. SESSION hooks and assertions below still need implementation.

1. Allocate a new logical 'primary' fixture ID through the test owner.
   make --no-print-directory pay-to-play/local/fixture/up FIXTURE_ID=<primary>
2. Inspect it using the current descriptor producer.
   make --no-print-directory pay-to-play/local/fixture/info FIXTURE_ID=<primary>
3. Attach Q: what if up is accidentally repeated with this same identity?
   Record prediction: refuse before touching resources not owned by this call.
4. Repeat the exact ordinary fixture/up target with the same ID in THIS world.
5. Inspect again. Compare original descriptor/core identity and relevant owned
   resources through the native fixture evidence; an expected error alone is
   insufficient to prove the original was untouched.
6. Tear down the owned fixture with fixture/down, then inspect: the expected
   absent fixture is a successful assertion, despite info returning nonzero.

Save GREEN only for those explicit assertions. If the duplicate call changes
the original, save RED with both before/after observations. If Docker cannot
start the baseline, save an incomplete experiment, not a duplicate-create pass.
If cleanup fails, preserve its separate evidence and retained world identity.

Restarting this inquiry allocates a NEW primary ID/world. Repeating up inside
one inquiry intentionally reuses its ID; replaying a saved inquiry does not.
This distinction is the reason generic 'rerun every saved argv' is incorrect.

14. Worked inquiry: release acknowledgement and recovery
---------------------------------------------------------
Begin with a recorded ordinary baseline such as:
  make escrow/release/rehearsal/run

Ask: if the transaction acknowledgement is lost, what does the caller know and
what should it do next? Attach prediction and the particular asserted law.

The current supported wait lanes provide a nearby useful first experiment:
  make escrow/release/approval-wait/check
  make escrow/release/ipc-approval-wait/check

tools/release_waits.sh has real delay/receipt/reject/drop cases and resets its
isolated chain between cases. Its setup/check failures are explicitly inconclusive.
Its transport/Forge observations are not proof of every full resume law.

An interactive mined-loss/resume case is a later bounded slice: forward one
approved fixture transaction, establish mining through an independent fixture
observer, drop the response, stop the controller, then use the same ordinary
resume command against the retained instance. Assert that the original creation
is reconciled without a second CREATE. Capture the independent before/after
chain evidence and native artifact; never infer absence from a timeout.

This notebook does not create that missing intervention/resume proof merely by
recording a wait test. Keep existing proof scopes and new experiments distinct.

15. Verdicts, regression promotion and useful failure
-----------------------------------------------------
Record process results immediately; do not assign an automatic test verdict.
An assessment names the law, its checker/version, evidence, world/source and
scope. A later correction appends a new assessment with the reason/reference.

RED: an assertion is violated. Preserve the smallest witnessed path.
GREEN: the named assertions held in this qualified run. Correct refusal can pass.
KNOWN-RISK: an explicitly reviewed unmet guarantee with owner/reason/boundary.
INCOMPLETE/NOT-RUN: not enough evidence, setup/checker failure or no execution.

Risk is not a catch-all for new failures or missing tests. Do not collapse a
RED safety assertion into risk because the command is difficult to reproduce.
Conversely a harness/storage failure is not automatically a product defect.
Present which assertion failed, which evidence is absent and what can conclude.

Turn a useful discovery into a small ordinary test:
  declare the baseline and logical fixture inputs;
  execute the exact public command prefix;
  synchronize a named intervention, if any;
  run an independent native assertion and check owned cleanup;
  retain the original RED history and a separate repaired GREEN history.

The test must run without agents/model APIs. It is not a permanent transcript
parser, timed keystroke script or general scenario DSL. Minimize the cause without
removing required dependencies. A source change creates a new compared run; it
does not overwrite the old command/output/evidence.

17. Plan: enforce execution ownership automatically
-----------------------------------------------------
Invariant: governed operation entrypoints reach their one execution owner;
callers do not recreate launches or workflows beside it. Recording belongs at
that boundary. Static checks enforce permitted routes/dependencies; an actual
execution test establishes that the route records what it does.

Language split: note 036's accepted decision makes Go the common execution and
architecture policy owner, with native analyzers supplying facts. The earlier
tests/checks/test_execution_ownership.py placement was provisional: do not create
that Python wrapper or duplicate policy merely to preserve a filename. Common
policy tests belong beside their Go owner; native analyzer tests belong beside
their frontend. Existing standard-library Python repo checks retain their own
useful scope. Structural rules do not belong in checks/text unless they actually
rely on brittle textual matching.

Step A: identify and expose the real ownership boundary.
  Define common role contracts and the actual host executor/process boundary,
  independently of application names. Identify native container jobs, fixture
  drivers and bootstrap separately; they have legitimate, different execution
  authority. Do not ban subprocess use across every test, tool and container.
  Enforcement must follow an implemented boundary, not invent an executor stub
  or pretend today's distributed host scripts already meet the proposed shape.
  Discover role-bearing modules automatically; do not register families or copy
  the checker for each application. Delete displaced routes as their real owners
  move to the shared execution boundary.

Step B: check entrypoint routing.
  Discover governed targets from their real declarations; do not maintain a
  parallel hand-written inventory that new targets can escape. Each declaration
  identifies its operation and recording capability at the same owner used by
  dispatch/discovery. Unknown or unclassified entrypoints in the governed boundary
  fail the check rather than silently falling outside its scope.
  Inspect expanded recipes, following the existing expanded_release_target
  approach in tests/checks/release_posture.py. Assert the supported forwarding
  shape and correct operation identity, not merely that an executor name occurs
  somewhere in shell text. Reject extra workflow/launch commands around it.
  Make dry-run can still evaluate shell probes/recursive recipes: inspect only
  controlled inputs in the secured offline lane, never operator configuration.
  Do not build a general shell parser. Prefer a constrained forwarding recipe
  generated by the owning declaration; compare its expansion to that shape.

Step C: check process-launch ownership and import direction.
  Inspect imports/calls in governed host source: only the designated process
  adapter may use raw process-launch facilities. Resolve import aliases and
  cover the relevant alternate APIs, such as os.StartProcess as well as os/exec
  in Go. Reject unanalyzable dynamic launch forms in that constrained surface.
  Use compiler/module visibility first and language-aware analysis where needed;
  do not call a keyword search proof of execution ownership.
  Keep Python checks standard-library-only. If Go/TypeScript parser support is
  needed, its semantic analysis runs in that language's existing/proposed pinned
  offline tool lane, wired into normal tests; do not install host runtimes or
  add parser dependencies to the Python checks container merely for this rule.
  Enforce callers -> operation implementations -> execution adapter. Operation
  code cannot import CLI/notebook/test drivers; production code cannot import
  fault-injection/test-support modules. Reuse existing dependency-check patterns.
  Keep necessary exceptions exact and owned; no blanket tests/tools exclusion
  that lets a second production path hide there.

Step D: prove the architecture checks detect violations.
  Add small positive/negative source and recipe examples: ordinary forwarding,
  direct launch, aliased launch API, embedded Make workflow, forbidden import,
  and a newly declared governed target lacking capability/routing information.
  Each forbidden example must be rejected with its file/location and owning
  boundary. These are checker tests, not a claim of arbitrary-program analysis.

Step E: prove recording through actual execution.
  Keep executor behavior tests in its native package suite. Put the supported-
  command integration case under tests/operations/ when the first real consumer
  exists, using the disposable fixture described in sections 13 and 16.
  Invoke ordinary Make targets; inspect request/result IDs, native descriptor
  evidence and cleanup independently. Suppress one required record in a small
  controlled test variant: the history assertion must fail even if the fixture
  operation succeeds. Do not obtain expected effects from the executor's output.
  This test is required because allowed imports/routes cannot prove a recorder
  was called, persisted its result or observed the intended external effect.

Step F: wire the gates into ordinary commands and commit by slice.
  Existing Python checks remain automatically discovered by make tests/checks.
  Native offline parser/executor tests join the offline CI path. The supported-
  command disposable integration joins make tests through its scoped lane;
  make ci remains offline. Static checks stay offline; disposable-chain
  qualification retains its own lane.
  Extend an existing scoped target when it owns the same purpose; add a target
  only for a distinct operator/runtime boundary, documented in make help.
  Land the initial bounded rules with their first real migrated owner and checker
  examples; land the recorded fixture witness with the recording implementation.
  Inspect staged scope and commit each coherent green slice. Do not accumulate
  a repo-wide exemption inventory or enable a permanently failing placeholder.

Completion: a direct-launch bypass, a wrong-direction import and a misrouted/new
governed target fail their static gates; an actual recorded Make inquiry passes;
omitting its required record fails the execution assertion. These prove the
declared boundary and named behavior, not that arbitrary obfuscated code cannot
perform effects or that every legacy target has already migrated.

Implemented common foundation (2026-10-30):
  js/tools/execution-ownership.test.mjs defines ONE ownership policy by module
  responsibility. Every immediate js/tools/*/ directory uses the same convention:
  core.ts, shared.ts, reference.ts, protocol.ts and config.ts declare core roots;
  main.ts and runner.ts declare entrypoint adapters. Discovery has no application
  names, release suffix or per-family registry. Adding a core role file makes

  architecture convention, not an inference that all other files are harmless.
  Static local tooling dependencies inherit the core constraints. Core imports
  of entrypoint adapters, test/fixture/scenario drivers, raw process-launch/loader
  modules or runtime module loading are rejected. Ambient Node process inputs
  and aliases are rejected; injected inputs and diagnostic stderr/exitCode remain
  legal. The TypeScript compiler owns parsing and symbol identity.
  This one policy now protects release planning, refund decisions/configuration,
  voucher protocol inputs and approval references without separate rule engines.
  Built workspace packages are their own boundary, discovered from the workspace
  manifest; their internals are not scanned. Unreachable differently named tool
  modules, Make/shell code and other languages are not implicitly classified.
  Native TypeScript analysis emits facts to the Go policy in ops/. The former
  JS policy and its npm command have been deleted. make js/execution/check uses
  a dedicated offline container and remains a prerequisite of js/tests/js/ci.
  Python checks inspect the rendered runtime grants; they do not parse TypeScript
  or repeat ownership policy. Release-specific invocations remain removed.
  Source acceptance cases live in tests/fixtures/execution-ownership and run

Go/native-analyzer cutover plan
-------------------------------
Completion contract:
  One Go owner decides common roles, allowed dependency directions, capability
  permissions and resulting findings. Native frontends report language facts;
  Make and presentation do not contain another copy of those rules. Existing
  CAM/ABI/contract semantic owners remain unchanged, as specified in note 036.

1. Establish the smallest common analysis handoff.
   Go owns source discovery and the declared analysis scope, derived from real
   workspace/source structure rather than an application enrollment list.
   A native frontend receives its assigned source inventory and reports modules,
   resolved dependency targets, resolved capability uses and source locations.
   Native mapping of a symbol such as Node process.env to an ambient-input
   capability is language knowledge. Deciding whether a core may use it is Go
   policy. Frontends do not emit allowed/forbidden decisions or rule findings.
   Role interpretation, package-boundary permission and graph traversal policy
   move to Go; do not leave them hidden in TypeScript discovery/filter helpers.

   Define only the facts consumed by the current ownership rules. Use a bounded
   versioned JSON handoff, not a general compiler IR, plugin engine or graph DSL.
   Join reports to the actual staged candidate bytes and pinned analyzer/build
   identity. Go requires coverage of the assigned inventory. Missing, stale,
   unsupported or unparsable reports block the check; an empty report is not a
   clean bill of health. Unsupported language forms remain explicit limits.
   Facts describe source; they never authorize runtime effects or transactions.

2. Move the complete CURRENT ownership policy to Go in one cutover.
   Keep the working JS checker authoritative until the integrated replacement is
   ready. Implement the Go policy and native TS facts frontend on the working
   branch, move all current decisions, and run their acceptance cases together.
   Before switching ordinary CI, delete the JS role/permission/verdict logic.
   A private comparison during development can provide evidence; it is not a
   second production authority, fallback or permanent shadow policy engine.
   Do not merge a Go pass-through that merely trusts JS violations, or a JS
   launcher plus duplicate Go/JS permission tables. No per-family policy forks.

   Evolve js/tools/execution-ownership.test.mjs into native extraction tests and
   black-box policy tests as appropriate; do not preserve its current structure
   for sunk-cost reasons. Ordinary checking enters Go, which requests native
   facts and evaluates them; the frontend does not call back into Go to select
   rules or orchestrate the check. Common policy and process/storage primitives
   live in the one ops/ Go module proposed by 036. Create packages only when this
   cutover provides their real caller. No host Go/Node/Python installation is
   assumed, no new dependencies are added merely for abstraction symmetry.

3. Keep analysis and operational runtime grants separate.
   Build the Go binary offline in a pinned builder, with source/tool inputs and
   target platform recorded. Cache reuse is keyed to those actual inputs, not a
   mutable tag or checkout HEAD alone. The checks consume a Linux binary and
   pinned native frontend through an explicit read-only artifact boundary in
   the existing secured Node posture, extended only as required for that job.
   The checker has no Docker socket, signing configuration or external network.
   Go can launch the packaged analyzer inside that container; no nested Docker.
   A native analyzer may intrinsically start a compiler backend, as the current
   TypeScript API does. It remains inside that declared analysis job's lifetime;
   Go owns job/process-group cancellation and cleanup. This is not permission
   for a frontend to add operation orchestration, nor a claim that Go individually
   observes every compiler-internal exec. Coverage must retain that distinction.
   Compile/output scratch stays bounded and container-local. Do not turn the
   standard-library Python checks image into a multi-runtime tool installation.

   The later operational host controller uses the same Go ownership model but
   has explicit process/Docker authority. That is a separate grant, not something
   the read-only checker inherits because both are Go. Additional native language
   frontends are introduced for actual rules/consumers, not installed speculatively.

4. Prove the split and retain the supported entrypoint.
   Preserve make js/execution/check as the focused operator interface while its
   implementation changes. Normal tests invoke the same common policy command.
   Policy tests feed known facts to Go; frontend tests assert extracted native
   facts, including aliases, computed properties, local shadows and re-exports.
   Put shared cross-language source/fact cases under tests/fixtures/, not inside
   one package's test exports. A same-law case in different languages must reach
   the same Go rule rather than duplicate expected policies in each frontend.

   Gate the cutover with the real current tool graph, forbidden dependency and
   ambient-input examples, a normal new role-bearing module, an unsupported
   source form, missing module coverage and a mismatched report/candidate.
   Assert the independent expected findings; do not generate expectations from
   the analyzer or policy under test. Native language parsing does not itself
   prove completeness, and policy tests do not prove the Make-to-checker wiring.
   Verify that old JS permission/verdict code and family-specific paths are gone.

5. Then use the Go execution owner for recording and operational commands.
   Implement shared process/store primitives with a real ordinary-command
   consumer, recording before new subject work and preserving existing cleanup
   and unknown-effect laws. Full workflows compose the same ordinary operations.
   Move consumers and delete displaced host orchestration together; do not keep
   a Go outer wrapper while Bash/Python still decide the same transitions.
   Preserve native TS/Solidity semantic jobs and independent approval boundaries.
   No production/Fuji effect is part of this documentation or analyzer cutover.

Current status: the complete existing JS/TS ownership policy has moved to Go.
Go discovers the source cohort, requests native facts and owns report admission,
role discovery, dependency traversal, capability permissions and findings. The
TypeScript frontend owns syntax, symbols, resolved imports and capability facts;
it emits no verdicts. Source digests, request digest, frontend digest, compiler
version and complete inventory join the report to its requested inputs.

The checker stages read-only source into container tmpfs, compiles Go offline
with a pinned SDK, runs its tests, then checks the real tool graph. This compiles
the actual staged policy rather than trusting an independently cached binary.
No host Go installation, Docker socket, operator secrets or external network is
granted. ops/format has a separate, explicit write grant to ops/ only.

Focused qualification covers the shared source cases, malformed/stale report
rejection, the real tool graph, bounded subprocess output and cancellation of a
native backend child. The overflow witness caught a promoted bytes.Buffer method
that bypassed Write; the adapter now keeps its buffer private. Rendered Compose
checks pin the checker and formatter grants. The host controller, operational
recording/recovery and additional language frontends remain unimplemented.

18. Focused acceptance and scope limits
----------------------------------------
Slice 1 needs an actual recorded fixture up/info/down sequence showing:
  requests/results/known launches and stable IDs for its declared commands;
  bounded native descriptor attachments and explicit unrecorded-output coverage;
  truthful incomplete observation after interruption or publication failure;
  no subject work if its top-level request fact cannot be published;
  cleanup remains possible when recording fails; further ordinary work stops;
  notebook retained after fixture teardown;
  no secret input/env capture or second deployment/approval state machine.

Slice 2 requires complete supported-workflow coverage at the declared boundary,
including rejected prerequisites, composed commands and bypass detection. Removing
the route through the common owner must fail a repository check. A structurally
valid route must also produce its request, governed launches and terminal or
incomplete outcome in execution tests. Questions and replay are deferred.

Slice 3 adds the streaming/PTY bounds, cap/write-failure draining and finalized
output contract from sections 7-8, at the actual existing terminal/log owner.
Do not make generic stream capture an accidental prerequisite for Slice 1.

Use the narrowest existing Docker-backed lane for publisher/reader logic and
the actual supported disposable target for the integration witness. Real PTY,
daemon and chain claims need their real bounded evidence. Do not add tests that
only mirror JSON field names, broad text checks or speculative recovery matrices.

This workshop is documentation, not that qualification. No command history
feature, HTML reader, replay, new Make target or fault adapter was implemented.
No services/fixtures were started and no operator instance was modified.

19. Deliberation and primary references
----------------------------------------
Three read-only peers independently examined capture/storage, local exploration
and mechanical/security limits. The coordinator owns this proposal. Agreements
are design input, not operational proof.

Accepted: minimum history before full replay; no transcript-to-shell execution;
normalized Make requests versus actual argv; inert discussion; native artifacts
remain authority; per-event files under a brief publisher lock; capture failures
do not grant retry permission or silently cancel in-flight effects.

Fresh independent audits corrected unsupported SESSION requests being silently
ignored, cleanup being accidentally blocked by journal failure, ambiguous sequence
ownership, and durable completion getting ahead of output finalization. The
proposal now refuses unsupported capture, preserves cleanup, leaves sequencing
with the test driver, and reports output durability honestly. Reader freshness
and first-slice versus replay acceptance were clarified as well.

A later feasibility pass narrowed initial output to the fixture owner's existing
descriptor, avoiding a new stream supervisor. It also separated mandatory public
request admission from best-effort child observations: the latter must not create
a new per-child logging permission gate inside an already-running operation.

Rejected as the default: global command tracing, a mandatory notebook shell or
outer COMMAND wrapper, a full host rewrite as prerequisite, VM checkpoints as
the first feature, and adopting an agent-evaluation framework for basic history.
