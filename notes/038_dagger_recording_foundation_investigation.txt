Dagger versus a shared Go execution owner
=========================================

Date: 2026-10-30.
Status: source/documentation investigation; no runtime qualification.
Scope: automatic structured command recording and enforced workflow coverage.
Questions, discussion, HTML presentation and replay remain deferred.

Decision
--------
Keep the proposed small Go execution owner as the foundation. Dagger provides
substantial reusable automation and observability, but the inspected versions
do not supply our required durable record-before-execution boundary. Replacing
Compose and the host lifecycle with Dagger would therefore not remove the need
for that boundary or for repository enforcement of supported entrypoints.

This is a fit assessment, not a claim that our current Go code already meets the
requirement. ops/cmd/cam-ops currently implements only the ownership check; its
process adapter supervises the native analyzer. Neither is an operational runner
or a durable command recorder. Do not turn that adapter into a host controller
by relabeling it or claiming analyzer cancellation proves deployment cleanup.

What exists, and the precise gaps
--------------------------------
1. Recording and persistence.
   Dagger has real local telemetry storage; it is not merely a Cloud dashboard.
   Released engine/clientdb/dbs.go opens telemetry databases in WAL mode with
   synchronous=OFF [R1]. Thus that store is not a durable acknowledgement on
   which to condition our next effect. This finding concerns telemetry, not a
   claim that every Dagger database has the same persistence settings.

   Newer main improves delivery: CallSpanProcessor has a separate retrying
   queue, while other spans use a bounded queue that may drop on overflow.
   OnStart snapshots and enqueues a call; it does not await disk persistence
   before returning. Session setup wires these processors separately [R2-R4].
   Larger queues, local storage and shutdown flushes do not establish our gate.
   The reviewed path lacks a durable-write acknowledgement in execution admission;
   this is a source conclusion, not a measured disk-full/crash result.

2. Structured relationships.
   Dagger's API/telemetry already represents function/exec relationships, sources
   and results. This is useful precedent. An engine withExec of a shell script
   is not evidence that every command/builtin inside it has a separate recorded
   semantic operation. Wrapping existing shell workflows would retain opaque
   internals and their existing lifecycle ownership [R5].

3. Commands with external effects and caching.
   The released function-caching documentation explicitly distinguishes function
   cache policy from execution-layer caching. cache="never" reruns the function
   but does not disable caching of withExec operations inside it [R6]. Adopting
   Dagger would require explicit execution semantics for deployments, fresh RPC
   observations and approvals. A cache hit is not evidence that a new external
   command ran, nor a recovery decision about an uncertain paid transaction.
   Dagger is not thereby unsuitable for external effects; correctness would
   remain our responsibility rather than follow automatically from its engine.

4. Interactive approval.
   Dagger offers interactive terminals [R7]; terminal support is not absent.
   Our actual boundary includes an independent approval process and signer,
   raw key input, socket readiness, detach/cancellation and bounded cleanup
   (tools/release_approval_deploy.sh). That whole handoff would need qualification
   under a changed runtime. A terminal API alone does not prove it preserves it.

5. Services, authority and lifetime.
   Dagger has useful health-checked, dependency-managed ephemeral services [R8].
   These could simplify disposable scenarios. Our persistent services and
   independently retained instance records have additional lifetime obligations.
   Compose currently declares exact mounts, network and capability grants;
   migration would have to replace and prove those grants, not run Docker inside
   an opaque Dagger command with broad engine authority. The current engine
   configuration permits rejecting insecure-root-capability requests [R9].

6. Coverage enforcement.
   Neither a Dagger invocation nor a Go executable automatically prevents a new
   Make recipe from running Docker directly. Both require the repo to enforce
   that supported workflow declarations reach the recording/execution owner.
   Derive coverage from those declarations; do not add a second workflow list.
   Native facts and Go policy can detect governed bypasses; actual supported
   invocations must prove recording. Neither approach alone provides hostile
   whole-host confinement against an operator with direct Docker access.

Comparison and implementation consequence
-----------------------------------------
Dagger adoption supplies execution graphs, caching, container services, secrets,
terminals and telemetry. It also changes the runtime and requires requalifying
our existing grants and interactive release boundary. Our durable admission and
coverage obligations would remain. Running all existing Make workflows inside
one Dagger container would not be the requested architectural replacement.

A small Go owner can retain the current scoped Compose jobs and native semantic
owners while acquiring only the demonstrated host process/store responsibilities.
It gives us no guarantee until those responsibilities are implemented and tested.
Its cost is explicit ownership of durable writes, locking, argument handling,
terminal/signals and cleanup; do not hide that work behind the word "small".

Reuse standard mechanisms: os/exec and platform process handling, filesystem
publication/sync primitives, structured serialization and trace correlation.
OpenTelemetry is suitable for interoperable observation/export, but its ordinary
batch processor permits dropped spans; it cannot be the sole execution gate
[R10]. Do not build a new container engine, cache engine or workflow language.

Next implementation and decisive proofs
---------------------------------------
- Publish a safe request before starting workflow prerequisites; preserve its
  identity across governed child launches and record terminal/unknown outcomes.
- Make recording automatic; migrate the ordinary execution owner with its
  caller and delete the displaced launch path. One fixture is a first witness,
  not completion of all-workflow coverage.
- Refuse a new operation when its initial durable write fails. Stop further
  ordinary launches after a later recording failure, while allowing owned
  cancellation/cleanup and retaining honest incomplete evidence.
- Show a real parent/child command, rejection, interruption and failed-write
  witness. Check that secrets do not enter stored inputs/arguments.
- Derive the coverage check from supported declarations. Add an ordinary target
  and an intentionally bypassing target: the former must be covered and the
  latter rejected. Execute supported routes to prove records actually appear.
- Keep process outcome separate from native verified effects. Reconciliation,
  independent signing approval and source-native verification retain their owners.

Reconsider Dagger if a pinned version demonstrates durable admission before every
governed launch, failed-write refusal, required terminal/cleanup behavior, and a
smaller complete migration of our authority grants. A dashboard, local trace file
or successful sample build alone would not establish those claims.
