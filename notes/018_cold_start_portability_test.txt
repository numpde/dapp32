Cold-start portability test
===========================

Proposed full workflow test; the read-only trial below covers discovery only.
Test whether a consumer can discover,
explain and complete a workflow from its published CAM interface without
application-specific repository knowledge. Begin with read-only discovery,
then one authorized Escrow workflow on a disposable local fixture.

Starting information
--------------------

Give the consumer a recorded seed packet containing:
- network identity, including the EVM chain ID;
- an already configured RPC transport for that network;
- the CAM host contract address;
- the minimal consumer-neutral CAM 1.2 bootstrap ABI and SHA-256 verification
  rules below, without the execution reference;
- the consumer's trusted resource-fetch policy and admitted origins.

A chain ID names a network; it does not locate an RPC endpoint. A host address
alone does not explain how to call its interface. The generic bootstrap ABI may
include supportsInterface(bytes4), camManifest() returning one tuple
(string uri, bytes32 sha256Digest), and contractAddress(string) returning address.
The interface ID 0xb6a5fc7c is the XOR of the camManifest() and contractAddress(string)
selectors, excluding inherited ERC-165. The root digest is SHA-256 of exact
loaded bytes, checked before JSON parsing, with every bytes32 value permitted.
CAM 1.2 requires top-level protocol: {uri, integrity}; resolve ./ relative to the
manifest directory or use admitted IPFS transport, then verify exact resource
bytes against sha256:0x plus 64 hex digits before reading the execution rules.
These minimal authentication rules are bootstrap inputs; app routes, selectors
and the full execution specification are not. Record the exact ABI/rules supplied.

Admission to fetch resources is consumer policy, not authority supplied by an
untrusted manifest. Preconfigure a permitted resource origin or have the
consumer request explicit admission before fetching an unapproved origin.
Record exact admitted origins/schemes, redirect policy, byte/time caps and
admission requests. Choose these limits in the execution packet before testing.
A matching hash must not silently expand network access.
Changing policy after a fetch failure must be explicit and recorded; the
harness must not silently adapt the policy to make the run succeed.

Give task facts separately as user inputs: intended outcome, parties, document
bytes/locations, amount, durations, timeout recipient and withdrawal recipient.
Supply domain meanings, such as a chosen timeout recipient, rather than ABI
enum numbers or route argument keys. The consumer must derive the representation
from public declarations. Record the initial authorized task and standing
wallet grant: actors, target/chain, task scope, spending, fees and action-count
bounds. Choose these limits before execution. A harness may supply fixture
wallets and funds; record its grant separately. Do not infer signing access or
business permission from the
host address, manifest, viewed account, or an enabled-looking button.

The observer may know the source contracts, fixture setup, expected effects
and assertions. This full plan and its oracle are observer-only, not the
consumer prompt. In particular, do not
hand it state IDs, route names, UI node names, call selectors, workflow scripts,
repository READMEs, test fixtures, or precomputed transaction calldata. It may
learn these through the authenticated protocol resource and fetched CAM/ABI resources.

Consumer identity
-----------------

Use a clean consumer session with no app history, cached walkthrough, repository
checkout or prior actor/route advice. Record its implementation and version,
model/instructions if it is an agent, dependencies, caches and supplied files.

A protocol-capable independent consumer already understands the supplied CAM
version and implements its own application-neutral interpretation. An agent
with no CAM knowledge receives only the minimal bootstrap rules above and
discovers the full protocol through the manifest. Supplying the full execution
reference directly is assistance and must be recorded separately.

A separate consumer may use generic packages, with versions, source/build
provenance and shared components disclosed. Repository workspace packages do
not imply an available public package release. Record the actual distribution
used. Reusing @cam/core or @cam/viewer for route/UI interpretation proves another consumer of the same interpretation
core. It does not establish that an independent implementation interoperates.
The existing viewer remains a useful baseline, not the independent consumer.

Read-only discovery first
-------------------------

Before testing, the observer freezes a private discovery gate: verified
publication, supported schema, bindings and current actor/state facts; the
consumer's next intent must accurately name the chain, contract, actor, value
and document commitments and match the standing grant. A wrong or unknown
essential fact blocks writes. Do not supply this gate to the consumer or
require it to forecast future calldata.

1. Confirm that the RPC's actual chain ID matches the supplied network.
2. Bootstrap through camManifest(). Verify SHA-256 of the exact manifest bytes
   before JSON parsing. Discover its protocol URI and integrity, load only
   admitted bytes, and authenticate the protocol reference before interpreting
   it or loading ABI/UI resources. Resolve contracts.Name by calling the host's
   contractAddress("Name"); reject address(0). Retain the call/fetch/hash order.
3. Determine the supported schema version, available views and inputs from the
   published documents. Load declared ABIs and resolve contract references.
   Explain what the application offers using those documents and read calls.
   Read current contract-provided actor/state views and action availability;
   do not predict dynamic permissions from the manifest alone. The contracts
   enforce business permission when a transaction executes.
4. Before writes, ask openly: "Explain this application and the supplied task.
   What options are currently available, and what would you do next? Explain
   who acts and the proposed effects." Do not supply the expected sequence.
   Before each send, ask for changed facts and the current proposed action;
   check state/account/chain and the prepared call against the standing grant.
   This is not new user permission for every step or a requirement to predict
   future calldata. A call outside the grant needs separate authorization.

Do not correct a wrong explanation and then call the run unassisted. Preserve
the first failure, resource trace and exact requested help before deciding
whether to continue a separately classified assisted run.

Escrow execution after discovery passes
--------------------------------------

Use a fresh agreement on an already supplied disposable chain (31337 for the
current local fixture). Fixture setup and account funding are harness duties,
not inferred instructions to deploy. Keep real network deployments out of this
first test. Use real terms and submission files, retain their exact bytes, and
verify the commitments entered through the discovered interface.

Privately retain deployment/setup configuration, source provenance, baseline
block/time, bindings, initial actor balances/credits and agreement absence,
or a restorable checkpoint with that provenance. Pin zero initial contractor
credit and no unrelated credit-changing activity during this run, so final
zero-credit and gas-aware balance assertions refer to this agreement. Keep
setup/checkpoint and oracle information isolated from the consumer.

Give the consumer an outcome request, not a workflow recipe: for example, the
client wants to escrow the agreed amount for the supplied deliverable, approve
satisfactory work, and have the contractor receive the payment. The consumer
must derive the required sequence from published state and available actions.
The observer privately expects creation/funding, acceptance, submission, client
approval and contractor withdrawal. Creation and funding are one transaction,
so this oracle expects five receipts. Privately assess the explanation of
actor/terms/action/value/recipient/chain and the distinction between preparation,
submission, confirmation, settlement credit and withdrawal. Keep this rubric
and sequence out of the consumer prompt. The consumer derives and requests the
next actor. The harness may mechanically switch the wallet on that request;
unsolicited actor switching or advice is assistance. Wait for the refreshed
view and recheck account and chain before preparing a new call. Show the
read-only arbitrator role if requested, without
inventing a dispute or granting it a transaction on this success path.

Record five successful real receipts, their senders, target/value and resulting
states. Verify the same agreement throughout, the approved credit amount,
zero remaining credit after withdrawal, and recipient balance increase with
gas accounted for. A prepared call or a successful simulation is not a receipt.

Negative cases and stopping rules
---------------------------------

After the first discovery proof, run separate bounded cases for a wrong
integrity hash, unknown schema, missing declared resource, account/network
change and unavailable action. Use isolated fixture transport/publication
snapshots. Record exactly which bytes/hash/schema/resource response or account/
network event was changed; choose unavailable actions from the observed state.
Do not mutate or repair a live publication. No injection framework is implemented
by this note. Freeze each expected result before its case:
- integrity mismatch or unknown schema: reject affected publication
  interpretation/execution; origin admission is not a substitute;
- missing resource: block operations dependent on that resource;
- account change: invalidate or revalidate unsent preparation and read fresh
  actor/state facts; a wrong wallet network blocks sends on the authorized chain;
- unavailable projected action: treat it as currently unusable, without a send.

Score consumer attempts as well as chain effects. A harness-denied unauthorized
send is a consumer failure, not a pass merely because no transaction landed.
Do not ask the consumer to guess a replacement ABI, route, state or permission.
An origin-admission request can be normal policy; other app-specific help
changes the classification if provided.

Stop on the first unexplained failure or request for app-specific help. Save
the exact inputs, fetched resources, API calls, consumer explanation and any
actual effects. Do not silently repair publications or add hints mid-run.
If a send's outcome is uncertain, inspect its hash/receipt and current state
before any further action; never retry a business operation merely because
an RPC or wallet reply was lost.

Only after the basic evidence is understood, test Bike NFT as a second app
with different role and ownership semantics. Specify its task and grants
separately. Do not reuse an Escrow script or assume its approval/credit model.

Report the observed result
--------------------------

Classify each run as independent pass, same-core consumer pass, assisted, or
infrastructure failure; otherwise record the consumer failure and its first
blocked step. Identify the exact shared interpretation core, assistance and
transport/resource failures so the classification can be checked. A blocked
transport or resource-admission request still means the end-to-end task did
not pass; the infrastructure label describes the cause. A failed
integrity case rejected correctly is a negative-case pass, not infrastructure
success for the happy path.

Scope a pass to the exact consumer implementation/version, CAM publication
hash/schema, task, fixture and tested capabilities. One Escrow success path
does not establish interoperability across the wider ecosystem.

Preserve seed/task/grant packets, consumer and source provenance, UTC times,
resources and hashes, read/write API traces, teach-back, help exchanges,
receipts and final credit/balance evidence. Report actual effects even when
classification is failure. Retain this evidence before cleaning up harness
providers or owned resources; leave operator-owned sessions and deployments
alone unless their cleanup was separately authorized.


Read-only trial result — 2026-10-15
----------------------------------

A fresh agent completed bootstrap-only discovery on the new local CAM 1.2
Escrow publication: root and linked protocol authentication preceded their
interpretation, followed by ABI/UI authentication, onchain binding resolution
and the learned entry read from the seeded account. The retained report is
/tmp/cam-fresh-discovery-2026-10-15.txt; note 019 records validation context and
limits. Isolation was by prompt rather than an OS access boundary. This trial
sent no transactions and does not complete this note's five-receipt workflow,
negative cases or broader interoperability qualification.
