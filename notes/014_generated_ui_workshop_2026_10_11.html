Generated Escrow UI workshop

Date: 2026-10-11. Baseline: 9387315.

The central problem is unclear separation of the user's task, contract facts, wallet capabilities and renderer diagnostics. Users should immediately know what they are doing, which agreement and account it concerns, what they can do now, and what pressing a button will do. Start with meaning and state; extend presentation vocabulary only for demonstrated missing capabilities. This is a researched proposal, not an implemented change.

Observed experience

The local Chromium walkthrough found a creation page approximately 1,817 pixels tall on desktop and 2,181 on mobile. Opening an existing agreement and creating a new one share the same undifferentiated surface. A funded agreement offering only an acceptance-timeout action still shows all four submission/dispute inputs; its action appears around 2,000 pixels down the page. Prepared review presents nested arguments as a JSON wall on mobile. Captured screenshots and reports provide temporary local evidence.

Source inspection explains these findings:

  • dapps/escrow/cam/ui.json puts technical limits before creation inputs and renders both evidence forms independently of available transitions.
  • Screen and Fragment flatten their children. There are no section, disclosure, associated hint, or closed-choice primitives.
  • prepared-call.ts displays execution fields without a human decision summary.
  • The inline fieldset padding of zero overrides .elements padding of 16px.

Persistent labels, exact integer strings, Back, Discard, focus arrival and tested overflow handling already work. Preserve them. The walkthrough does not establish screen-reader usability or real wallet-extension approval behavior.

Urgent findings from the additional review

An independent screenshot-only reviewer identified the four-way separation above. Source inspection supports the task and identity concerns: the shell displays the internal route, the shared screen says “Contract-projected escrow workflow”, and “Open agreement” precedes creation content. Give the current task a human title and make “View existing agreement” a distinct secondary task. Put route IDs, resource provenance and raw exceptions in labelled technical details, while keeping operational failures visible.

Distinguish the address being viewed as, an agreement's assigned parties, and the wallet account available to sign. Creation's “Client” is the address supplied to the projection, not proof that a wallet controls it. Explain which reads and draft preparation remain possible without a wallet, and which submissions require one. “Unavailable” currently means no injected provider was detected; avoid duplicate unexplained warnings or a connection control that cannot work. Here the host is CamRoot, the CAM publisher and address resolver, distinct from the escrow contract. Use verified configuration for network and native-asset names; the current wallet metadata's hardcoded ETH/18 decimals is not proof of an arbitrary chain's asset.

Agreement-ID correction belongs beside “Agreement ID”, not solely in an ABI diagnostic above the whole view. Propose “Enter an agreement ID” for empty submission, and “Enter an agreement ID beginning with 0x, followed by 64 hexadecimal characters” for malformed input. Provide persistent format help, associated corrective text and an invalid state; preserve the exact entered value without padding or truncating it. A valid ID with no stored agreement and a failed network request are different outcomes. The screenshot does not establish that the exception occurred on initial render. Solidity fixed-size bytes, W3C error identification, W3C corrective suggestions

Group general contract limits separately from agreement-specific facts, and distinguish permitted beneficiary options from the selected beneficiary. Put creation limits beside the relevant inputs; put consequential rules ahead of incidental limits. Explain the contract-scoped agreement ID versus the client-supplied, client-scoped agreement reference: the ID is derived from the client address and reference, not interchangeable with that text. Offer the existing client/reference lookup as an alternative entry path. Keep byte limits as UTF-8 byte limits, not character counts. An exact duration may show “365 days” alongside “31,536,000 seconds”, without implying a calendar year. Solidity string encoding

The weak input boundary deserves a targeted contrast check. The current CSS uses a #d8e0ea border and #fbfcfe fill; the reviewer's approximately 1.33:1 border-to-white ratio agrees with the declared colors. Verify computed active, focus and invalid styles and adjacent backgrounds. Recommended task model

Creation should group People, Payment, Timing, Terms, with a separate existing-agreement entry. Keep one editable form initially rather than adding a wizard. Hints explain units, accepted formats, and the timeout beneficiary. Do not make zero addresses and zero durations look like suggested valid values.

Explain arbitration precisely: V1 has no on-chain arbitrator acknowledgement or acceptance step at any phase. Contractor acceptance therefore does not establish that the arbitrator has agreed to act. The existing “before the contractor accepts” wording can incorrectly suggest a later acknowledgement step. This belongs near the arbitrator choice as a consequential rule.

An agreement should lead with its identity, current state, viewer role, amount, deadline and available actions. Contractor submission owns submission inputs; client dispute owns dispute inputs. Arbitration presents both evidence sets and the beneficiary decision. CamEscrow owns business permissions; CamEscrowUI maps its available actions into transition IDs. The manifest uses that projection; writes remain enforced by CamEscrow against the actual sender.

Terminal states explain credit allocation, not viewer withdrawal eligibility. Account-credit navigation is a read; withdrawal appears only when projected for the viewed account. Approval creates beneficiary credit, not immediate wallet payment. Withdrawal transfers complete accumulated account credit, potentially from several agreements.

Review keeps prepared chain, sender, destination, attached native value, action and exact arguments visible and bound to the prepared call, never later draft values or publisher prose. Zero attached value does not imply no internal transfer or credit. Publisher prose is untrusted explanation. Do not hardcode Escrow or token-function semantics in the generic renderer. Human amount, duration, date or enum formatting needs declared metadata and exact strings. Document URIs stay inert unless validated against allowed HTTP(S) schemes. Neither URI nor digest proves safe navigation or fetched, verified contents. Simulation does not guarantee later execution.

The first bounded composition fix remains grouping each submission/dispute input pair with its corresponding action, using existing Fragment and Include primitives. The new priorities describe the release requirements, not a reason to build a new form engine before that fix.

Additional state tests should cover a ready first render with an empty ID, empty/malformed submission, pending and repeated lookup, absent agreement, transport/projection failure, and older responses arriving after newer requests. Require title, selected context and body to remain coherent after failed navigation; preserve Back recovery when reconciling wallet/network changes. These are proof obligations, not claims that every case fails today.

Current tests already cover a valid absent-ID result, Back draft recovery, failed-navigation consistency and atomic account changes. Preserve those guarantees. Focus arrival and alert/status roles also exist; field association and scoped presentation need improvement, rather than a second feedback system.

Check keyboard activation and focus recovery, label/hint/error associations, scoped pending announcements, full-value address/ID access and copy feedback, and ordinary form reflow at an effective width of 320 CSS pixels. Existing focus and overflow tests are partial proof; new status feedback should not repeatedly interrupt typing. W3C status messages, W3C reflow

Document presentation tests must reject unsafe navigation schemes and claims that an unverified document has been verified.

Browser proof should include pointer and keyboard use, repeated actions, pending states and nearby interactions that must not trigger effects. Static ordering checks do not prove comprehension. Ask an independent reader to explain who can act, what funds move, and what remains pending.

Generation pitfalls to gate

Avoid attractive cards around the same flat inventory; frontend role/state permission mirrors; floating-point financial formatting; hidden essential facts; unattributed manifest claims; new wizard state loss; and tests coupled to exact labels instead of task laws. Keep the contract authoritative and the frontend untrusted. Preserve the architecture stop signs: no viewer/session or ABI decomposition, new UI framework, Solidity change, or CAM hash change is required by this workshop.
