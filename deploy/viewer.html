Deploy the stand-alone viewer ​

Two hosted versions are available: the stand-alone viewer, deployed independently, and the Pages preview, built from recent reviewed source and updated ahead of the stand-alone release. The preview is for early testing and may change sooner; inspect all contract details before authorizing transactions. Each origin requires its own wallet permission and browser-accessible RPC/resources.

The Pages preview is published automatically from qualified main builds. CI records its source revision, qualification run and exact built file hashes, then independently checks the published and HTTPS-served bytes. See Published-site integrity and drift. Those checks cover the Pages preview only; they do not deploy or monitor your independently hosted viewer.

Serve the generic browser application at your own HTTPS hostname. This hosts viewer software only: no blockchain, CAM bundle, contract deployment, wallet or private instance directory is created.

Run on
The Linux server, as its non-root Docker operator. Use that server's local Docker context, not a remote workstation context.
Requires
Git, Make, Bash, Python 3, Docker with Compose and Buildx; the kernel setting net.mptcp.enabled; a hostname you control; host-side Caddy for the HTTPS example.
Changes
A local image, a viewer container/network and the hostname's proxy configuration.
Success
The HTTPS health endpoint responds, the viewer setup page loads, and a known compatible app opens through a browser-readable RPC.

1. Build a known source revision

Clone the repository on the server and check out the reviewed commit you intend to serve. Use a clean checkout so the revision identifies its actual content. In that checkout, set the context and acquire the exact base images named by its Dockerfiles:

CTX=your-local-context &&
test "$(git rev-parse --show-toplevel)" = "$PWD" &&
test -z "$(git status --porcelain)" &&
make base-images/pull DOCKER_CONTEXT="$CTX" \
  DOCKERFILES="containers/node-deps/Dockerfile containers/https-egress-proxy/Dockerfile containers/viewer/Dockerfile" &&
make js/deps/install DOCKER_CONTEXT="$CTX" &&
REV=$(git rev-parse --short=12 HEAD) &&
IMAGE="cam-viewer:$REV" &&
make viewer/image/build DOCKER_CONTEXT="$CTX" VIEWER_IMAGE="$IMAGE"

Replace your-local-context with a local entry from docker context ls. Image acquisition and locked dependency installation are the networked preparation steps. The viewer builder then runs offline. It does not publish the image or install missing dependencies implicitly. Solidity dependencies are not needed just to build the viewer.

base-images/pull requires host Python 3 (standard library only) and Docker Buildx. Without DOCKERFILES, it discovers all Dockerfiles under containers/. Docker's native --call=targets,format=json parser identifies the stages without running build instructions; BuildKit may acquire a declared syntax frontend during discovery. The command checks all returned bases for literal digest pins before pulling each distinct external image once. Earlier stages and scratch need no pull; unresolved variables and explicit stage platforms are rejected. Package downloads remain separate.

Downloaded bases stay in the selected Docker engine's cache. Other builds can use the same images, so acquisition does not delete images or containers. Resource cleanup belongs to the command that owns those resources.

2. Start it on loopback

Continue in the same shell. Record the resulting image ID for updates and rollback, then start the existing runtime:

docker --context "$CTX" image inspect "$IMAGE" --format '{{.Id}}' &&
make viewer/up DOCKER_CONTEXT="$CTX" \
  VIEWER_IMAGE="$IMAGE" VIEWER_COMPOSE_PROJECT_NAME=cam-viewer \
  VIEWER_BIND_HOST=127.0.0.1 VIEWER_PORT=8080 &&
curl --fail --show-error http://127.0.0.1:8080/healthz &&
make viewer/status DOCKER_CONTEXT="$CTX" VIEWER_IMAGE="$IMAGE" VIEWER_COMPOSE_PROJECT_NAME=cam-viewer

The service runs in the background with restart: unless-stopped, a read-only filesystem, resource limits and its own health check. Ensure the selected Docker engine starts at server boot too; for a rootless engine this is an operator service configuration, not something the Compose restart policy establishes.

Only loopback port 8080 is exposed by this recipe. viewer/up neither builds nor pulls an image. Do not prune the previous working image while testing a replacement.

3. Put the hostname in front of it

This example assumes Caddy is installed as a host systemd service, not in another container. Follow its official installation instructions for your distribution. Point your hostname's A/AAAA records at this server and allow inbound TCP 80 and 443 to Caddy. Keep 8080 private.

Add this site block to /etc/caddy/Caddyfile, replacing the example hostname. Preserve any existing sites in that file:

viewer.example.org {
    reverse_proxy 127.0.0.1:8080
}
sudo caddy validate --config /etc/caddy/Caddyfile &&
sudo systemctl enable --now caddy &&
sudo systemctl reload caddy &&
curl --fail --show-error https://viewer.example.org/healthz

Replace the hostname in the last command too. Caddy obtains and renews a public certificate when its DNS, port and persistent-storage requirements are met. The repository does not manage Caddy or DNS. See the upstream reverse-proxy recipe, HTTPS prerequisites and service management.

4. Open a real application

Visit your HTTPS hostname in your local browser. In Open a contract app, choose the network, enter the trusted CAM host address, and select a browser-accessible RPC. The viewing address is optional for a public view; connect a signing wallet separately when needed.

The host discovers the CAM bundle and bound business contracts. The viewer server does not proxy these resource or RPC requests by default: your browser must be able to reach them through HTTPS and the necessary CORS policy. Never place a private signing RPC credential or key in a shared link.

Verify the chain, host, loaded resources and a known read. A healthy web container proves only that the viewer is served; it does not prove an app is authentic, compatible, funded or ready for transactions. Investigate integrity warnings before signing.

Update, roll back and stop

Build the new reviewed revision under a new image tag using step 1. Repeat viewer/up with that new VIEWER_IMAGE and the same project, bind address and port. Check health and reopen the app. A container replacement may briefly interrupt service; this is not a zero-downtime deployment procedure.

To roll back, repeat that same startup command with the retained previous image tag or image ID. A viewer rollback does not roll back contracts, CAM publication or transactions. In a new shell, set CTX and the chosen IMAGE again before using these commands.

make viewer/down DOCKER_CONTEXT="$CTX" VIEWER_IMAGE="$IMAGE" VIEWER_COMPOSE_PROJECT_NAME=cam-viewer

Stopping removes this viewer's runtime, not its images or on-chain state. Remove its Caddy site block and reload Caddy when retiring the hostname; do not stop a shared proxy serving other sites.

Automatic updates from a deployment branch

make viewer/update performs one foreground attempt against origin/deploy/viewer. Publish changes to main first, then advance deploy/viewer to a commit already contained in main. Advancing that branch authorizes a release. The updater fetches both branches and refuses a deployment commit outside main before changing the checkout or runtime. It requires host Python 3 (standard library only), flock, timeout, an existing viewer built with viewer-owned revision labels, a clean deployment checkout and the same Docker context/project/bind settings as the running service. It builds on the server using the acquisition, locked dependency and offline image-build commands above.

make viewer/update DOCKER_CONTEXT=your-local-context \
  VIEWER_COMPOSE_PROJECT_NAME=cam-viewer \
  VIEWER_BIND_HOST=127.0.0.1 VIEWER_PORT=8080 \
  VIEWER_PUBLIC_ORIGIN=https://viewer.example.org

The target fetches the branch, selects its exact commit and compares it with the running container's immutable image and labels. Historical source without the updater is rejected before checkout, preserving the controller when selecting such releases. A healthy matching release needs no build. The checkout follows the selected commit even on that path. A replacement must reach container health and expose its full source revision in the public entry bundle. This observes the served revision; it does not prove publication integrity of every asset.

There are no deployment receipts, SHA files, settings snapshots or release directories. Docker tags cam-viewer-<project>:current and :rollback retain the current and previous working images. An empty lock under $XDG_RUNTIME_DIR serializes attempts; it is runtime synchronization, not deployment history. Temporary build inputs are removed by their creating commands. Compose retires generated dependency/compiler images; the updater removes obsolete images in its own namespace with matching viewer/project/source labels, preserving container references and other tags. Shared upstream bases remain cached.

Dependency or build failure leaves the service unchanged. Activation or public-revision failure attempts rollback and still returns failure. Unconfirmed rollback preserves recovery images. Cleanup failure reports failure without rolling back an accepted healthy release. Abrupt host failure or an uncatchable kill can require manual recovery.

Automatic updates refuse changes to compose/viewer.yml or the existing bind/port settings: migrate the runtime explicitly with viewer/up. A retained rollback used to recover an unhealthy viewer must also have clean viewer-owned identity and a compatible runtime model. Historical images with inherited nginx revision labels require an initial manual build/up migration; they are not admitted as automatically identified viewer releases.

The checked-in tools/systemd/cam-viewer-update.service and .timer are examples. Configure the service's working directory, Docker context, project, bind address, port and public origin in the host-local copy before installing it. Keep host account names, private listeners and full operator paths out of the repository. Preserve existing checkouts and installed production settings when updating the example. After one successful manual attempt, install the configured units into ~/.config/systemd/user/, run systemctl --user daemon-reload and systemctl --user enable --now cam-viewer-update.timer. User lingering and the Docker user service must be enabled for operation after logout and reboot.

The timer runs one minute after completion; overlapping manual attempts fail the same lock. The complete attempt has a twenty-minute deadline with bounded cancellation/recovery grace. View status with systemctl --user status cam-viewer-update.timer cam-viewer-update.service and logs with journalctl --user -u cam-viewer-update.service -n 100 --no-pager. A failed attempt retries at the next timer activation. Stop the timer before manual rollback, otherwise the next attempt will reapply the branch. Use viewer/up with the retained :rollback image and the same runtime settings; restart the timer after correcting or moving the branch.

On a dedicated builder, configure an appropriately small native BuildKit garbage-collection budget. The updater does not change shared engine policy or run engine-wide prune. Container logs are already rotated by the runtime; bound journal storage through the host's existing journal configuration.

SymptomNext check
Required local base image missingRepeat explicit acquisition for the Dockerfiles at your selected revision and context.
Container fails before healthCheck the image exists on that engine, port ownership, and the kernel's per-namespace MPTCP setting. Do not remove confinement to hide the failure.
Loopback health works; HTTPS failsCheck DNS, firewall, Caddy configuration and journalctl -u caddy.
