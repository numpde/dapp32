One workflow for people and agents

dapp32 lets an app author describe screens, inputs, contract calls and their next steps in JSON, using the Contract Application Manifest (CAM) format. A deployed contract publishes where to find that description and its hash. Given the chain and that contract’s address, the dapp32 viewer can load the workflow and render its screens; a TypeScript library lets apps and agents inspect the same workflow and prepare contract calls without a browser. You write the app-specific workflow; dapp32 supplies the reusable viewer and library.

Why not just build a website?

An ABI describes callable functions. A CAM workflow also declares which inputs a screen collects, how an action uses those inputs in a contract call, and what follows the call. Another compatible viewer or agent can discover that description from the contract, without opening the app’s website.

A custom website can provide all of this. dapp32 lets you reuse its form rendering, contract-call preparation and workflow navigation instead of implementing them for each app. You still design the workflow; dapp32 does not infer an application from an ABI. Use the generic viewer when its controls fit, or build a custom interface for a different experience or service integration. A custom interface can also use the TypeScript library.

Approach

Contract-anchored manifests

A host contract publishes the manifest's location and hash. The manifest also records hashes for its ABI and UI resources, so the viewer can check that it loaded the expected bytes. The app's screens, reads, and actions live in reviewable manifest data instead of a custom frontend codebase.

Routes before rendering

A route names a contract call and its follow-up view. Read routes supply values to the UI. Write routes prepare transaction arguments for simulation and wallet review; preparation does not send a transaction.

Small UI model

The UI resource describes portable nodes such as text, fields, addresses, status rows, NFT references, includes, and actions. The viewer renders these nodes as controls. Apps and agents can inspect the resolved screens and action descriptions through the TypeScript library.

Current evidence

  • Bike NFT, native-asset escrow and Pay-to-Play have local real-RPC fixtures, CAM bundles, and generic viewer workflows.
  • Runtime packages load the host contract's publication, verify resources, resolve contract names to addresses, read routes, and prepare writes.
  • @cam/viewer tracks the current workflow view and prepares actions through a library that a terminal, web app, wallet, or agent can drive.
  • @cam/conformance catches authoring errors across manifests, ABI usage, resources, routes, UI, and typeflow.
  • The React viewer is deliberately thin: DOM and wallet interaction stay outside the protocol packages.
  • A generic integration-fuzz runner walks deployed CAM hosts to catch workflow failures that static checks miss.

Local demo

Use a demo to explore an app’s workflow or manually test changes to its contracts, CAM bundle and viewer together. Each launcher starts its own disposable blockchain and fresh app contracts, serves the CAM resources, and prints a local viewer URL. See what the demo launchers do, or follow the Bike NFT, Escrow or Pay-to-Play instructions. Docker, Compose and Make are required; install the locked dependencies before launching a demo.

Each demo attempts cleanup when its foreground command exits. Closing the browser tab does not stop the GUI. Successful cleanup removes the fixture state. If interruption or cleanup failure leaves a demo running, use make bike-nft/local/demo/gui/down or make escrow/local/demo/gui/down or make pay-to-play/local/demo/gui/down for the matching demo, then check that it has stopped. 

git clone https://github.com/numpde/dapp32.git
cd dapp32
make dapps/deps/install
make js/deps/install
make cam/conformance/check
make bike-nft/local/demo/gui/up
# open the printed http://127.0.0.1:5173/... URL

What is in the repo

Protocol packages

@cam/protocol, @cam/core, @cam/screen, @cam/evm-viem, @cam/viewer, and @cam/conformance parse, validate, resolve, and test CAM bundles.

Reference app

cam-web is a thin renderer around the headless viewer. The browser owns DOM and wallet interaction; protocol logic stays in reusable packages.
