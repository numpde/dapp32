A contract points to its workflow

dapp32 lets an Ethereum contract publish the location and hash of a CAM manifest: a JSON workflow document stored outside the blockchain. It describes the dapp's screens, contract reads, inputs, and wallet actions. A graphical viewer lets people follow the workflow; a TypeScript library lets apps or agents drive it without a graphical interface. Developers can run the open dapp32 viewer, embed it, or use a hosted viewer they trust instead of building a whole custom frontend.

Current CAM workflow

1
Host contract

Publishes the manifest's location (camURI) and byte hash (camHash).

2
main.json

Names contracts and resources, defines read/write routes, and says what to show after each call.

3
ui.json

Defines named screens, display elements, fields, and buttons.

4
Generic viewer

Loads, validates, renders, simulates, and hands writes to a wallet.

Why this matters

Smart contracts enforce dapp rules, but the workflow a human or agent follows is usually encoded in a custom website: what to display, what to collect from the user, what a button does, and what should happen after a transaction. Every team rebuilds that UI layer even when the contract already knows the relevant state and permissions.

dapp32 puts that workflow description in a manifest referenced by the contract. A generic viewer validates the manifest and renders its UI. The same workflow is available through the TypeScript CamViewerSession library for an app or agent to drive. This library interface does not provide an HTTP service.

Approach

Contract-anchored manifests

A host contract publishes the manifest's location and hash. The manifest also records hashes for its ABI and UI resources, so the viewer can check that it loaded the expected bytes. The app's screens, reads, and actions live in reviewable manifest data instead of a custom frontend codebase.

Routes before rendering

A route names a contract call and its follow-up view. Read routes supply values to the UI. Write routes prepare transaction arguments for simulation and wallet review; preparation does not send a transaction.

Small UI model

The UI resource describes portable nodes such as text, fields, addresses, status rows, NFT references, includes, and actions. Those nodes can become graphical controls or a minimal machine interface, not an app-specific runtime every project must rebuild.

Current evidence

  • Bike NFT and native-asset escrow both have local real-RPC fixtures, CAM bundles, and generic viewer workflows.
  • Runtime packages load the host contract's publication, verify resources, resolve contract names to addresses, read routes, and prepare writes.
  • @cam/viewer tracks the current workflow view and prepares actions through a library that a terminal, web app, wallet, or agent can drive.
  • @cam/conformance catches authoring errors across manifests, ABI usage, resources, routes, UI, and typeflow.
  • The React viewer is deliberately thin: DOM and wallet interaction stay outside the protocol packages.
  • A generic integration-fuzz runner walks deployed CAM hosts to catch workflow failures that static checks miss.

Local demo

The current path is Docker-backed through the Makefile. Dependency installation is explicit and may take time. Choose Bike NFT below or follow the escrow guide. Each GUI target starts a local Anvil chain, deploys its app fixture, serves CAM resources, and launches the React viewer through a local gateway. The target prints the URL to open in your browser.

Each demo attempts cleanup when its foreground command exits. Closing the browser tab does not stop the GUI. Successful cleanup removes the fixture state. If interruption or cleanup failure leaves a demo running, use make bike-nft/local/demo/gui/down or make escrow/local/demo/gui/down for the matching demo, then check that it has stopped. 

git clone https://github.com/numpde/dapp32.git
cd dapp32
make dapps/deps/install
make js/deps/install
make cam/conformance/check
make bike-nft/local/demo/gui/up
# open the printed http://127.0.0.1:5173/... URL

What is in the repo

Protocol packages

@cam/protocol, @cam/core, @cam/screen, @cam/evm-viem, @cam/viewer, and @cam/conformance parse, validate, resolve, and test CAM bundles.

Reference app

cam-web is a thin renderer around the headless viewer. The browser owns DOM and wallet interaction; protocol logic stays in reusable packages.

Example dapps

dapps/bike-nft exercises registration, lookup, metadata updates, a missing report lifecycle, retirement, local deployment, and CAM UI projection. Escrow adds funding, timed work review, arbitration, and separate credit withdrawal.

Build on the current model

Escrow uses CAM 1.1.0; Bike NFT uses CAM 1.0.0. Both use UI 1.0.0. Read the authoring guide to connect a host, manifest, ABI resources, routes, and a declarative UI.

Start with the existing examples and validation lanes. A manifest describes the workflow; the onchain contracts enforce permissions, amounts, and deadlines.
