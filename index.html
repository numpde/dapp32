What is dapp32? ​

A typical dapp32 application has these components:

ComponentOn-chainApp-specificResponsibility
Business contractsYesYesBusiness logic, state, permissions, and transactions
Contract Application Manifest (CAM)NoYesDescribe workflows, contract interactions, views, forms, and actions
CAM root contractYesYesPoint to the CAM and resolve contracts by name
Standard viewerNoNoRead contract state, interpret and render the CAM, prepare transactions
UI projection (optional)YesYesAssemble contract state into useful information

Important distinctions

The CAM is a standardized description of contract workflows that positions itself between low-level on-chain operations and custom frontends. It can be read by both autonomous agents and the standard viewer (implemented in this repo), and allows developers to build and ship faster by providing functionality without the overhead of a custom frontend. It consists of off-chain files, including:

  • main.json: describes workflows, routes, and contract reads and writes;
  • ui.json: contains forms, screens, controls, and presentation definitions;
  • ABI and protocol resources: the interfaces and conventions needed to interpret those operations.

The CAM root contract is a publication and discovery mechanism. It identifies the on-chain contracts by name and publishes the location and digest of the off-chain CAM.

The viewer is not specific to the application. It is a standard frontend-only application that can be self-hosted or not.

How they fit together

Opening an application:
Viewer → CAM root → CAM → contract reads → rendered interface.

Executing an action:
Interface → prepared transaction → wallet approval → business contract.

The business contracts remain authoritative throughout.

This repository demonstrates this approach end to end with three applications:

  • Pay-to-Play as a blockchain payment system with cumulative voucher collection;
  • An Escrow service;
  • A Bike NFT on-chain registration database for bicycle components.
