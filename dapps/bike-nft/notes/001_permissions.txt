# Bicycle Registry V1 Permissions

This note describes the current fresh-contract implementation and checked-in
CAM 1.3.0 publication. See `002_owner_workflow_test_contract.md` for workflow
qualification boundaries and the README for deployment and handoff policy.
Previously deployed irreversible `Retired` records retain their original
meaning; these workflows do not migrate them or introduce recovery authority.

## Authority boundaries

- `CamRoot` is the app entry point and CAM/address resolver.
- `BicycleComponents` is a non-upgradeable ERC-721 collection with role-gated
  minting and token metadata updates.
- `BicycleComponentManager` owns registry records, reports and delegation policy.
- `BicycleComponentManagerUI` is read-only: it selects CAM views/actions and
  aggregates data. It has no privileged role or write authority.
- Registrars create records; their role grants no continuing owner authority.
  Administrators have no fallback inside owner/delegate permission checks.
- The calling account is the actor. Sponsorship, relayers, paymasters, bundlers
  and frontends confer no registry authority. A viewed account is not a signer.
- Standard ERC-721 ownership and approvals govern direct token transfers.
  Missing reports and inactivity are registry facts, not transfer locks.

## Administration

| Contract | Admin model | Scope |
| --- | --- | --- |
| `CamRoot` | `Ownable2Step` | Owner updates CAM URI/hash and contract address bindings; ownership transfer requires acceptance. |
| `BicycleComponents` | `AccessControlDefaultAdminRules` | Delayed default-admin handoff; ordinary operational roles are separate. |
| `BicycleComponentManager` | `AccessControlDefaultAdminRules` | Delayed default-admin handoff; ordinary operational roles are separate. |
| `BicycleComponentManagerUI` | Immutable constructor wiring | Read-only projection, no manager role. |

The supported release lane gives the manager only the token mint and URI-setter
roles, removes the deployer's ordinary roles, and requires separate root and
two default-admin handoffs. Operational holders and nonzero admin delays are
explicit release inputs, not owner-level exceptions. See README release policy.

## `BicycleComponents` permissions

| Function | Authorized actor | Notes |
| --- | --- | --- |
| `mint(to, tokenId, uri)` / `safeMint(to, tokenId, uri, data)` | `MINTER_ROLE` | Manager holds this role in the release lane; nonempty URI required. Safe mint checks the receiver. |
| `setTokenURI(tokenId, uri)` | `TOKEN_URI_SETTER_ROLE` | Manager performs owner/delegate authorization before calling; nonempty URI required. |
| `pause()` / `unpause()` | `PAUSER_ROLE` | Stops/resumes minting, token URI updates and transfers. |
| `setBaseURI(uri)` / `setContractURI(uri)` | `CONFIGURER_ROLE` | Collection configuration; not blocked by token pause. |
| `grantRole(...)` / `revokeRole(...)` | Role's admin | Ordinary roles use `DEFAULT_ADMIN_ROLE`; default-admin changes use the delayed handoff API. |
| `transferFrom` / `safeTransferFrom` | Owner or authorized ERC-721 spender | Direct ERC-721 path, subject to token pause and receiver checks for safe transfers. |
| `approve` | Owner or operator approved for all | Token-specific ERC-721 approval, not a workshop grant. |
| `setApprovalForAll` | Token holder acting for their own account | Operator approval, not a workshop grant. |

## `BicycleComponentManager` permissions

| Function | Authorized actor | Notes |
| --- | --- | --- |
| `registerComponent(owner, serialNumber, tokenURI_)` | `REGISTRAR_ROLE` | Creates a record and mints using the configured collection; nonempty serial and metadata URI required. |
| `setComponentsAddress(tokenContract)` | `CONFIGURER_ROLE` | Changes future registrations only; existing records retain their collection and token ID. |
| `setMaxDelegationDuration(duration)` | `CONFIGURER_ROLE` | Sets the positive maximum duration checked for new grants. |
| `setComponentMetadata(serialNumber, tokenURI_)` | Current owner or `CAP_UPDATE_METADATA` delegate | Nonempty URI required; permitted while inactive or missing, subject to manager and recorded token pause. |
| `markComponentMissing(serialNumber, reportURI)` | Current owner or `CAP_MARK_MISSING` delegate | Opens a report when not already missing; nonempty report URI required. |
| `clearComponentMissing(serialNumber, resolutionURI)` | Current owner or `CAP_CLEAR_MISSING` delegate | Resolves an open report; nonempty resolution URI required. Registrar role alone is insufficient. |
| `decommissionComponent(serialNumber)` | Current owner only | Sets the independent inactive flag; does not open or resolve a report. |
| `reactivateComponent(serialNumber)` | Current owner only | Clears the inactive flag; does not open or resolve a report. |
| `setComponentDelegate(serialNumber, delegate, capabilities, validUntil)` | Current owner only | Replaces that address's grant, capturing owner and ownership generation; nonzero delegate required. |
| `revokeComponentDelegate(serialNumber, delegate)` | Current owner only | Deletes that address's grant; nonzero delegate required. |
| `setAccountInfo(infoURI)` | Calling account | Changes only the caller's profile URI. |
| `pause()` / `unpause()` | `PAUSER_ROLE` | Stops/resumes registry workflow writes, not direct token transfers. |
| `grantRole(...)` / `revokeRole(...)` | Role's admin | Ordinary roles use `DEFAULT_ADMIN_ROLE`; default-admin changes use the delayed handoff API. |

Lifecycle writes require a registered nonempty serial. Inactivity is reversible
and independent of the missing-report status. Metadata corrections, workshop
permissions and ordinary transfers are not disabled by inactivity. There is no
`retireComponent` write or retirement capability in the current implementation.

## Workshop capabilities and validity

| Capability | Bit |
| --- | --- |
| `CAP_UPDATE_METADATA` | 1 |
| `CAP_MARK_MISSING` | 2 |
| `CAP_CLEAR_MISSING` | 4 |
| `VALID_CAPABILITY_MASK` (all supported permissions) | 7 |

New grants reject zero masks and any bits outside mask 7, including the former
retirement bit 8. They require an expiry strictly after the chain timestamp and
no further away than `maxDelegationDuration`. No workshop mask authorizes
lifecycle changes, delegation management or NFT transfers.

Each stored `Delegation` contains `grantor`, `capabilities`, `validUntil` and
`ownershipGeneration`. Effective authority requires a nonzero grantor and
capabilities, an unexpired grant, the grantor still being the recorded token's
owner, and the recorded token's current `ownershipGeneration(tokenId)` matching
the saved generation. Ownership equality alone is insufficient.

Every actual ownership change increments the token generation through its
ERC-721 update hook before receiver callbacks. Earlier grants remain invalid
if the token returns to its former owner. Self-transfers preserve the generation;
failed transfers roll back both ownership and generation changes. A current
owner can explicitly issue a fresh grant after a transfer.

The CAM exposes address-based workshop inspection, grant replacement and
revocation. It does not enumerate all delegates. The UI offers named presets
with masks 1, 2, 4 and 7. `viewDelegation(serialNumber, delegate, account, duration)`
uses the chain clock to preview the exact `validUntil` passed to the existing
grant write. It rejects zero/over-limit durations and timestamps/expiries outside
uint48. The owner must refresh an expired preview; execution rechecks expiry and
authority. Manager pause disables grant/revoke actions; collection pause does not.

## Direct handover through CAM 1.3.0

The published `transferComponent` route is not a manager write. Its single
read-only resolver calls `tokenReference(serialNumber)` on the host-bound
manager and supplies the recorded collection address and token ID to the
ERC-721 `safeTransferFrom(address,address,uint256)` call. The destination
contract is a resolver output, not an editable collection input or the manager's
collection configured for future registrations. The UI offers handover to the
current owner when the recorded collection is unpaused.

Handover conveys token ownership only: it supplies no payment escrow, recipient
consent protocol, physical-delivery verification or recovery privilege. ERC-721
approved spenders can still transfer through the token's ordinary API; workshop
grants do not create that approval.

## Pause boundaries

Manager pause blocks registration, token metadata writes through the manager,
missing-report changes, decommission/reactivate, grant/revoke and account-info
writes. Its configuration and role administration are not pause-gated. The UI
projects manager pause and omits unavailable workflow actions from its action
list; the viewer can display their controls disabled.

Token pause is separate. It blocks minting, token URI updates and direct
transfers, but not ERC-721 approvals or collection configuration. Registration
uses the configured collection's pause; an existing component's metadata and
handover use its recorded collection's pause. Reports, lifecycle flags,
delegation and account info remain writable during token pause if the manager
is unpaused. Manager pause alone does not prevent token transfers.

Read projections are not authorization. State can change after resolution or
simulation, and direct callers bypass CAM presentation. Final onchain checks
remain authoritative.

## Report references and exclusions

Report/resolution URIs are external references, not authority. The manager
stores the currently open missing-report URI, clears it on resolution, and emits
`ComponentReported` / `ComponentReportResolved` alongside the status update.
Only nonempty strings are required; operators should prefer immutable references
and an offchain document schema. Lifecycle inactivity neither clears nor alters
these report references.

This implementation provides no manager transfer privilege, transfer capability,
recovery/dispute override, transfer lock, upgrade path, migration mechanism or UI
write role. None is implied by CAM publication or registrar/admin status.
