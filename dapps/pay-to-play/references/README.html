Service-payment reference sources

These snapshots support the pay-to-play app. The design record specifies E's native-currency channel accounting and authorization rules. Each channel has one stable ID. Y describes the offchain settlement service coordinating its API purchases; APIs using Y trust its shared accounting and onward payments. Their credits are obligations of Y, not claims against E.

The sources below help distinguish the channel contract from Y's shared API ledger. They do not settle Y's purchase coordination and API payout mechanisms. The snapshot collection is under service-payment-channels/ beside this README. It contains provenance.json and the five source-family directories.

Suggested reading order

  1. AbstractStreamChannel

    The closest concrete core to inspect first. It supports funding/top-ups, cumulative EIP-712 delta payments and closing. Compare its fixed 15-minute grace period and payee identity with E's per-channel period and stable channel ID and mutable recipient.

    • AbstractStreamChannel.sol
    • IAbstractStreamChannel.sol

  2. x402 batch settlement

    Read the EVM specification and implementation notes, then the matching contract. This provides a modern cumulative-voucher and batch-claim comparison. Its maxClaimableAmount is a signed ceiling over server-accounted actual charges; this differs from the app's cumulative entitlement, collectible in partial deltas as backing permits. Its claim accounting and recipient transfer are separate.

    • EVM batch-settlement specification
    • Implementation notes
    • x402BatchSettlement.sol
    • IDepositCollector.sol

  3. microRaiden

    A historical API/content micropayment design. Deposits, cumulative balance proofs and top-ups support receiver withdrawals while open, as well as cooperative and challenged unilateral closing paths.

    • Introduction
    • RaidenMicroTransferChannels.sol

  4. Raiden service payments

    raiden-spec describes the shared UserDeposit and OneToN model; raiden-contracts contains its concrete contract implementations. A shared deposit permits competing service claims, an accepted trade-off in that design. Compare this with Y's responsibility for shared API credits; E keeps different channel positions separately backed.

    • Service-contract specification
    • UserDeposit.sol
    • OneToN.sol
    • ServiceRegistry.sol

Snapshot boundaries

provenance.json records immutable repository commits, retrieval date, exact upstream paths/URLs, byte sizes and SHA-256 hashes. Upstream files retain their original bytes. Small repository-local imports accompany the main contracts; external OpenZeppelin, Solady and forge-std dependencies are not vendored, so this is not a self-contained compilation tree. No upstream code was executed to prepare the snapshots.

Repository LICENSE files are retained for microraiden, x402 and raiden-contracts; x402's NOTICE is retained too. The pinned abstract-packages tree has no root or contracts-package LICENSE, and raiden-spec has no LICENSE file; those absences are recorded in provenance.json and source SPDX notices are preserved. This collection records precedents without selecting a dependency or making an adoption/security assessment.
