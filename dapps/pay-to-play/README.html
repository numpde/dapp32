Pay-to-Play

A customer funds a native-currency position and signs cumulative payment vouchers for a settlement service. Anyone can collect a valid voucher; payment goes to the channel's current recipient. Each channel has a fixed withdrawal waiting period. The design record describes the accounting rules and trust assumptions.

Run the local fixture

make pay-to-play/local/scenario/run
make pay-to-play/local/demo/gui/up

The scenario deploys a private Anvil chain, PayToPlay and a CAM host, then exercises the published CAM actions through the generic viewer session. It signs vouchers offchain and advances fixture time using RPC. It checks cumulative purchases, partial collection and retries, current-recipient changes, renewal, collection during the wait, mature partial and zero withdrawals, and movement through channel 0. It is included in make tests. Solidity tests cover additional signature, recipient, authorization and accounting boundaries.

The GUI command prints its viewer URL on loopback port 5175 and remains in the foreground. This session owns an in-memory chain. Stopping the command or restarting its frontend or gateway tears down the fixture and loses its chain state. Viewer JavaScript is copied at startup; code changes require a fresh demo session. Open that URL in your existing browser. Connect a wallet on chain 31337 to prepare and submit transactions. The fixed admin, customer, relayer and recipient keys in compose/pay-to-play/local/deploy.yml are public local fixture values; use them only on this disposable chain. The deployment initially defines only channel 0. Use the admin account to create channel 1, then use the customer account to open and fund its position. Unavailable fields and actions remain visible and disabled. Native amount controls accept wei or exact decimal native amounts; transaction fees are separate.

make pay-to-play/local/demo/gui/down

The fixture uses an internal network, read-only source mounts and container-local build outputs. Only the GUI gateway exposes a loopback port. Teardown removes the fixture containers and broadcast volume. It does not deploy to an operator-supplied chain.

The initial view and “Open my wallet position” follow the selected account. Connecting or switching a wallet opens the current channel for that account. An explicitly inspected customer position stays fixed when the wallet changes; the new signer changes the available actions. Switching accounts clears unfinished form inputs. Funding, requesting, renewing and moving always affect the transaction sender's position, and their confirmed continuation opens that wallet's position.

Use Refresh to read current balances, recipients and withdrawal maturity without losing compatible unfinished inputs. Refresh discards any prepared transaction so you can prepare it against the new snapshot. In voucher signing details, Back restores the previous inputs; the direct position link starts fresh. After channel creation, the viewer opens a lookup with the current channel count. Find the exact new ID in your transaction receipt's ChannelCreated event; the count may include other creations.

Sign a voucher

Use standard EIP-712 typed-data signing. Obtain the PayToPlay deployment address from the deployment log; the CAM host is a different contract. The domain and message are:

{
  "domain": {
    "name": "PayToPlay", "version": "1",
    "chainId": 31337, "verifyingContract": "<PayToPlay address>"
  },
  "types": {
    "Voucher": [
      {"name": "customer", "type": "address"},
      {"name": "channelId", "type": "uint256"},
      {"name": "cumulativeTotal", "type": "uint256"}
    ]
  },
  "primaryType": "Voucher",
  "message": {
    "customer": "<customer address>", "channelId": "1",
    "cumulativeTotal": "100"
  }
}

The deployment's chain ID and PayToPlay address must match the domain. Amounts are native base units. The signature binds the customer, channel and lifetime cumulative authorized total; it does not bind the payment recipient or expire. A valid voucher can collect unpaid authorization after later deposits. The admin can redirect existing vouchers by changing the recipient. Contract-wallet signatures must still be valid at collection.

For the fixed local customer only, this offline helper prints a signature to paste into the viewer. Keep that output out of logs and commits:

make pay-to-play/local/voucher/sign PAY_TO_PLAY_ADDRESS=0x... PAY_TO_PLAY_CHANNEL_ID=1 PAY_TO_PLAY_TOTAL=100

The viewer's signing-details action shows the digest for comparison with a standard EIP-712 signer. Do not sign that digest as a personal message. The viewer prepares collection transactions; it does not sign vouchers.

Settlement-service responsibilities

The settlement service assigns cumulative totals for API purchases, retains signed authorizations, and provides retry-safe purchase IDs and a durable ledger. The local scenario uses two sample purchases with assigned totals; it does not implement an API server or a purchase ledger. Service credits and onward API payments remain outside the contract.

Effective balance is max(balance minus requested withdrawal, 0). This is a snapshot for budgeting, not reserved funds. A customer may renew a larger request within the balance, starting the full wait again. Vouchers may consume the actual balance during that wait. Mature withdrawal or movement consumes the request even if it pays zero; later deposits need a fresh request. Channel 0 has no voucher consumer.

Browser check

With the GUI and an existing browser CDP endpoint running, run the opt-in fixture write check. It opens a tab in that browser, checks the pinned CAM publication and signs local fixture transactions:

make pay-to-play/live/browser/check CDP_ORIGIN=http://127.0.0.1:9222 VIEWER_URL='<printed viewer URL>' EXPECTED_CAM_URI=http://127.0.0.1:5175/cam/main.json EXPECTED_CAM_HASH=0x...

Set the expected hash from the SHA-256 of the checked-in cam/main.json bytes. This lane uses host networking to reach the existing browser and GUI. It neither starts a browser window nor starts the GUI.
