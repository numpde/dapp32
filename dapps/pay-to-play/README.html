Pay-to-Play

Deposit native coins into a contract, pay a recipient using signed vouchers, or withdraw your remaining deposit after a waiting period. Each account has a separate balance in each numbered channel. The channel defines the payment recipient and withdrawal wait; the admin can change the recipient, but not the wait.

This demo handles deposits and voucher payments onchain. A service must separately manage purchases, customer credits and API access. See the design record for that boundary and the trust model.

Whose balance am I viewing?

Balance owner is the account whose deposited balance is displayed. Selected account is the account used to check available actions; before wallet connection, it can come from the page URL. Connected wallet is the account that submits transactions.

Start by choosing a balance owner and channel, then choose Open balance. Before a wallet connects, the owner field defaults to the selected account from the page URL and channel 0. Connecting a wallet on this initial chooser updates that default to its active account. Opening a balance only reads it; it sends no transaction. The opened owner and channel stay fixed when you connect or change wallet accounts. Use Change account or channel to choose another balance; that chooser starts with the currently open owner and channel.

The connected wallet sends transactions. Deposit, request and move require the opened balance owner’s account. Other accounts can submit valid vouchers (except in channel 0) or ready withdrawals back to the owner. Connecting a wallet or changing its account clears unfinished inputs. To deposit for a different account, open that account’s balance and connect its wallet.

Deposit, pay or withdraw

  1. Deposit: connect the balance owner’s wallet and choose the channel. A deposit credits that sending account’s balance in that channel, not the payment recipient. Channel 0 holds deposits that vouchers cannot spend; moving them to a payment channel requires a withdrawal request and its wait.
  2. Pay with a voucher: the balance owner signs an authorized total in a separate signer. Enter that total and signature. Anyone can submit it, but payment goes to the channel’s current recipient. See the signing reference below.
  3. Get funds back: request a positive amount no greater than the deposited balance. The displayed channel’s full wait starts when the request transaction is included in a block. Replacing it restarts that wait, even for the same or a smaller amount. There is no cancellation. When ready, withdraw to the balance owner or move funds to another channel for the same owner. Anyone can submit the withdrawal; only the owner can move funds.

Each Review button prepares and simulates a transaction. Review it, then choose Send with wallet to submit it. A successful simulation is a check against current chain state, not a guarantee of later success. Wait for transaction confirmation. The local test wallet asks for a browser confirmation and submits immediately when you confirm.

A withdrawal request does not reserve coins. Vouchers can spend the balance during the wait. With 80 wei requested and only 40 wei remaining, completing the request returns or moves 40 wei and clears the request. It also clears the request when nothing remains. Deposits made afterward need a fresh request and wait.

Balance minus withdrawal request subtracts the pending request, with a minimum result of zero. It does not subtract unpaid vouchers or tell you how much is safe to authorize again. Total paid by vouchers counts actual payments from this owner’s balance in this channel; it excludes withdrawals and moves.

Refresh, Back and account changes

Refresh re-reads the current balance and channel from the latest block. Compatible unfinished inputs stay; any reviewed transaction is discarded so you can review it again. It does not reload app resources or advance the chain. Readiness uses the latest block’s time, not your computer’s clock. Ready times show UTC and exact Unix seconds; an absent request is labeled explicitly.

Back re-reads the previous view and restores compatible earlier inputs when this session has history. The direct balance link in signing details starts with fresh inputs. Reloading the page clears history and unfinished inputs.

Create or change a channel

Connect the admin account. Channel creation is available on the chooser and on opened balances; you do not need to open a balance first. A new channel gets a recipient and a withdrawal wait that cannot change. Enter the wait as whole Days, Hours, Minutes and Seconds; the total is stored in seconds. Blank parts count as zero once any part is entered. After confirmation, obtain the exact ID from the ChannelCreated event in that transaction’s receipt, using a receipt-inspection tool. The viewer shows the transaction hash and opens the chooser with the channel ID left blank; it does not decode the event. The current channel count cannot identify which channel your transaction created.

Changing a channel’s recipient redirects unpaid authorization from already-signed vouchers as well as new ones. It applies to every customer in that channel. Customer balances and withdrawal waits stay unchanged.

Voucher signing reference

A voucher authorizes a lifetime total for one balance owner and channel, not a fresh payment of that amount. If the total is 100 wei and 30 wei has already been paid, up to 70 wei can still be collected, limited by the current remaining balance. After a partial payment and refill, the same voucher can pay again. It pays zero only when that total is already paid or no deposited balance remains. Authorization has no expiry.

Use an EIP-712 typed-data signer with the following schema. The signer must use the deployment’s chain ID and PayToPlay payment contract address, not the CAM host address shown in the viewer header. Obtain the payment contract address from the deployment output or the CAM host’s PayToPlay binding. The signing-details screen shows a hash for comparison; it does not supply that address or create a signature. Do not sign the hash as a personal message.

{
  "domain": {
    "name": "PayToPlay", "version": "1",
    "chainId": 31337, "verifyingContract": "<PayToPlay address>"
  },
  "types": {
    "Voucher": [
      {"name": "customer", "type": "address"},
      {"name": "channelId", "type": "uint256"},
      {"name": "cumulativeTotal", "type": "uint256"}
    ]
  },
  "primaryType": "Voucher",
  "message": {
    "customer": "<balance owner address>", "channelId": "1",
    "cumulativeTotal": "100"
  }
}

The signature binds that owner, channel, total, chain and payment contract. It does not bind the recipient. Contract-wallet signatures must still be valid when submitted. A higher total does not revoke an earlier voucher; actual lifetime payments determine how much remains collectible.

Run the local demo

make pay-to-play/local/demo/gui/up

Open the printed loopback URL on port 5175 in your existing browser. The fresh chain has only channel 0. Connect a wallet on chain 31337, or use the maintained local test-wallet selector with the existing tab. Its admin, customer, relayer and recipient accounts are public test accounts, not real funds. Choose admin to create a channel; choose customer to deposit and request withdrawals; relayer can submit someone else’s signed voucher. The contract enforces the permissions, not the role names.

Amounts can be entered as whole wei or decimal native coins in the linked boxes. One native coin is 1,000,000,000,000,000,000 wei; transaction fees are separate. This local chain mines when transactions are sent. Waiting in real time may leave withdrawal readiness unchanged until another block is mined.

Keep the GUI command running. Its in-memory chain is deleted when the command stops or its supervised frontend or gateway restarts. Viewer JavaScript is copied at startup; a code change needs a fresh session. Do not restart a live service to update it while expecting to preserve the chain. Stop the disposable demo with:

make pay-to-play/local/demo/gui/down

The demo uses an internal network, read-only source mounts and temporary build outputs. Only the GUI gateway is exposed on loopback. Teardown removes the containers and broadcast volume. It deploys no contracts to an operator-supplied chain.

For the fixed local customer only, this offline command prints a voucher signature to paste into the app. Keep its output out of logs and commits:

make pay-to-play/local/voucher/sign PAY_TO_PLAY_ADDRESS=0x... PAY_TO_PLAY_CHANNEL_ID=1 PAY_TO_PLAY_TOTAL=100

Check the local workflows

make pay-to-play/local/scenario/run

This disposable real-RPC test uses published app actions for deposits, cumulative voucher payments, partial-payment retries, recipient changes, withdrawal replacement and completion, and moves through channel 0. It signs vouchers outside the viewer and advances fixture time through RPC. It is part of make tests. Solidity tests cover further signature, recipient, permission and accounting cases; these checks do not implement a service API or purchase ledger.

The optional browser check opens one tab in an existing browser, uses public local test accounts, and sends bounded fixture transactions:

make pay-to-play/live/browser/check CDP_ORIGIN=http://127.0.0.1:9222 VIEWER_URL='<printed viewer URL>' EXPECTED_CAM_URI=http://127.0.0.1:5175/cam/main.json EXPECTED_CAM_HASH=0x...

Use the SHA-256 of the checked-in cam/main.json bytes as the expected hash. The GUI and browser CDP endpoint must already be running. This lane starts neither a browser window nor the GUI.
