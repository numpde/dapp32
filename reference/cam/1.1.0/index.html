Contract Application Manifest (CAM) 1.1.0

Experimental draft. Document format versions: CAM 1.1.0, UI 1.0.0. Implementation baseline: 6a3c3c4. Documentation revisions do not change these format versions.

Definitions

On chain and off chain
On chain refers to contract code and state recorded in a blockchain. Off chain refers to software and files outside that recorded state, such as an agent, web application, or downloaded JSON file.
Manifest (CAM)
A Contract Application Manifest is a JSON document describing a workflow: which contract calls to prepare, which files to load, and which step follows a call. Software reads this document off chain.
CAM host contract
The contract from which software reads the manifest's URI and hash. The URI says where to retrieve the document; the hash lets that software check the retrieved bytes. This repository's CamRoot contract also maps contract names to addresses; these mappings are called address bindings.
Called contract
The contract whose function a workflow calls. Its executable code enforces business rules. The CAM host contract and a called contract can be the same deployed contract; the names describe roles.
Consumer, runtime, and viewer
A consumer is an off-chain agent or application that loads and interprets a manifest. Its runtime is the software that resolves values and prepares or performs the described calls. A viewer is a consumer that also renders the described user interface. An agent can interpret the workflow without displaying that interface.
ABI
An Application Binary Interface is a JSON description of contract functions and their argument and result types. In this reference it describes calls for the Ethereum Virtual Machine (EVM); it is separate from deployed contract code.
UI document
A JSON description of user-interface elements, called UI nodes, and how they are composed. A consumer interprets it off chain; a viewer displays the resulting text, fields, and controls.
Bundle
The manifest together with its declared ABI and UI resources. This implementation retrieves these files from external storage; the CAM host contract does not fetch or interpret them.

A consumer starts from a selected chain and CAM host contract address. It reads the manifest URI and hash, downloads and verifies the bundle, then interprets its instructions to request a contract read or prepare a wallet transaction. A viewer also renders the UI. The called contract enforces its business rules when the EVM executes the call.

This reference is for AI and LLM coding agents and the people reviewing their work. It explains the document model and this repository's EVM adapter, the software that translates CAM calls into EVM requests. It describes verified behavior at the implementation baseline; it does not claim a complete independent standard or interoperability with other implementations.

How the contracts and consumer work together

The bundle author publishes the files. This repository's CamRoot owner configures the manifest URI/hash and contract address bindings. The consumer verifies and interprets the bundle, then requests calls to those bound contracts. Publishing a description of an operation does not authorize it: the called contract still decides whether an attempted operation is allowed.

In this document, document rules describe accepted CAM/UI fields and relationships. EVM profile means the rules this repository's EVM adapter uses to translate declarations into contract calls and normalize their results. Runtime policy means choices made by off-chain software, such as which resources it may fetch or how it waits for a transaction receipt. Authoring advice is identified as advice.

Conformance checks are off-chain publication checks of supplied manifests, ABIs, and UI documents. They can find malformed declarations and incompatible references between files before publication. Passing them does not establish live contract state, wallet permission, or transaction success. A document-loading rejection is separate from a contract revert during execution.

Find and verify a manifest

The consumer needs a blockchain connection before it can read the CAM host contract. It sends remote procedure calls (RPC) to a blockchain node, which answers reads and can receive submitted transactions. An RPC node is distinct from the UI nodes described later.

Start with an independently selected chain and CAM host contract address. The EVM profile uses a chain identifier such as eip155:1, with a positive safe-integer chain number, checks the RPC client's chain, and checks ERC-165 support for ICamApp (0x03625ff6). That interface exposes camURI() and camHash(). This repository's CamRoot contract additionally supplies contractAddress(string). The lookup argument is the bare contract name: contracts.Registry maps to Registry.

Reading the CAM host contract needs a bootstrap ABI before the advertised ABIs are available. These signatures describe the calls used by this profile:

function supportsInterface(bytes4 interfaceId) external view returns (bool);
function camURI() external view returns (string);
function camHash() external view returns (bytes32);
function contractAddress(string contractName) external view returns (address);

The loader requires supportsInterface(0x03625ff6) to return true; false or a failed read blocks loading. The CAM interface ID excludes the inherited ERC-165 selector. The adapter uses the separately known binding signature after loading the manifest; support for ICamApp alone does not assert support for that extension.

A nonboolean interface response is also rejected. The URI must be a string, the manifest hash must be 0x plus 64 hexadecimal digits, and each contract binding must be a valid nonzero EVM address. Malformed responses fail at the CAM host contract or binding boundary.

Contract bindings are separate, mutable facts supplied by the CAM host contract. The manifest hash does not commit to their addresses, and loading does not promise an atomic snapshot of the manifest URI, hash, and bindings. An agent reviewing a transaction needs to inspect the actual selected chain and resolved destination.

Viewer policy: this repository's viewer resolves bindings and ABIs when it loads a session and reuses them for navigation and preparation. A prepared write carries that resolved destination; simulation and submission use it without rereading the CAM host contract's mapping. Later binding changes do not retarget that prepared call. Reloading the session resolves the bindings again. Other consumers can choose a different binding lookup policy.

A JavaScript safe integer is an integer from −9,007,199,254,740,991 to 9,007,199,254,740,991. EVM chain identifiers use only the positive part of this range; expression array indexes use only the nonnegative part.

The manifest hash is Keccak-256 of the manifest bytes, returned by camHash() as bytes32. The off-chain loader downloads those bytes, computes their hash, and compares it with the contract-returned commitment before parsing JSON. Reformatting JSON changes those bytes even when the parsed objects appear equivalent. A zero manifest hash is rejected by default; the adapter's explicit unsigned-loading option permits it and skips manifest hash verification. Do not describe such a load as contract-anchored integrity.

Contract ABI and UI declarations in the external manifest carry integrity in the form sha256:0x followed by exactly 64 lowercase hexadecimal digits. The off-chain loader verifies SHA-256 of each resource's original bytes before parsing it. This second commitment lets the verified manifest bind the resources it references, even though their bytes are stored off chain. Neither digest authenticates a human author's identity or proves that an ABI matches deployed bytecode.

An IPFS URI identifies content with a content identifier (CID). Supported spellings are CIDv0 base58btc (Qm plus 44 base58btc characters) decoding to a SHA-256 multihash, or lowercase CIDv1 base32 with version 1, raw (0x55) or dag-pb (0x70) codec, and a 32-byte SHA-256 multihash. IPFS manifest and resource URIs use the same path restrictions shown above; credentials, trailing slashes, and query or fragment components are rejected. URI acceptance does not supply an IPFS transport. A caller-provided loader still has to retrieve the bytes.

Relative resource references resolve against the directory of the original camURI: https://example.org/app/main.json plus ./abi/Registry.json becomes https://example.org/app/abi/Registry.json. The same rule applies to the UI resource.

Resolution drops the manifest URI's query and fragment: https://example.org/app/main.json?rev=2#section plus ./ui/main.json becomes https://example.org/app/ui/main.json.

Runtime policy: the shared HTTP loader restricts requests to a selected origin, refuses redirects, and bounds decoded response bytes to 2 MiB per resource. A custom loader has its own access and timeout responsibilities; accepting a URI is not permission to access arbitrary network or local resources. The adapter also checks returned resource size. A zero or invalid contract binding is rejected.

Declare the manifest and namespaces

A namespace tells the consumer what a name refers to and how a call to it should be interpreted. contracts.Registry means a bound contract described by an ABI; ui means the UI document; routes means the manifest's own named call plans. These declarations let the consumer distinguish an EVM function call from a UI selection or a next-route selection.

CAM is declarative JSON interpreted off chain. Its top-level object has exactly cam, entry, namespaces, and routes. cam is "1.1.0"; the readers also accept explicit "1.0.0" documents. entry names an existing route, the call-and-next-step plan defined in the following section. Unknown fields are rejected at the closed document, namespace, route, and invocation boundaries.

Namespace nameDeclaration fieldsPurpose
contracts.<Name>type: "contract", abiURI, integrityCalls a contract whose address comes from the CAM host contract. Name matches [A-Za-z_][A-Za-z0-9_]*.
routestype: "routes"Names routes within this manifest; has no external resource.
uitype: "ui", uri, integrityNames nodes in the UI document.

An invocation describes a call by naming its namespace, function, and arguments: {"namespace": "…", "function": "…", "args": {…}}. A contract invocation selects an ABI function; a UI invocation selects a named UI node; a routes invocation selects another route. The namespace has to exist and have the type allowed at that call site. In CAM routes, function is a nonempty literal name. Argument values may contain expressions recursively. An ABI call's argument keys are ABI parameter names, not positions.

Define routes, arguments, and results

A route is a named plan interpreted by the consumer. Its call describes one contract invocation. Its then describes the next invocation, called the continuation. The route itself is not deployed contract code. A read route obtains contract results and selects a UI node; a write route prepares a transaction and names another route to follow after success.

A route has kind, inputs, call, and then. inputs declares its complete external argument interface as an array of unique names using the expression identifier grammar. Route execution rejects missing and additional input names before resolving either invocation, even if the route does not read every input.

Kindcallthen
readContract namespace; EVM function is view or pure.UI namespace; passes resolved arguments to a named UI node.
writeContract namespace; EVM function is nonpayable or payable.Routes namespace; names the next route.

Document parsing and conformance allow a write continuation to name another write route. This repository's viewer does not reject that destination while preparing the first write. If the first transaction succeeds, the viewer then attempts to navigate to the next route; navigation rejects a write route at that point. The viewer reports transaction success with a view-refresh failure; the first transaction's effects are not rolled back. A consumer supporting a write-to-write handoff must decide how to prepare and authorize the next transaction; the declaration does not automatically submit it.

A consumer may inspect the resolved UI model and action descriptions without drawing a graphical interface. A read route still has a UI continuation; interpreting it without a display does not change the allowed namespace or turn that continuation into a second contract call.

In the ABI, view and pure describe EVM function mutability. They are separate from a UI view, the interface selected for display.

EVM profile: a bare function name must identify one ABI function; an overloaded bare name is ambiguous and rejected. A full signature using the types declared in the supplied ABI, such as lookup(uint256), selects an overload. The named arguments must match its named inputs, including tuple component names. The adapter checks the following value shapes and ranges before calling. Use decimal strings to avoid rounding large integers. Fixed-size arrays are unsupported in this profile.

Signature matching uses the supplied ABI's type spellings without whitespace, expands tuple components inside parentheses, and retains array suffixes. For example, a tuple of uint256 and address has signature type (uint256,address). The adapter does not rewrite uint to uint256 while matching signatures.

Read outputs are a positional array: no ABI outputs produces []; one ABI output produces one array item, even if that item is itself an array or tuple. Integer outputs become decimal strings, addresses become lowercase strings, bytes remain hexadecimal strings, and named tuple components become object fields. A continuation can use $outputs.0 or $outputs.0.component. Top-level outputs are selected by position, rather than by their ABI output names.

Top-level ABI outputs may be unnamed because their position identifies them. Tuple components, including components of output tuples, must have unique nonempty names; unnamed or duplicated components are rejected. This lets an agent select tuple fields by name without guessing how a decoder represented them.

The adapter validates the entire loaded ABI array, including functions no route currently calls. Unsupported parameter types, malformed function declarations, and duplicate function signatures reject the ABI; nonfunction entries receive only an object/type check, so this is not a comprehensive ABI linter. Separately, a read result with the wrong count, shape, or range is rejected at runtime rather than silently converted or skipped.

Native transaction value in CAM 1.1.0

A write route may additionally declare value, as a literal or expression. It is transaction value in the chain's native base unit, separate from call.args. For a payable function this profile requires an explicit value, including "0" for zero. It must resolve to a decimal uint256 value. A nonpayable function rejects any declared value, including zero. Read routes and CAM 1.0.0 routes reject the value field.

Advice: publish an explicit unit with any amount editor and pass its canonical base-unit string as route input. A token amount in ABI arguments is not automatically native transaction value; transferring a token remains a contract operation.

Resolve expressions

The off-chain runtime resolves expressions by selecting values already supplied to it. Expressions do not evaluate JavaScript, perform arithmetic, concatenate strings, or fetch resources. An expression occupies the entire string. A normal string is literal; a leading $$ escapes one dollar sign.

An expression root is the first name after the dollar sign: inputs in $inputs.itemId. It selects a runtime value from the table below; subsequent segments select fields or array items within that value.

Runtime values are inert: strings, finite numbers, booleans, null, arrays, and plain objects containing those values. Functions, undefined values, bigint values, and cycles are rejected. EVM integer results are converted to decimal strings before entering this model.

reference  = "$" identifier ("." segment)*
identifier = [A-Za-z][A-Za-z0-9_]*
segment    = identifier | arrayIndex
arrayIndex = "0" | [1-9][0-9]*  (within JS safe-integer range)

Array indexes have no leading zeros; $outputs.01, empty segments, bracket notation, and operator syntax are invalid. Selection traverses arrays by numeric index and objects by their own fields. A missing expression root or segment fails resolution; it does not become null or an empty string. Selecting an existing null leaf succeeds; traversing through it fails. Recursive resolution preserves the selected value's type. A selected string beginning with $ is a value, not a second expression to execute.

$hostSelected CAM host contract's chainId and address.
$accountOptional current account object with address. Referencing it requires an available account.
$inputsInputs for the current route.
$outputsCurrent call's normalized positional results; available to the read continuation.

$viewValue passed to a named UI node as its view argument. It can be any inert value; it is separate from the rendered interface and editable $state.
"$inputs.itemId"    → the input value, preserving its type
"$outputs.0.name"   → a named field in the first result

Advice: use $outputs in the continuation of the read that produced it, and pass needed values into the next route explicitly. A write does not turn a Solidity return value, receipt, or event into route outputs.

Describe a UI 1.0.0 view

A UI node describes an element such as a screen, text, field, or button. Nodes may contain child nodes or include named nodes, forming an interface tree. A UI view is the resolved tree for a selected named UI node; a consumer can inspect it or render it. A CAM read route's continuation selects that named node.

A UI document has exactly ui: "1.0.0" and a nonempty nodes object. Each named UI node declares requires, either [] or ["view"]; its caller supplies exactly those argument names. The argument named view carries values from a route or another UI node and becomes $view during resolution. Despite its name, that argument is not the rendered interface. Inline children have no requires. Expression roots such as host and state cannot be shadowed by UI node arguments.

The element vocabulary is closed. Each element accepts only its listed structure and props, plus the named-node requires declaration. String props may be expressions but have to resolve to strings. There are no style, script, event-handler, or arbitrary HTML fields.

Status with stringList requires an array of strings, displays an empty array as None, and otherwise joins entries with comma and space. bytes and durationSeconds require a nonnegative decimal integer string or safe nonnegative integer number. Bytes are comma-grouped with singular/plural units, such as 1 byte or 1,024 bytes. Durations below 60 use seconds; larger values use nonzero day/hour/minute/second parts followed by total seconds, such as 1 minute, 1 second (61 seconds). Without a format, the viewer chooses the presentation of the inert value.

Publication tool policy: the conformance checker follows statically known types through references, a check called typeflow. For Nft.tokenId, it expects known references to provide an integer or string; known boolean, tuple, or array references receive a diagnostic. That check does not restrict literal values at this site. The UI runtime's acceptance of any inert token ID remains a separate boundary.

State and typed editing

UI $state holds off-chain editable values; editing a field does not submit a transaction or update contract storage. Each field's state contains key and defaultValue, both expression-capable values. The key resolves to an expression identifier and the default resolves to a string. Selected fields, including fields reached through Includes, collect their defaults before ordinary view and action resolution. Duplicate state keys fail, even when their defaults agree. Default collection starts with empty state because those defaults initialize the state: defaults and the Includes selecting fields cannot depend on editable $state. An Include selecting Buttons without fields can consume state after defaults exist.

The UI runtime separates initialization from resolving current state. Initial resolution discards any supplied state, collects defaults, then resolves the UI view. Current resolution uses the supplied state without merging defaults, pruning old keys, or initializing fields that appear after an Include changes. The off-chain consumer owns edits and persistence. This repository's viewer starts fresh state on ordinary route navigation; its Back action can restore compatible saved drafts after rereading the prior route. Those choices do not add persistence rules to UI 1.0.0.

Typed numeric fields distinguish editable text from usable values. Empty, incomplete, invalid input, or text still being composed through an input method, has a canonical value of null; a valid zero has the string "0". An agent preparing a call must respect that distinction instead of converting unset input into zero.

Runtime policy: numeric editing accepts at most 2,048 UTF-16 code units of text and 1,024 canonical significant digits. Integer field bounds resolve to nonnegative decimal strings with empty editable state; min and max are inclusive and cannot depend on $state. These editing limits do not replace the ABI's integer range or the contract's business limits.

Integer and base-unit amount editors accept ASCII decimal digits only. Display-unit amount editing also permits one decimal point: .5 and 1. can represent valid values; a lone point is incomplete. Signs, whitespace, grouping separators, hexadecimal forms, and exponents are invalid. Leading zeros are allowed in editing and removed from the canonical value. Amount precision beyond the declared scale is accepted only when the excess digits are zero.

Numeric defaults are base-unit digit strings or empty strings. Invalid or out-of-bounds defaults reject view initialization rather than becoming an editable null value. If both integer bounds are supplied, min cannot exceed max; there is no implicit uint256 maximum in the editor.

AmountField.props.unit has exactly assetId, baseLabel, displayLabel (nonempty literal strings), and decimals (an integer from 0 to 255). For example, a scale of 2 converts display text "1.25" to canonical "125". Conversion uses exact decimal scaling; nonzero excess precision fails instead of rounding. A unit declaration does not verify the asset or authorize spending it.

DocumentHashField can calculate SHA-256 of selected document bytes or bytes obtained from optional sourceURI, producing a 0x plus 64-hex-digit digest. Its editable/default string is not itself guaranteed to be a valid digest; the receiving ABI or contract owns acceptance of the supplied value. This document digest is distinct from ABI/UI resource integrity. File selection and fetching behavior belong to the off-chain consumer.

Composition and availability

An Include's call.function resolves to a node name or an ordered array of distinct node names; an empty array includes nothing. Every selected node must exist and receive its exact required argument set. Include cycles fail. Included nodes share the runtime and state; the Include is replaced by its resolved children in selection order. A Button's call.function resolves to one route name, and call.args supplies that route's inputs.

"enabledWhen": {
  "member": "edit",
  "in": "$view.availableActions"
}

enabledWhen is allowed only on Buttons and fields. It has exactly a nonempty literal member and in, either an expression resolving to an array of nonempty strings or a literal array of them. Membership uses exact case-sensitive equality. Absence of the member disables the control while retaining it in the view. Disabled controls still resolve props, arguments, and defaults, so an unresolved value remains an error. Membership is presentation availability, not permission proof.

Literal membership strings cannot be single-dollar references and do not apply dollar escaping: a literal "$$edit" compares as those two dollar signs. Route and UI node names and invocation argument keys are nonempty strings; they do not share the identifier restriction on route inputs and state keys.

UI 1.0.0 defines route buttons and UI node composition. Back, history, focus placement, storage, wallet controls, and confirmation dialogs are features of the off-chain application, without corresponding UI document fields.

Execute a route and handle its outcome

For a read, the off-chain runtime supplies the current CAM host contract's chain/address, optional account, route inputs, and initially empty outputs. It resolves the call and validates it against the bound ABI, then asks an RPC node to execute the EVM read against chain state without committing transaction effects. The runtime normalizes the returned results and resolves the UI continuation off chain. A failed call or invalid result cannot supply an ordinary successful UI view.

In this EVM profile, a supplied account.address also becomes the caller of route RPC reads, even when no expression references it. Caller-dependent contract reads can therefore return different results for different accounts. Without an account, the adapter leaves the RPC caller unspecified. These reads do not require a wallet signature.

The off-chain consumer decides how an account change affects its UI: when to reread contract results and whether to retain drafts or prepared calls. CAM does not prescribe an account-change policy.

For a write, the off-chain consumer prepares both the contract call and route continuation with empty outputs. It may first ask an RPC node to simulate the call; simulation executes against the node's state without committing transaction effects and cannot guarantee later success. The wallet authorizes and submits a transaction; submission returns a hash. An included transaction executes the contract on chain and can apply state changes if it succeeds. A reverted transaction does not apply the attempted contract changes.

The transaction hash identifies a submission, not a successful confirmed operation. Receipt observation happens off chain: this repository's web viewer waits for a successful receipt, then tries to navigate to the route named by the prepared write continuation. Successful read navigation refreshes the UI view.

Confirmation count, timeouts, replacement transactions, reorg recovery, and stale-interaction handling are off-chain application policies. CAM does not specify those policies or require the repository's session architecture. If confirmation succeeds but the following read fails, report both facts: the write has succeeded and the view refresh has failed. A timeout or uncertain submission is not proof of failure; check the wallet or chain before retrying a consequential write.

Authoring advice: have writes continue to a read that obtains the needed live state. Do not fabricate write outputs from events or simulated return values. Account availability, RPC connectivity, wallet approval, and contract state can change after a document passes conformance checks.

Follow a neutral worked example

Consider a hypothetical registry contract with labelOf(uint256 itemId) view returns (string) and setLabel(uint256 itemId, string label) nonpayable. Assume a CamRoot CAM host contract binds Registry and advertises the following resources. The registry contract decides who may edit a label.

The manifest, ABI, and UI below are off-chain files. The CAM host contract stores the manifest URI/hash and the Registry address binding on chain; ABI/UI URIs and digests appear in the external manifest. The next read receives the item ID explicitly because write outputs are empty. The UI receives the previous read's label through the view argument, then keeps the user's edit in local state. This separates live contract results from an unsubmitted draft.

Recognize invalid and failed cases

ConditionRejection or outcome
Downloaded manifest bytes differ from the nonzero manifest hash.EVM loader rejects them before JSON interpretation.
Valid manifest JSON, but ABI/UI bytes differ from declared integrity.Resource verification rejects them; parser success is insufficient.
Duplicate JSON object key or invalid UTF-8.Byte-to-JSON parsing rejects the document.
abiURI: "https://example.org/abi.json" or "./../abi.json".Secondary URI declaration policy rejects it.
Read continuation uses the routes namespace.CAM invocation validation rejects the namespace type.
Call to show omits itemId, or adds debug.Route input validation rejects the argument set.
$outputs[0] or $outputs.01.Expression syntax validation rejects the reference.
$account.address without an account.Runtime cannot resolve the value.
Nonpayable write includes value: "0".EVM write validation rejects the value declaration.
Two selected fields resolve to the same state key.UI state collection rejects the conflicting declarations.
A disabled Button contains a missing expression value.UI resolution still fails; disabled state does not skip validation.
Well-formed write violates a contract business rule.The contract can revert; document conformance does not predict success.

Sources, checks, and open limits

This draft derives from the implementation at 6a3c3c4. The links below pin that source baseline rather than following a moving branch. Repository tests are evidence for this implementation's behavior; they are not an independent interoperability certification.

  • ICamApp contract interface and CamRoot binding extension.
  • Wire versions, CAM parser, and core route and parser tests.
  • URI, integrity, and resource bounds, expression grammar and resolution, and protocol tests.
  • Loading from a CAM host contract, read/result conversion, write submission, and EVM tests.
  • UI parser, UI resolution and state, and UI tests.
  • Viewer write preparation and web viewer lifecycle.

The existing offline validation commands are make tests/checks, make js/tests, and make cam/conformance/check, after materializing locked dependencies through the repository's separate dependency lanes. Conformance examines supplied document/resource joins. It does not contact live contracts to prove account authority or transaction success.

Open limits: this reference does not define independent discovery catalogs, non-EVM adapters, wallet permissions, a transaction finality standard, an atomic snapshot protocol, deployed code identity, or a complete renderer appearance contract. The worked example has not been exercised against an independently implemented consumer. A consumer should select and document its resource transport and transaction policies before operating a live workflow.
