Bike NFT component registry

Bike NFT is a contract-defined workflow for registering serial-numbered bicycle components as ERC-721 tokens, looking them up by serial number, and exposing owner/delegate actions through a generic CAM viewer.

What the app does

The app models a bicycle component registry. A role-authorized registrar creates a registry record for a physical component serial number and mints a normal ERC-721 token to the owner. The manager contract stores the serial lookup, status, registrar, timestamps, token contract, and token id. The NFT contract remains a regular token contract, so wallets and indexers can treat component ownership normally.

“Verified” here identifies a registrar-created record; the contract does not inspect the physical component or prove its authenticity.

The visible app is defined by CAM resources. A host contract publishes the manifest URI/hash and contract address bindings; the generic viewer loads those resources, calls the read routes, renders the declared UI nodes, and prepares wallet writes from the manifest routes.

User workflow

1. Look up

Enter the component's serial number to see its registered owner, status, and available actions.

2. Register

A registrar mints the component NFT and creates the verified serial record.

3. Maintain

The owner or a scoped delegate updates metadata, opens a missing report, or resolves it.

4. Change service state or ownership

Only the owner can take the component out of service or reactivate it. Missing reports remain attached. An ownership handover transfers the NFT directly and permanently invalidates previous workshop grants.

Try locally with Docker

From the repository's main branch, run the commands below. The GUI target starts a disposable Anvil test chain, deploys the contracts and demo records, and prints the browser URL. This page documents the workflow; it does not host a registry app.

git clone https://github.com/numpde/dapp32.git
cd dapp32
make dapps/deps/install
make js/deps/install
make cam/conformance/check
make bike-nft/local/demo/gui/up

You can browse the seeded DEMO-FRAME-001 record without a wallet. The address in the printed URL selects whose actions you see; it cannot sign transactions. Preparing a write does not change the registry.

To send a transaction, use a separate browser wallet profile. Add chain ID 31337 with RPC URL http://127.0.0.1:5173/rpc, or the printed GUI origin followed by /rpc if you changed the port. Import the public local-only PRIVATE_KEY from compose/bike-nft/local/deploy.yml and connect it to the viewer. That funded fixture account is both the registrar and the owner of the demo components. Connecting a wallet selects its address for the view and clears prepared calls. If you switch accounts in the wallet, wait for the refreshed view, check the account and chain, then prepare again. This fixture key is unsafe on any other chain; keep real funds and valuable keys out of this disposable chain.

After connection, wallets that report account and network changes update the viewer automatically and clear unsent prepared calls. A different wallet network leaves the viewer's configured chain and RPC unchanged and disables sending until the wallet returns to that chain. Disconnecting keeps the last successful read-only view. Submitted transaction hashes and receipt tracking survive wallet changes. If your provider cannot report changes, use Switch wallet to reconnect after changing accounts or networks.

To register, enter an unused serial number, the intended owner's address, and a token metadata URI. Prepare the call, review it, and send it with the registrar wallet. Wait for successful confirmation before treating the record as created; the viewer then reads the component view. The GUI target attempts teardown when its foreground command exits. Successful teardown removes the local fixture state. After an interrupted run, or if the fixture remains running, use make bike-nft/local/demo/gui/down and check that it has stopped.

Token metadata describes one component, including its name and image reference. For your own release, the empty base URI default lets the viewer store a complete HTTP(S) metadata URL or embedded JSON data URI for each token. A shared nonempty prefix requires an advanced client that supplies relative suffixes; the viewer's complete URIs must not be combined with that prefix. Collection metadata describes the collection as a whole and is separate from token metadata and the CAM manifest. See the release setup's metadata choices, including inline collection JSON.

This fixture allows a zero manifest hash for local development. It still checks the manifest's ABI and UI resource hashes; it does not demonstrate a hash-pinned root publication.

Onchain pieces

CamRoot

Publishes the CAM URI/hash and resolves manifest contract names to deployed addresses for this chain.

BicycleComponents

A non-upgradeable ERC-721 collection. It owns token behavior, transferability, token URI storage, and collection metadata.

BicycleComponentManager

The registry and policy contract. It owns serial lookup, status, component delegations, account info, missing report state, lifecycle events, and write permissions.

BicycleComponentManagerUI

A read-only route projection contract. It never writes manager state; it returns semantic view data and action names for CAM.

CAM manifest

Declares contract namespaces, read routes, write routes, ABI resources, and the UI resource consumed by generic viewers.

Generic viewer

Renders the workflow from manifest data and prepares contract calls; business authority remains in the manager and token contracts.

Authority model

Registrar authority

Registrars create verified component records and mint component tokens to owners. Removing the registrar role immediately changes both write authority and the registration view.

Owner authority

Current ERC-721 owners can update metadata, manage missing reports, take components out of service or reactivate them, manage expiring workshop permissions, and transfer the NFT directly. Service state does not erase or block missing reports.

Scoped delegates

Owners grant workshops selected update capabilities with an expiry and can revoke them in the app. These grants do not authorize NFT transfers or changes to service state. A change of owner invalidates old grants permanently, including if the token returns to that owner.

Account metadata

Account info is self-managed by the account address and is used by the read projection. Report and resolution documents remain external URI references, not registry authority.

Important boundaries

The UI contract is read-only

BicycleComponentManagerUI has no roles, no owner, and no write functions. It selects views and actions from manager state, including hiding manager writes while the registry is paused and registration or component metadata writes while the component token is paused.

The token remains standard

Transfers and approvals are ordinary ERC-721 operations on BicycleComponents. Registry status is stored by the manager; token transfers do not update it in V1.

The manifest is not authority

CAM describes reads, UI nodes, and prepared writes. The manager and token contracts still enforce all business rules onchain.
