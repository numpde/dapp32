Deploy Escrow

Instance settings, contract authority and acceptance checks for the Escrow example app.

Example app guide · Shared setup, deployment and verification

This page defines the app-specific inputs and checks. Use the shared guide for source snapshots, protected configuration, approval, records and cleanup. Example addresses and paths below are placeholders; your saved configuration selects the actual instance.

The shared component workflow provides escrow/release/contracts/deploy, escrow/release/ui/deploy and keyless escrow/release/cam/bundle. Business deployment, UI deployment and CAM publication have separate records and may use different actors and source commits. A UI replacement can reuse the verified business artifact without redeploying its contracts.

Release deployment

For guided setup, run make escrow/release/setup CONFIG=/absolute/private/escrow.json, then make escrow/release/deploy CONFIG=/absolute/private/escrow.json. The shared walkthrough saves every app input, concrete RPC URL, signing key, selected approval image and deployment confirmation in one protected off-repo file. Use the same CONFIG for release verification.

Public setup checks the selected RPC chain. Explicit local setup selects the shared chain-31338 fixture; local fixture keys must never be used for public deployments. The offline planning step validates the complete checked-in CAM bundle. By default, CamRoot stores the manifest's exact-byte SHA-256; selecting a zero CAM hash stores zero instead.

Shared source-snapshot, secret-file, output, Compose-isolation, one-shot, and verification-snapshot rules are documented in the release ceremony guide.

For the first public rehearsal, prepare Ethereum Sepolia (11155111) but do not conflate it with the local Anvil workflow. Anvil is a disposable process on the operator's machine; Sepolia is a persistent public test network with externally funded accounts, provider RPC, public CAM hosting, wallet interaction, explorer records, and an explicit finality decision.

Publish the checked-in CAM bundle and its declared protocol/ABI/UI resources at the chosen URI before deployment. By default, the release planner records the manifest's exact-byte SHA-256; it does not fetch the remote publication. You can choose a zero CAM hash instead. The viewer displays a mild warning for zero and a prominent warning for a hash mismatch, while continuing to display the UI.

Prepare the RPC and deployer-key files:

umask 077
printf '%s\n' 'https://rpc.example.invalid' > /secure/escrow-rpc-url
printf '%s\n' '0x<32-byte-deployer-private-key>' > /secure/escrow-deployer-key

Run the release only from the exact clean commit intended for publication:

CONFIRM_ESCROW_RELEASE_DEPLOY=YES \
ESCROW_RELEASE_EXPECTED_CHAIN_ID=<chain-id> \
ESCROW_RELEASE_CAM_URI=https://published.example/escrow/cam/main.json \
ESCROW_RELEASE_INTENDED_CAM_ROOT_OWNER=0x<intended-root-owner> \
RPC_URL_FILE=/secure/escrow-rpc-url \
DEPLOYER_PRIVATE_KEY_FILE=/secure/escrow-deployer-key \
ESCROW_RELEASE_OUTPUT_DIR=/secure/releases/escrow-<chain>-<version> \
make escrow/release/deploy

The target writes:

plan/release-plan.json
broadcast/DeployEscrowRelease.s.sol/<chain-id>/run-latest.json
artifact/deployment.json

The escrow.release-plan.v2 and escrow.deployment.v2 schemas identify SHA-256 manifest commitments; older v1 artifacts retain their Keccak meaning and are rejected by these lanes.

plan/release-plan.json binds the source commit, expected chain, published CAM URI, selected CAM hash, and intended CamRoot owner. artifact/deployment.json records the three contract addresses, creation transaction hashes, deployed code hashes, deployer, and intended CamRoot owner. It also records whether an ownership transfer was required and whether that account owned CamRoot with no transfer pending when the artifact was created.

The deployed CamEscrow and CamEscrowUI are immutable and have no owner, pause, upgrade, fee, sweep, or recovery authority. CamRoot remains mutable under its owner because it controls the published CAM URI/hash and contract-address bindings. If the intended root owner differs from the deployer, the deployment script submits transferOwnership(newOwner) to nominate it. The script does not sign or submit acceptance for the nominee. After reviewing the addresses and artifact, the nominee must send a separate acceptOwnership() transaction to the saved camRoot address. There is no built-in wait; the deployer remains owner until acceptance. When the intended owner is the deployer, no handover is needed. Do not treat the release as accepted while pendingOwner() is nonzero.

Release verification

Run verification from the same exact clean source commit recorded in deployment.json:

RPC_URL_FILE=/secure/escrow-rpc-url \
ESCROW_DEPLOYMENT_ARTIFACT_FILE=/secure/releases/escrow-<chain>-<version>/artifact/deployment.json \
make escrow/release/verify

The verifier checks:

  • current chain ID and source commit;
  • nonzero deployed code at all three addresses;
  • exact runtime bytecode against contracts compiled from the current source tree;
  • artifact code hashes;
  • CAM URI and digest equal to the saved artifact, including zero;
  • final CamRoot ownership with no pending owner;
  • exact CamEscrow and CamEscrowUI root bindings;
  • the projection's immutable escrow address;
  • ERC-165 interfaces;
  • totalLiabilities() <= address(CamEscrow).balance.

A deployment whose two-step ownership transfer is still pending intentionally fails verification. The original deployment.json remains an immutable record of the post-deployment observation; it is not rewritten after ownership acceptance.

Operational monitoring

Protect the final CamRoot owner as release authority; operationally, use an appropriately controlled account rather than the deployer hot key. Monitor:

  • OwnershipTransferStarted and OwnershipTransferred on CamRoot;
  • CamUpdated and ContractAddressSet on CamRoot;
  • AgreementCreated, AgreementStateChanged, and Withdrawal on CamEscrow;
  • totalLiabilities() against the escrow balance;
  • active deadlines that require a public timeout transaction;
  • arbitrator availability for disputed agreements.

No component automatically executes timeouts. The arbitrator is selected by each client and never acknowledges participation on-chain.
