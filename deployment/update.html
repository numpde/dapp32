Update an existing app

First identify what changed. A new viewer image, new workflow files and a new contract are not interchangeable updates.

ChangeOperationApproval boundary
Browser viewer softwareReplace its image.Server operator; no CAM transaction.
Labels, screens or navigation using compatible interfacesPrepare/host a CAM bundle; publish its reference.Current CAM root owner.
Read-only Solidity projectionDeploy/select a compatible projection and update CAM.Projection deployer and current CAM owner.
Business behavior or incompatible ABIPlan a new deployment and client/state migration.Explicit migration decisions; not a UI refresh.

Example: publish the focused Pay-to-Play navigation

Run on
The release operator's machine with its local Docker engine and private instance.
Requires
Existing compatible business/projection contracts and CAM root, reviewed authored resources, their retained artifacts and the current publication owner's approval.
Changes
Prepared files and approved CAM reference/binding transactions; no intended business-contract replacement.

Check the deployed ABI and voucher policy first. The current guide does not qualify an older Pay-to-Play deployment automatically. The new operation must select the intended authored source revision; editing defaults does not rewrite the retained inputs of an older operation.

CTX=your-local-context
INSTANCE=/absolute/private/pay-to-play-fuji
make pay-to-play/release/verify \
  DOCKER_CONTEXT="$CTX" INSTANCE="$INSTANCE"
make pay-to-play/release/cam/bundle \
  DOCKER_CONTEXT="$CTX" INSTANCE="$INSTANCE"

Choose the compatible retained components and the existing CAM root. Preparation exports their original ABIs, combines the authored files, refreshes resource pins and checks conformance. It sends no transaction. Review the selected identities and the resulting bundle before hosting it.

Host, then publish

Host only the printed bundle contents at a new versioned public location. Keep relative resource paths and browser CORS working. Compare the served bytes with the prepared files; never replace the private instance with a public web directory.

make pay-to-play/release/cam/publish \
  DOCKER_CONTEXT="$CTX" INSTANCE="$INSTANCE"

Select the prepared bundle and existing root, provide its hosted manifest URI, and review the proposed bindings and manifest hash. Approve only the intended publication. The command does not upload files, and a nominated future owner cannot publish before accepting ownership.

Check the new result

make pay-to-play/release/verify \
  DOCKER_CONTEXT="$CTX" INSTANCE="$INSTANCE"
make viewer/release/up \
  DOCKER_CONTEXT="$CTX" INSTANCE="$INSTANCE"

Select the completed publication. Open a fresh viewer session or reload: refreshing a screen's read is not the same as reloading publication resources. Check the selected chain/root, resource integrity and the six navigation destinations. Business balances and keys should belong to the same intended contracts.

Record verification and a working read do not replace a full application smoke test. Check intended authorities and critical actions before accepting a public cutover.

Projection or business changes

release/ui/deploy creates a read-only projection without changing the root. release/ui/update can select or deploy a projection, prepare resources and update the root; it still requires hosting and explicit approvals. See the component reference.

A new business contract has a new address and its own state. Pay-to-Play signatures bind their verifying address; an ABI or manifest edit cannot migrate deposits, permanent keys or vouchers. Stop and design that migration separately.

Recover without guessing

Retain failed attempts and resume the same selected operation. Restoring an older publication is itself an authorized on-chain update and may no longer be compatible; it is not the same as rolling back the viewer image. Use retained evidence to resolve uncertain submissions before attempting another transaction.
